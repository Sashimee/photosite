# Step 1B.10 – Consent banner, Consent Mode v2 and the consent settings page

Plan reference: `docs/PLAN.md` step 1B.10. Owners: web-developer, then compliance-reviewer (a listed 1E.7 checkpoint). Blocked by 1B.1 only, so it is unblocked today — and it is the step that makes analytics legal rather than the step that adds analytics.

| Sub-step | Scope | Branch |
|----------|-------|--------|
| 1B.10a | Banner, consent state, Consent Mode v2 defaults, settings page | `feat/1B.10a-consent-banner` |
| 1B.10b | GTM container load, GA4 config, the conversion events | `feat/1B.10b-analytics-events` |

1B.10a ships with **no tag manager and no measurement id**, so it is useful and testable before Alex has a GA4 or GTM account (0.6). 1B.10b is gated on those ids and does nothing without them.

## What already exists

- `ConsentRecord` in the schema: `userId` **or** `anonymousId`, `purpose` (`ConsentPurpose` enum), `granted`, `policyVersion`, `ip`, `userAgent`, `recordedAt`, indexed on both id columns. Append-only in practice.
- `POST /v1/consents` in `packages/shared/src/contract/gdpr.ts`, **public** (no `security`), rate limited, returning the created record. So the server side of consent is already built; this step is the client that uses it.
- `docs/COMPLIANCE.md` fixes the categories: necessary (always on), analytics, ads/marketing — and requires Consent Mode v2 defaults of denied for `ad_storage`, `ad_user_data`, `ad_personalization` and `analytics_storage`.

## Decisions for this step

- **Nothing that stores or reads a non-essential cookie runs before a choice is made.** The banner is not a formality: with defaults denied and no GTM load until `analytics` is granted, a first visit sets exactly one cookie — the consent cookie itself, which is strictly necessary and therefore lawful without consent.
- **The consent cookie is first-party, `SameSite=Lax`, `Secure`, one year, and holds only the decision and the policy version** — no identifier. An `anonymousId` is generated **only when a choice is recorded**, so a visitor who never interacts is never assigned one.
- **The record is written for signed-out visitors too**, with `anonymousId`, because `COMPLIANCE.md` requires proof of consent and a cookie alone is not proof. When a visitor later signs in, the next decision is written against `userId`; earlier anonymous records are **not** retro-linked, because joining an anonymous trail to an identity is exactly the processing the visitor did not consent to.
- **Three buttons, equally weighted: accept all, reject all, manage.** Reject must be as easy as accept and must not be visually subordinate — CNPD guidance and EDPB decisions are consistent on this, and a "reject" hidden behind "manage" is the single most common finding against consent banners.
- **No dark patterns, stated as a rule** so it survives a future redesign: no pre-ticked non-essential categories, no "legitimate interest" tab that re-enables what was refused, no nag on every page after a refusal (the choice is remembered for a year, the same as an acceptance).
- **Consent Mode v2 defaults are set in the document head, before any tag can load**, as a `<script>` carrying the CSP nonce (`apps/web/src/proxy.ts` already issues one per request). `gtag('consent', 'default', …)` with all four signals denied, `wait_for_update` set. An `update` only follows a granted choice.
- **Withdrawal takes effect immediately**: revoking analytics removes the GTM script, clears `_ga*`/`_gid` cookies on the site's own domain, and records the withdrawal. A banner that only stops *future* loading is not a withdrawal.
- **The settings page is reachable without JavaScript and from the footer on every page** (`/{locale}/consent`), because "withdraw at any time, as easily as you gave it" is the legal standard. It shows the current decision, the policy version it was given under, and when.
- **A policy version bump re-asks.** `policyVersion` comes from `PlatformSetting` (as 1A.12 established) and is compared with the stored decision; a newer version shows the banner again rather than silently inheriting an old consent. 1D.7a is what actually publishes it: `GET /v1/policy-version` (public, uncached, `packages/shared/src/contract/countries.ts`) returns `{ policyVersion: string | null }`, `null` meaning nothing has ever been published — treat that as older than any stored decision and show the banner. The value is a plain incrementing integer as a string, bumped by `POST /v1/admin/countries/{code}/legal-texts` (`apps/api/src/modules/countries/admin-countries.service.ts`) each time any country's legal text is published; it carries no per-country or per-locale meaning of its own; it just names the version a consent decision was made under, matching what `ConsentRecord.policyVersion` (`z.string().min(1).max(20)`) already expects.
- **Analytics is never a condition of use.** No feature is gated on consent, and no "consent or pay" variant.
- **Server-side rendering must not depend on the decision**, so the banner is a client component and pages stay cacheable. The decision is read from the cookie on the client to avoid a flash; when it is absent, the banner renders after hydration rather than blocking first paint.
- **1B.10b's conversion events** (`sign_up`, `request_created`, `quote_sent`, `booking_paid` with value, `profile_published`, `job_offer_published`) push to `dataLayer` only while analytics is granted, and carry **no** personal data — ids, not emails or names. `booking_paid`'s value comes from the same shared fee helper the server uses, never a recomputed number.

## 1B.10a tasks

1. `src/lib/consent.ts`: the cookie shape, read/write, the policy-version comparison, and an `anonymousId` created only on a decision.
2. `src/components/consent/consent-banner.tsx` (three actions), `consent-dialog.tsx` (per-category switches, necessary shown as on and disabled), and a `ConsentProvider` exposing the current state.
3. The Consent Mode v2 default script in the layout head, nonce-carrying, all four signals denied.
4. `POST /v1/consents` wired for both signed-in and anonymous decisions, with failures swallowed silently **only** for the network call — the local decision still applies, because a visitor's refusal must never depend on our API being up. A failed write is logged (and reaches Sentry once 1E.2a lands).
5. `/{locale}/consent` settings page plus a footer link on every page, in all five locales.
6. i18n keys under `web.consent.*`; the banner text says what each category does in plain language, not legalese.
7. Tests:
   - a first visit sets **only** the consent cookie and loads no tag;
   - accept, reject and per-category choices each write the right record and cookie;
   - withdrawal clears `_ga*` cookies and stops the tag;
   - a newer `policyVersion` re-shows the banner;
   - the settings page renders and submits without JavaScript;
   - reject is present and not visually subordinate (assert both buttons exist at the same level, so a redesign that buries one fails);
   - no personal data in any `dataLayer` push.

## 1B.10b tasks (gated on 0.6)

GTM container load after a granted decision, GA4 configuration with EU data settings and no Google Signals, and the conversion events above. Every id comes from env (`NEXT_PUBLIC_GTM_ID`, `NEXT_PUBLIC_GA4_ID`); unset means nothing loads, which is also the correct behaviour on the preview.
