## The gap this step closes

Nothing in the API or worker ever sets `PortfolioImage.status` to `approved` today — `apps/worker/src/queues/processors/image-process.processor.ts:82` moves a processed image to `pending_review` and it stays there, while `apps/api/src/modules/profiles/profiles.service.ts:100` only ever serves `approved` images. Only `packages/db/src/seed.ts` writes `approved`. So a real photographer's portfolio upload is invisible on their public profile. This step is what decides that status, so it is also what makes 1B.3 usable with real uploads on the preview.

## Decisions for this step

- **Vendors sit behind interfaces, and the step ships without them.**
  - Two interfaces in `apps/worker/src/provenance/`: `AiDetectionProvider` (`detect(image) -> { score, vendor, raw }`) and `ReverseSearchProvider` (`search(image) -> { matches: [{ url, domain, similarity }], vendor }`).
  - Each has a `null` implementation selected when its API key env var is absent. A null provider returns "no signal" (not a zero score), the check row records `aiScore: null` / `reverseMatches: []` with the vendor `none`, and the missing signal is excluded from the score rather than counted as clean.
  - This is what unblocks O4: the pipeline, scoring, admin review and status effects are all testable and mergeable before Alex picks Hive vs Sightengine and TinEye vs Google Vision. Swapping in a real vendor is then one adapter file plus env vars — no change to the processor, the scoring or the admin API.
  - The concrete adapters (one per candidate vendor) are **not** written in this step. Writing an HTTP client against an API we cannot call and have not read the response shape of would be guesswork. 1A.10 ends with the null providers wired and an adapter contract plus a vendor checklist in this file.
- **C2PA is its own adapter too.** `c2pa-node` is a native module and the worker image is Alpine-based (`infra/docker/worker.Dockerfile`); a native build failure must not be able to block this step. `C2paReader` defaults to a no-op returning `c2paValid: null` unless `PROVENANCE_C2PA_ENABLED=true`, and adding the dependency (subject to `minimumReleaseAge`, never an exclusion) plus verifying it builds in the worker image is a separate task inside 1A.10b that can be dropped without dropping the step.
- **EXIF comes from the existing pipeline, not a vendor.** `Upload.exif` is already populated by `apps/worker/src/processing/exif-extractor.ts` during `image-process`. `exifCamera` and `exifCapturedAt` on the check row are read from there. No second extraction, and the private EXIF blob never leaves the worker.
- **A new `provenance-check` queue, chained from `image-process`.**
  - Job shape `{ portfolioImageId }` — ids only, no keys or URLs in Redis, matching the `notify` queue rule.
  - The `image-process` processor enqueues it in the same step where it sets `pending_review`, but only for an upload that actually belongs to a `PortfolioImage`. Avatars, covers and chat attachments are never checked. The API does not enqueue it, so a portfolio image created against an already-processed upload (`apps/api/src/modules/profiles/portfolio.service.ts:121`) enqueues it at creation instead — those are the only two entry points.
  - `jobId = portfolioImageId` plus a unique index on `ProvenanceCheck.portfolioImageId` make it idempotent: a retry or a duplicate enqueue updates the one row and never calls a paid vendor twice for an image already checked. The processor short-circuits on an existing row unless the job carries `force: true` (admin re-check).
  - Vendor calls cost money per image, so the worker concurrency for this queue is 2, attempts 3 with exponential backoff, and a vendor timeout of 15s. A vendor error leaves the verdict `review` rather than failing the job forever — an image awaiting a human is a safe resting state.
- **`PROVENANCE_ENABLED`.** With the flag off (the default until a vendor exists) the processor still runs, records the EXIF and C2PA signals and computes a verdict from what it has. It never calls an external service. This is what the preview runs.
- **Scoring is a pure function in `packages/shared`.** `computeProvenanceScore(signals) -> { score, verdict }`, so the worker, the admin API, the web dashboard and the tests all agree, and the weights are reviewable in one place.
  - Signals: `aiScore` (0–1, vendor confidence the image is AI-generated), `reverseMatches` (count and whether any match is on a domain other than the photographer's own linked domains), `c2paValid`, `hasExifCamera`, `exifCapturedAt` sanity (not in the future, not absurdly old).
  - Missing signals lower confidence, not the score. The function returns `verdict: 'review'` whenever the available signals are too thin to justify `pass` — which is every image while O4 is open and `PROVENANCE_ENABLED` is off, except the C2PA-valid case.
  - Thresholds live next to the function as named constants with a comment for each, since they are a judgement call we will tune.
- **Status effects, and never an automatic ban** (D7).
  - `pass` -> `PortfolioImage.status = 'approved'`.
  - `review` -> stays `pending_review`.
  - `fail` -> `'flagged'` (visible to the photographer as "under review", never public).
  - `rejected` is only ever written by an admin decision. The pipeline cannot reject.
  - Every automatic status change writes an `AuditLog` row with the check id and the verdict, as does every admin decision (CLAUDE.md: moderation mutations are audited).
- **Admin endpoints** (`GET /v1/admin/provenance`, `GET /v1/admin/provenance/{id}`, `POST /v1/admin/provenance/{id}/decision`, `POST /v1/admin/provenance/{id}/recheck`).
  - Keyset pagination, filters `verdict` and `status`, oldest-first by default so the queue drains.
  - Guarded by the admin session helper 1A.9b introduces (`apps/api/src/common/auth/require-admin.ts` — admin role plus a verified second factor within the session window). 1A.10 must not add a second, weaker admin guard; if 1A.9b has not merged when 1A.10b starts, 1A.10b waits for it rather than forking one.
  - The decision body is `{ status: 'approved' | 'flagged' | 'rejected', note }`. `reviewedByAdminId`, `reviewedAt` and `note` land on the check row; the note is admin-internal and never returned to the photographer.
  - The list response carries the photographer's `displayName` and profile slug and the image's public thumbnail URL — no client PII, no private originals.
- **What the photographer sees.** `GET /v1/me/portfolio` (1A.4) gains a `provenance: { verdict, status, checkedAt }` field. No score, no vendor, no match URLs and no admin note — that would be a map of how to evade the check. 1B.8 renders it as processing / live / under review.
- **Sending images to third parties is a data-processing decision, not a technical one.**
  - Only the **public, EXIF-stripped** variant of an image the photographer published is ever sent, through a presigned GET valid for 5 minutes, and only when `PROVENANCE_ENABLED` is on. Private originals and the private bucket are never exposed to a vendor.
  - Match URLs returned by a reverse-search vendor are stored but never logged, and the redaction list in the API and worker loggers gains `reverseMatches` and `raw`.
  - Each vendor is a sub-processor: it must appear in the privacy policy and in `docs/COMPLIANCE.md`, with a DPA signed and an EU/adequacy transfer basis, **before** `PROVENANCE_ENABLED` is turned on anywhere real. That is Alex's, and it is recorded in the human follow-ups below.
- **Retention.** A `ProvenanceCheck` outlives its image's review (it is the evidence for a moderation decision) but not forever: it is deleted with the `PortfolioImage` and, for a passed check, its `raw` vendor payload is cleared after 90 days by the existing cleanup sweep. Recorded in `docs/COMPLIANCE.md` retention.

## 1A.10a tasks

1. **Contract** (`packages/shared/src/contract/provenance.ts`): check, admin list/detail/decision and recheck schemas with error responses; `PROVENANCE_VERDICTS` enum; the `provenance` field on the photographer's own portfolio item; `ProvenanceCheckJobSchema` and `provenance-check` in `packages/shared/src/queues.ts`; regenerate `openapi.json` and the api-client; add the routes to `not-yet-implemented.ts`.
2. **Scoring helper** (`packages/shared/src/provenance-score.ts`) with its unit tests: every signal missing, each signal alone, the C2PA-valid pass, a high `aiScore`, matches on foreign domains, a future `exifCapturedAt`.
3. **Schema** (schema-migrator, `docs/DATA-MODEL.md` first): `ProvenanceCheck` per the data model (`portfolioImageId` unique, `aiScore`, `aiVendor`, `reverseMatches` JSON, `c2paValid`, `exifCamera`, `exifCapturedAt`, `score`, `verdict`, `reviewedByAdminId`, `reviewedAt`, `note`, `raw` JSON, timestamps), a `ProvenanceVerdict` enum, an index on `(verdict, createdAt)` for the queue, cascade delete from `PortfolioImage`; migration via `migrate diff` applied to `photoo` and `photoo_test`.

## 1A.10b tasks

1. **Worker** (`apps/worker/src/provenance/`): the two provider interfaces plus their null implementations, `C2paReader` (no-op default), the `provenance-check` processor, env validation for `PROVENANCE_ENABLED`, `PROVENANCE_C2PA_ENABLED` and the per-vendor key vars (absent is valid and selects the null provider), and the enqueue from `image-process`.
2. **API**: `ProvenanceModule` with the admin endpoints, the `provenance` field on the photographer's own portfolio list, `AuditLog` writes, logger redaction, and the enqueue for a portfolio image created against an already-processed upload.
3. **Tests**: idempotency (a second job does not re-call a vendor); a vendor timeout leaves `review`; each verdict's status effect and its audit row; the pipeline never writes `rejected`; admin decision ownership and 403 without a verified second factor; the photographer's view omits score, vendor, matches and note; a non-portfolio upload enqueues nothing; keyset pagination and a malformed cursor returning 400.
4. **Shared checkpoint** (security-reviewer and compliance-reviewer together, one pass): presigned URL scope and lifetime, private bucket never reachable by a vendor, match URLs and raw payloads absent from logs, admin guard strength, IDOR on the admin routes, sub-processor and retention entries present in `docs/COMPLIANCE.md`.

## Vendor adapter checklist (for whoever writes the real adapter)

An adapter is complete when it: reads its key from env and is absent-safe; accepts a presigned URL and nothing else; enforces the 15s timeout; maps the vendor's confidence onto 0–1 with the mapping written down; surfaces rate-limit and quota errors as retryable and everything else as a `review` outcome; stores the raw payload under `raw` without logging it; and has a unit test against a recorded response fixture, never a live call in CI.
