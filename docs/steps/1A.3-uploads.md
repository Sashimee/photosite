Plan reference: `docs/PLAN.md` step 1A.3. Owners: schema-migrator (model), devops-engineer (ClamAV service), api-developer (API module, worker). Security-reviewer checkpoint afterwards (1E.6: uploads). Blocked by 1A.1 (merged).

## 1A.3a tasks

1. Schema (schema-migrator, DATA-MODEL first): `Upload` with `id`, `ownerId` → User, `purpose` enum (from `UPLOAD_PURPOSES` in shared), `status` enum (`pending_upload`, `uploaded`, `scanning`, `clean`, `infected`, `failed`, `processed`), `mimeType`, `declaredSizeBytes`, `actualSizeBytes?`, `objectKey` (private bucket, never serialised), `variants` JSON (public keys, never raw keys to clients), `exif` JSON (private), `virusScanStatus` enum mirroring shared `VIRUS_SCAN_STATUSES`, `expiresAt` for unconfirmed uploads, timestamps; indexes on `ownerId`, `status`. Migration via `migrate diff` (shadow DB) + `migrate deploy`.
2. ClamAV (devops-engineer): `clamav/clamav` pinned image in `compose.dev.yml`, bound to 127.0.0.1, healthcheck, named volume for signatures; `CLAMAV_HOST`/`CLAMAV_PORT` in `apps/worker/.env.example`; note in human-followups that production needs ClamAV sized for signature memory (~1.5 GB RAM).
3. Worker bootstrap (api-developer), reusing API patterns (explicit `@Inject`, zod env, pino with redaction, Prisma provider): NestJS standalone application context, BullMQ workers registered per queue with concurrency from env, graceful shutdown draining jobs, a minimal HTTP health endpoint for the container (`/health`, `/ready` checking Redis, DB), and a shared queue-name and job-payload zod schema module in `packages/shared` (`queues.ts`) used by both API producers and worker consumers.
4. Move the email queue consumer contract into `packages/shared/queues.ts` (the dev Mailpit consumer in the API stays until 1A.7).
5. Tests: env validation, graceful shutdown, a job payload rejected by zod ends in failed with a logged reason, health endpoints (integration against the local stack).

## 1A.3b tasks

Owner: api-developer; devops-engineer for the CI MinIO service. Security-reviewer checkpoint (1E.6: uploads) before merge.

1. Contract first (`packages/shared/contract/uploads.ts`): align `UploadSchema` with the model (`status`, `virusScanStatus`, `declaredSizeBytes`, `actualSizeBytes`, no keys); `CreateUploadResponseSchema.headers` lists the exact headers the client must send; regenerate openapi and the client.
2. Storage module in `apps/api` (and reused by the worker through a small shared factory, no duplication of bucket names): `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`, pinned; env `S3_*` from `.env.example`; private bucket for originals and private files, public bucket for image variants only.
3. `POST /v1/uploads`: validates purpose, mime allow-list and size limit (shared), creates `Upload` (`pending_upload`, `expiresAt` = now + 10 min), key `u/<ownerId>/<uploadId>` (no user-controlled path parts), returns a presigned PUT signing `Content-Type` and `Content-Length` so storage rejects other values; 10 min expiry. Rate limit per IP and per account (reuse the auth rate-limit service pattern, extracted to a common module rather than copied).
4. `POST /v1/uploads/:id/complete`: owner only; HEAD the object; reject (and delete the object) when size differs from declared or exceeds the purpose limit, or when content-type differs; once the HEAD checks pass, `CopyObject` from `u/<ownerId>/<uploadId>` to `o/<ownerId>/<uploadId>` (a key no presigned PUT was ever issued for) with `MetadataDirective: REPLACE` and the declared content type, delete the `u/` key, persist the new key; sets `uploaded`, `actualSizeBytes`, enqueues `file-scan`. Idempotent for an already completed upload.
5. `GET /v1/uploads/:id`: owner only, returns status. `GET /v1/uploads/:id/download`: owner only for now (other viewers come with chat/verification access rules), only when `virusScanStatus = clean`, presigned GET of 5 min with `ResponseContentDisposition: attachment` for non-images; 409 otherwise.
6. Worker `file-scan`: stream the object to clamd INSTREAM with a size cap and timeout; `clean` -> for image purposes enqueue `image-process`, otherwise status `clean`; `infected` -> delete object, status `infected`, AuditLog (`actorType: system`); clamd unreachable -> retry with backoff, then `failed`.
7. Worker `image-process`: magic-byte check (`file-type`) must match the declared mime; `sharp` with pixel limit (e.g. 100 MP) to prevent decompression bombs; auto-orient, extract EXIF (camera, capture time, GPS kept only in the private `exif` field), re-encode to JPEG/WebP variants thumb 320, medium 1280, large 2560 without metadata into the public bucket under an unguessable key; status `processed`; original stays private.
8. Worker `uploads-cleanup`: repeatable job (every 10 min) deleting objects and marking `failed` for `pending_upload` rows past `expiresAt`.
9. CI: MinIO service in `.github/workflows/ci.yml` (same tag as compose) with bucket creation, env added to the turbo test env list.
10. Tests: API integration against MinIO (presign, upload with a real PUT, size mismatch rejection, wrong content type, non-owner 404, download before clean 409); worker unit tests with a clamd INSTREAM test double (FOUND, OK, timeout); image-process with fixture images (EXIF stripped in variants, GPS only in private exif, mismatched magic bytes rejected, oversized pixel count rejected); cleanup job. Remove the uploads routes from `not-yet-implemented.ts`. Coverage thresholds must hold.

ClamAV is not part of CI (`.github/workflows/ci.yml`): the real image's initial `freshclam` download takes minutes, which would blow the CI time budget. Instead, `file.scan` unit tests run against a test double that speaks the clamd INSTREAM protocol over a local TCP socket (returning canned `FOUND`/`OK` replies), plus one integration test gated behind an env var (e.g. `CLAMAV_INTEGRATION_TEST=true`) that only runs locally against the real `clamav` dev-stack service and is skipped in CI.
