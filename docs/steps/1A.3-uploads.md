Plan reference: `docs/PLAN.md` step 1A.3. Owners: schema-migrator (model), devops-engineer (ClamAV service), api-developer (API module, worker). Security-reviewer checkpoint afterwards (1E.6: uploads). Blocked by 1A.1 (merged).

## 1A.3a tasks

1. Schema (schema-migrator, DATA-MODEL first): `Upload` with `id`, `ownerId` → User, `purpose` enum (from `UPLOAD_PURPOSES` in shared), `status` enum (`pending_upload`, `uploaded`, `scanning`, `clean`, `infected`, `failed`, `processed`), `mimeType`, `declaredSizeBytes`, `actualSizeBytes?`, `objectKey` (private bucket, never serialised), `variants` JSON (public keys, never raw keys to clients), `exif` JSON (private), `virusScanStatus` enum mirroring shared `VIRUS_SCAN_STATUSES`, `expiresAt` for unconfirmed uploads, timestamps; indexes on `ownerId`, `status`. Migration via `migrate diff` (shadow DB) + `migrate deploy`.
2. ClamAV (devops-engineer): `clamav/clamav` pinned image in `compose.dev.yml`, bound to 127.0.0.1, healthcheck, named volume for signatures; `CLAMAV_HOST`/`CLAMAV_PORT` in `apps/worker/.env.example`; note in human-followups that production needs ClamAV sized for signature memory (~1.5 GB RAM).
3. Worker bootstrap (api-developer), reusing API patterns (explicit `@Inject`, zod env, pino with redaction, Prisma provider): NestJS standalone application context, BullMQ workers registered per queue with concurrency from env, graceful shutdown draining jobs, a minimal HTTP health endpoint for the container (`/health`, `/ready` checking Redis, DB), and a shared queue-name and job-payload zod schema module in `packages/shared` (`queues.ts`) used by both API producers and worker consumers.
4. Move the email queue consumer contract into `packages/shared/queues.ts` (the dev Mailpit consumer in the API stays until 1A.7).
5. Tests: env validation, graceful shutdown, a job payload rejected by zod ends in failed with a logged reason, health endpoints (integration against the local stack).

## 1A.3b tasks (detailed when 1A.3a merges)

S3 client (MinIO locally) with presigned PUT (content-type + content-length conditions, 10 min expiry, key `u/<ownerId>/<uploadId>`), presigned GET (short-lived, owner or authorised viewer only), per-purpose allow-lists from shared, per-IP and per-account upload rate limits, `complete` verifies object size and type via HEAD then enqueues `file.scan`; worker `file.scan` streams to ClamAV (INSTREAM), marks clean/infected (infected objects deleted, AuditLog); `image.process` re-validates magic bytes, re-encodes with sharp, writes thumb/medium/large variants to the public bucket without EXIF, stores extracted EXIF privately; download only for `clean`; unconfirmed uploads expire via a repeatable cleanup job. Remove the uploads routes from `not-yet-implemented.ts`.

ClamAV is not part of CI (`.github/workflows/ci.yml`): the real image's initial `freshclam` download takes minutes, which would blow the 15-minute CI budget. Instead, `file.scan` unit tests run against a test double that speaks the clamd INSTREAM protocol over a local TCP socket (returning canned `FOUND`/`OK` replies), plus one integration test gated behind an env var (e.g. `CLAMAV_INTEGRATION_TEST=true`) that only runs locally against the real `clamav` dev-stack service and is skipped in CI.
