## What the API already gives us

Read from `packages/shared/src/contract/auth.ts` and `apps/api/src/modules/auth/`:

- `POST /v1/auth/sign-up` `{ email, password, roles[], locale }` → `201 { user }`, and a verification email. It does **not** sign the user in.
- `POST /v1/auth/sign-in` `{ email, password }` → either `{ user, session: { token, expiresAt } }` or `{ twoFactorRequired: true }`.
- `POST /v1/auth/sign-in/totp` `{ code }` or `{ backupCode }` → `{ user, session: { token, expiresAt } }`.
- `GET /v1/auth/session`, `POST /v1/auth/sign-out`, `POST /v1/auth/sessions/revoke-all`, `POST /v1/auth/roles`.
- `POST /v1/auth/verify-email` `{ token }`, `POST /v1/auth/password-reset/request` `{ email }`, `POST /v1/auth/password-reset/confirm` `{ token, password }`.
- `GET /v1/auth/oauth/{provider}/start` → 302 to the provider, and the callback ends on the **web** app.

`requireSession` accepts a bearer token (`apps/api/src/modules/auth/session.ts`), and `session.token` from sign-in is exactly that token, so the mobile app is a first-class client for everything except OAuth.

## Decisions for this step

- **The bearer token lives only in `expo-secure-store`**, through the existing `src/lib/session.ts`. Never in AsyncStorage, never in a query string, never in a log line or a Sentry breadcrumb. `expiresAt` is stored beside it so the app can treat an expired token as signed out without a round trip.
- **One auth state holder** (`src/lib/auth-context.tsx`): `{ status: 'loading' | 'signed-out' | 'signed-in', user }`. It restores the token at boot, calls `GET /v1/auth/session` once, and clears the token on 401. Every screen reads this, so there is a single place where sign-out happens.
- **A 401 from any request signs the user out.** The api-client middleware from 1C.1 gains a response hook that clears the session and lets the router fall back to the auth stack. This is what makes a revoked session (password reset, "sign out everywhere") actually end on the device.
- **Routing.** An `app/(auth)/` group with `sign-in`, `sign-up`, `verify-email`, `forgot-password`, `reset-password`, and a `two-factor` screen. `app/(tabs)/_layout.tsx` redirects to `(auth)/sign-in` while signed out; the auth group redirects to the tabs while signed in. Requests, Messages and Account require a session; Discover does not, because browsing is public on the web too.
- **Sign-up** mirrors 1B.2: email, password with the same strength rules as the shared `PasswordSchema` (validated client-side with the shared zod schema, never a second hand-written rule), role choice (client or photographer, multi-select as the contract allows), and locale defaulted from `expo-localization` and overridable. On `201` the app goes to a "check your email" screen.
- **Email verification without deep links.** Universal links and Android App Links both need the Apple/Play accounts (0.6), so this step does not rely on them:
  - the "check your email" screen's primary action depends on whether a token is already on the device: sign-up never returns a session, so in that (common) case the action is "I've verified my email — sign in", routing straight to sign-in; only when a token already exists does the button instead retry `GET /v1/auth/session`, which is the one case where a re-check resolves anything;
  - it also accepts the token pasted from the email as a fallback, posting it to `POST /v1/auth/verify-email`;
  - the `photoo://` scheme from `app.config.ts` is already registered and `expo-linking` parses `photoo://verify-email?token=…` and `photoo://reset-password?token=…` if the email ever carries them, so turning links on later is a mail-template change, not an app change.
  - Recorded in human follow-ups: once the store accounts exist, add the association files and switch the emails to universal links.
- **TOTP.** `{ twoFactorRequired: true }` routes to the two-factor screen, which posts a 6-digit code or a backup code. The pending credentials are **not** kept: the contract's TOTP call continues the same server-side attempt, so the screen holds no password in memory beyond the request. Enrolment and disabling (`/auth/totp/*`) are account settings and belong to 1C.2b.
- **Password reset** posts the email, always shows the same neutral confirmation (the API already answers uniformly), and the reset screen takes the token plus a new password.
- **Rate limits are user-visible.** A `429` maps to a localised "too many attempts, try again later" and disables the submit button for the window the API reports, rather than a generic error. Lockout (`403`) gets its own message.
- **All strings under `mobile.auth.*` and `mobile.account.*` in `en.json`**, other locales through i18n-maintainer drafts. Error copy is keyed by the API's `code`, with one generic fallback.
- **No biometric unlock, no "remember me", no social account linking** in this step. Biometrics are worth their own increment once there is something valuable behind them.

## 1C.2a tasks (mobile-developer)

1. `src/lib/auth-context.tsx`, plus the 401 hook in `src/lib/api.ts`, and `session.ts` extended with `expiresAt`.
2. `(auth)` route group and the screens above, NativeWind styling consistent with 1C.1's neutral theme, `KeyboardAvoidingView`, `autoComplete`/`textContentType` set so password managers work, and `secureTextEntry` everywhere a password is typed.
3. Guarded tabs: redirect rules in the two layouts, and a splash hold while `status === 'loading'` so no screen flashes.
4. i18n keys and `pnpm i18n:check` green.
5. Tests (jest-expo, as 1C.1 chose):
   - the auth context restores a stored token and signs out on a 401;
   - an expired `expiresAt` is treated as signed out without a request;
   - sign-up posts the shared schema's shape and routes to "check your email";
   - a `twoFactorRequired` response routes to the two-factor screen, and a wrong code shows the mapped error;
   - 429 and 403 map to their own messages;
   - the token is never written anywhere but `expo-secure-store` (assert on the mocked module);
   - a render test against the real `en` catalog.

## 1C.2b tasks (mobile-developer)

1. Account screen: name/email, roles with "become a photographer" posting `POST /v1/auth/roles`, locale switcher persisting to the API and to i18next, TOTP enrol/verify/disable, sign out, and "sign out everywhere" calling `/auth/sessions/revoke-all`.
2. TOTP enrolment shows the secret and backup codes once, with a copy action and an explicit "I stored these" confirmation before `verify`.
3. Account deletion and data export are **out of scope**: they are 1A.12, which is planned but not built. The screen links to the web account page for now and the gap is recorded in the 1A.12 plan.
4. Tests: role addition updates the context, locale change re-renders strings, "sign out everywhere" clears the local session too, and backup codes are never re-displayed after confirmation.

## 1C.2c tasks (api-developer, then mobile-developer)

The gap: `GET /v1/auth/oauth/{provider}/start` ends on the web app with a cookie session, which a native app cannot read.

- **API**: the start route takes an optional `client=mobile`, and the callback then redirects to the app scheme with a **one-time code** (single use, 60-second TTL, stored in Redis keyed by a random id, bound to the OAuth state). `POST /v1/auth/oauth/exchange` `{ code }` returns `{ user, session }`. The session token itself never appears in a redirect URL, because URLs land in logs and in the OS's recent-apps history.
- **Mobile**: `expo-web-browser`'s `openAuthSessionAsync` against the start URL, returning to `photoo://auth/callback?code=…`.
- **Provider buttons are gated on configuration**: a small `GET /v1/auth/providers` (or the existing OpenAPI-visible set filtered by `isProviderConfigured`) tells the app which providers to show, so an app build with no Apple credentials shows no Apple button rather than a broken one.
- **Native Apple Sign In** (`expo-apple-authentication`) is required by App Store review whenever another social login is offered. It needs the Apple Developer account, so it stays a human follow-up and 1C.2c ships with the web-session flow only; the button switches to native once `usesAppleSignIn` can be turned on.
- Security review of this sub-step: one-time code single use, state binding, no token in any URL, and the redirect allow-list.
