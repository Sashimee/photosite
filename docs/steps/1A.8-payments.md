## The blocker, and how this step works around it

A real Stripe platform account needs the operating legal entity (open decision **O2**), which does not exist yet. Waiting would stall the largest step in Phase 1 and everything downstream of it.

- **All Stripe access goes through one `StripeGateway` interface** (`apps/api/src/modules/payments/stripe/`), with the methods this step needs and nothing more: `createConnectedAccount`, `createAccountLink`, `createPaymentIntent`, `createTransfer`, `createRefund`, `reverseTransfer`, `retrieveEvent`, `constructWebhookEvent`.
- Two implementations: `LiveStripeGateway` (the `stripe` SDK, used when `STRIPE_SECRET_KEY` is set) and `FakeStripeGateway` (deterministic ids, in-memory state, used in tests, in CI and in local dev). The fake is a **test double, never a fallback in production**: the API fails to boot when `NODE_ENV=production` and the key is absent, the same way the worker treats SMTP.
- The official `stripe-mock` container is added to the local stack behind a compose profile for wire-level checks of request shapes the fake cannot verify. It is not part of CI, because it does not implement Connect faithfully enough to be worth the flake.
- What genuinely cannot be built without the account: verifying a real webhook signature end to end, Connect Express onboarding against Stripe-hosted pages, and Radar/3-D Secure behaviour. Those are listed as human follow-ups with the exact test-mode checklist to run once the keys exist, so the gap is a known, scheduled verification rather than an unknown.

Everything else — the state machine, the ledger, idempotency, refunds, the release job, the PDFs — is fully testable against the fake and ships now.

## Decisions for this step

- **Money never comes from the client.** The PaymentIntent amount is read from the accepted `Quote` row inside the same transaction that creates the `Booking`. No endpoint accepts an amount, a fee or a currency from the caller. The fee is recomputed with the shared helper from `Quote.feePercent` (the snapshot taken at quote creation) and asserted to equal `Quote.platformFeeCents`; a mismatch fails loudly rather than charging a number nobody agreed to.
- **Idempotency everywhere money moves.**
  - Every Stripe call carries an idempotency key derived from our own ids (`booking_<id>_pi`, `booking_<id>_transfer`, `refund_<bookingId>_<n>`), so a retried request never creates a second charge or transfer.
  - `Booking.paymentIntentId` is unique; `LedgerEntry` is unique on `(bookingId, type, stripeObjectId)`, which makes a replayed webhook a no-op at the database level and not merely in application logic.
  - `StripeEvent` stores `event.id` as the primary key and is inserted **before** the event is processed, in the same transaction as the state change. A duplicate insert means "already handled" and the handler returns 200 without redoing the work.
- **The webhook is the source of truth for state, never the API response.** Creating a PaymentIntent does not mark a booking paid; only `payment_intent.succeeded` does. The endpoint verifies the signature against the **raw body** (Fastify needs an explicit raw-body capture scoped to this route only — a global one would weaken every other route's parsing), rejects anything unsigned with 400, and returns 200 as soon as the event is recorded, with side effects (email, push, PDFs) enqueued rather than done inline. A webhook that does slow work is a webhook Stripe retries.
- **Unknown or out-of-order events are recorded, not dropped.** An event for a booking we do not know yet (webhook arriving before our own transaction commits) is stored and retried by a small sweep rather than discarded, because Stripe does not guarantee ordering and the alternative is a booking permanently stuck in `pending_payment`.
- **The booking state machine is explicit and one-directional**, with the allowed transitions in one table in `packages/shared` so the API, the admin app and the tests share it: `pending_payment -> paid_held -> in_progress -> delivered -> released`, with `refunded`, `disputed` and `cancelled` as terminal branches from defined states only. Any transition attempt outside the table is a 409 and writes nothing. Every transition writes an `AuditLog` row (CLAUDE.md: money mutations are audited).
- **Release.** `POST /v1/bookings/{id}/accept-delivery` (client) or the worker's `booking-release` repeatable job at `releaseDueAt` creates the `Transfer` with `source_transaction = chargeId` and the booking's `transfer_group`. `autoReleaseDays` comes from `PlatformSetting` (seeded 7, open decision O3), read at delivery time and stored on the booking as `releaseDueAt` so a later settings change never moves money that was already promised on different terms.
- **Refunds.** Before release: full or partial refund against the PaymentIntent, booking to `refunded`. After release: a transfer reversal first, then the refund, and **admin only, behind the same verified-2FA admin guard as verification** — this is the single most dangerous operation in the system and it does not get a self-service path in Phase 1. A partial refund after release that exceeds the reversible balance fails with a clear error rather than a partial state.
- **Disputes.** `charge.dispute.created` moves the booking to `disputed`, freezes release (the release job skips disputed bookings), and notifies an admin. `charge.dispute.closed` records the outcome. No automatic refund or reversal on a dispute — a human decides.
- **The ledger is append-only and is the reconciliation source of truth.** One row per money movement (`charge`, `platform_fee`, `transfer`, `refund`, `reversal`, `payout`), never updated, never deleted, with the Stripe object id. A test asserts that for a completed booking the ledger sums to zero against the charge, which is the invariant that catches a whole class of bugs.
- **PDFs are generated in the worker, not the API**, into the private bucket, with a presigned download for the owner (client for the receipt, photographer for the fee invoice). `pdfkit` over React-based renderers: it streams, it has no React runtime in a worker process, and it is a much smaller dependency surface — subject to `minimumReleaseAge` like everything else. The receipt states that the photographer is the seller and that their own invoicing obligations remain theirs (`docs/PAYMENTS.md`).
- **VAT on the fee is a flag, not a hardcoded rate.** The shared fee helper gains an optional VAT-on-fee input driven by `Country.vatRate`, defaulting to off until the accountant confirms (O2). Rounding is half-up on cents, as the spec says, and there is a test for the .5 case specifically.
- **Publishing gating.** `PhotographerProfile.isPublished` already requires `verificationStatus = verified`; this step adds `stripePayoutsEnabled`, mirrored from `account.updated`. A photographer who loses payouts capability is unpublished by the webhook handler, and notified — silently leaving them published would take bookings we cannot pay out.
- **Currency is EUR only at launch**, asserted at the boundary. A quote in any other currency cannot be accepted, with an explicit error, rather than being charged in the wrong currency.

## 1A.8a tasks

1. **Contract** (`packages/shared/src/contract/payments.ts`): booking read and list, accept-delivery, refund request, admin refund and reversal, Connect onboarding link, and the webhook payload type; `BOOKING_STATUSES`, `LEDGER_ENTRY_TYPES`, `DISPUTE_STATUSES`; the transition table; `BookingReleaseJobSchema`, `ReceiptPdfJobSchema` and their queue names; regenerate openapi and the api-client; add the routes to `not-yet-implemented.ts`.
2. **Fee helper**: the VAT-on-fee flag and its tests, including half-up rounding at exactly .5 cents.
3. **Schema** (schema-migrator, `docs/DATA-MODEL.md` first): `Booking` (unique `quoteId`, unique `paymentIntentId`, `chargeId`, `transferId`, `releaseDueAt`, timestamps per the data model), `Delivery`, `LedgerEntry` (append-only, unique on `(bookingId, type, stripeObjectId)`), `StripeEvent` (`id` PK, `type`, `receivedAt`, `processedAt`, `payload`), `Dispute`; indexes for the release sweep (`status, releaseDueAt`) and the admin queues; migration applied to `photoo` and `photoo_test`; seed gains a paid booking so 1B.7 and 1D.5 have something to render.

## 1A.8b–d tasks

- **1A.8b**: the gateway interface and both implementations, env validation (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_CONNECT_*`), onboarding endpoints (`POST /v1/me/stripe/account`, `POST /v1/me/stripe/account-link`), the `account.updated` handler, publish gating and its notification.

## Tests that must exist before this merges

Beyond the per-sub-step unit tests: accept -> pay -> deliver -> release end to end against the fake gateway; accept -> pay -> refund; the dispute path freezing release; webhook replay (the same event id twice changes nothing); an out-of-order event arriving before its booking; a client-supplied amount being ignored; a quote in a non-EUR currency being refused; the ledger summing to zero for a completed booking; the release job skipping disputed and already-released bookings and being idempotent across two runs; a transfer never exceeding `subtotalCents - platformFeeCents`; and an admin refund after release requiring a verified second factor.
