## What the API gives us

From 1A.9b, now on the `verification` permission with **fresh 2FA** after 1A.11b migrated it:

- `GET /v1/admin/verification-cases` — keyset, filterable by `status` and `countryCode`.
- `GET /v1/admin/verification-cases/{id}` — the case with its documents. `VerificationDocument.downloadUrl` is **optional**: a document whose upload has not cleared the virus scan has no URL, and the UI must treat that as a state, not an error.
- `POST .../start-review`, `POST .../approve`, `POST .../reject` (with a reason).
- Business fields (`businessName`, `vatNumber`, `businessRegistrationNumber`) are encrypted at rest and decrypted server-side for this endpoint only.

Statuses are `draft`, `submitted`, `in_review`, `approved`, `rejected`. `draft` never appears in the queue — the photographer has not submitted it.

## Decisions for this step

- **The queue defaults to `submitted`, oldest first.** A verification queue sorted newest-first quietly starves the oldest applicant, who is the one already waiting longest. The sort is not a user preference in this step.
- **`start-review` is a claim, and the UI treats it as one.** Opening a case does **not** claim it; the reviewer presses a button. A list shows who is reviewing what, so two admins do not work the same case. Reviewing an already-claimed case is allowed but warns first — a claim is coordination, not a lock.
- **Documents are fetched on click, never eagerly.** Each `downloadUrl` is a short-lived presigned GET; rendering ten of them on list load would put ten live URLs to identity documents into one page's HTML. One document at a time, fetched when the reviewer asks for it.
- **The viewer is an isolated surface.** Documents render in a dialog with no `target="_blank"`, no download button, and `referrerPolicy="no-referrer"`. PDFs render in an `<object>`/`<iframe>` **sandboxed** without `allow-same-origin`, because a PDF is attacker-supplied content and the admin app holds a privileged session. A missing `downloadUrl` renders "still being scanned", not a broken image.
- **No document ever reaches browser storage or a cache.** `Cache-Control: no-store` is already set on the admin app; the dialog revokes any object URL on close.
- **The decision needs a reason, and rejection needs a *specific* reason.** A free-text box plus a required category (illegible, expired, name mismatch, wrong document, suspected forgery). The photographer sees the category and the text, so the text must be written for them — the field label says so. "Rejected" with no actionable reason produces a support ticket and a resubmission of the same document.
- **Approve and reject both re-prompt for the second factor** (the API demands fresh 2FA), and the UI says why rather than showing a bare failure.
- **The case detail shows the decision history** from the audit log (`targetId={caseId}`), so a reviewer can see that a case was rejected twice before and why.
- **Nothing in this step exposes the document bytes to the admin app's own logs or Sentry.** 1E.2a's `beforeSend` already drops request bodies; this step adds no logging of URLs or document ids beyond what the audit log records server-side.
- **A photographer's profile is not published by this screen.** Approval has status effects the API owns (1A.9); the UI shows what changed after the fact rather than reimplementing the rule.
- **1D.3b is a separate sub-step** because `Country.requiredDocuments` is a `Json` column driving what applicants must upload: editing it changes what every future applicant in that country sees, so it needs its own review, a preview of the resulting applicant form, and a confirmation naming the country.

## 1D.3a tasks

1. `app/(admin)/verification/page.tsx` — `DataTable` with status and country filters, defaulting to `submitted` oldest-first, showing who is reviewing each case.
2. `app/(admin)/verification/[id]/page.tsx` — applicant identity, decrypted business fields, document list, decision history, and the actions.
3. `components/verification/document-viewer.tsx` — click-to-fetch, sandboxed, no download, revoking URLs on close, with the "still being scanned" state.
4. Decision dialogs: approve (confirmation naming the applicant) and reject (required category plus text, labelled as visible to the applicant).
5. Claim handling: the `start-review` button, the warning when a case is already claimed, and the `409` path if it was claimed while the page was open.
6. i18n under `admin.verification.*`, English only.
7. Tests:
   - the queue defaults to `submitted` oldest-first;
   - a document URL is requested only on click, and never appears in the initial HTML;
   - a document with no `downloadUrl` renders the scanning state rather than a broken viewer;
   - rejection requires both a category and text, and the dialog says the text is shown to the applicant;
   - `TWO_FACTOR_REQUIRED` on approve routes to re-verification and returns to the case;
   - a case claimed by another admin warns before review;
   - the PDF container carries `sandbox` without `allow-same-origin`;
   - one test renders against the real `en` catalog.

## 1D.3b tasks

The per-country editor for `requiredDocuments`, with a preview of the applicant-facing form, a confirmation naming the country, and an audit entry. Its own PR, after 1D.3a.
