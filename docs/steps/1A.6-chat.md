## Decisions for this step

- **Participants as rows, not arrays.**
  - `ConversationParticipant(conversationId, userId, lastReadAt, archivedAt, joinedAt)`, unique on the pair, replaces `participantIds[]`, `archivedBy[]` and `Message.readBy`.
  - Membership checks, unread counts (`messages.createdAt > lastReadAt` and sender ≠ me) and archive then become indexed queries instead of JSON scans. DATA-MODEL is updated first.
- **Who can talk to whom** (anti-circumvention of the platform fee, no open DMs):
  - A `quote` conversation is created when a quote is created (request or direct), between the photographer's user and the client. It's idempotent on `(type, subjectId)` through a unique index, and created in the same transaction as the quote.
  - A `booking` conversation is reused from the quote at 1A.8. `type` stays for later, and 1A.8 decides whether booking reuses the quote thread (proposal: yes, no new row).
  - `request` and `direct` conversation types stay in the enum but aren't creatable in the MVP. There's no endpoint to start a conversation freely.
  - Existing seeded quotes get conversations in the seed.
- **Messages.**
  - Body is 1–4000 chars, trimmed. A message needs a body or at least one attachment, with at most 10 attachments.
  - Edits aren't supported in the MVP (`editedAt` stays null).
  - Delete is a soft delete by the sender within 15 minutes; the body is blanked, and "message deleted" is rendered.
  - Plain text only; clients render it as text, never HTML.
- **Attachments.**
  - `MessageAttachment(messageId, uploadId)`, which reuses `Upload` (purpose `chat_attachment`) instead of a separate `Attachment` table. DATA-MODEL `Attachment` becomes this join.
  - The uploader must be the sender. The upload must be `clean` or `processed` (ClamAV passed) before it can be attached, otherwise 422.
  - Images and PDF only, per the existing upload MIME allow-list for this purpose.
  - Served through short-lived presigned GET (5 minutes), generated per request for conversation participants only.
- **REST** (existing contract in `packages/shared/src/contract/chat.ts`; fill the gaps contract first):
  - `GET /v1/conversations`: mine, keyset by `lastMessageAt desc, id`, `archived` filter, with `unreadCount` and last message preview. The preview blanks deleted messages.
  - `GET /v1/conversations/{id}` and `GET /v1/conversations/{id}/messages`: keyset `createdAt desc, id`, with `before` cursor.
  - `POST /v1/conversations/{id}/messages`, `POST /v1/conversations/{id}/read`, `POST /v1/conversations/{id}/archive` (and unarchive), plus a new `DELETE /v1/conversations/{id}/messages/{messageId}`.
  - A non-participant gets 404, never 403 (no existence leak).
  - An abuse report endpoint is required by SECURITY, but the `Report` model is 1A.11. For now there's a `POST /v1/conversations/{id}/report` that writes `AuditLog` plus a structured log line. 1A.11 migrates it to `Report`.
- **Realtime.**
  - Socket.IO on the API process at path `/v1/socket.io`, so the preview's Traefik `/v1` route covers it with no infra change beyond WebSocket upgrade, which Traefik passes by default.
  - `@socket.io/redis-adapter` on the existing Redis, so multiple API instances work.
  - Handshake auth: session cookie (web) or `auth.token` bearer (mobile), validated through Better Auth exactly like HTTP. The Origin check uses the same allow-list as `OriginGuard`. It's rejected before `connection`.
  - Each socket auto-joins `user:{userId}`. `conversation:join` checks membership in the DB and caches it in Redis for 60 s; the cache is invalidated on archive and participant changes.
  - Events follow `packages/shared/src/contract/socket.ts`:
    - `message:send` goes through the same service as REST, one code path;
    - `message:new` is emitted to the conversation room and each participant's user room;
    - `typing` is relayed only, never stored, and throttled to 1 per 2 s per socket;
    - `read` updates `lastReadAt` and emits;
    - `conversation:updated`.
  - Every client payload is zod-validated; an invalid payload gets an error ack, not a disconnect loop.
- **Limits.**
  - Messages: 30 a minute and 500 a day per user (`RedisRateLimiter`, shared by REST and socket).
  - Socket connections: 10 per user.
  - Payload max 16 KB (Socket.IO `maxHttpBufferSize`).
  - Report: 5 an hour.
- **Notifications.**
  - New type `message_received` (1A.7 infrastructure, preferences apply).
  - Push is sent only when the recipient has no connected socket, checked through the Redis adapter's `fetchSockets` on `user:{id}`, collapsed to at most one per conversation per recipient per 10 minutes (Redis key).
  - Email isn't sent per message in the MVP. A digest is a Phase 3 increment, recorded in `docs/PLAN.md`.
  - The payload holds the conversation id and sender display name only, never the message body (privacy: push goes through Expo and Apple/Google).
- **AuditLog.** Chat isn't money, verification, moderation or roles, so there's no audit row per message. Report and admin reads (1A.11) write `AuditLog`.
- **Retention.** Messages follow the account deletion and anonymisation rules of 1A.12. A note is added to `docs/COMPLIANCE.md` retention: conversations are kept 3 years after the last message for dispute handling (proposal, flagged for the 0.7 lawyer brief).
- **Not in scope.** Contact detail filtering (phone and email masking against fee circumvention) is a Phase 3 moderation increment, filed as an issue. Also out: message search and edits.

## 1A.6a tasks (schema-migrator)

1. DATA-MODEL:
   - `Conversation(type, subjectId, lastMessageAt, createdAt)`, unique `(type, subjectId)`;
   - `ConversationParticipant` as above, index `(userId, archivedAt)`;
   - `Message(conversationId, senderId, body, createdAt, deletedAt)`, index `(conversationId, createdAt desc, id)`;
   - `MessageAttachment(messageId, uploadId)`, unique `uploadId`, because an upload attaches once.
2. Schema and migration via `migrate diff`, applied to photoo and photoo_test.
3. Seed: a conversation for the seeded quote with two messages, idempotent.
4. Tests:
   - unique `(type, subjectId)`;
   - a participant pair is unique;
   - an upload can't be attached twice;
   - cascade rules: deleting a conversation removes participants and messages, while uploads are `Restrict`.

## 1A.6b tasks (api-developer)

1. Contract gaps in `chat.ts` and `socket.ts`:
   - delete, report and unarchive routes;
   - `unreadCount` and preview on the conversation;
   - error responses;
   - the `message_received` type in the notifications enum and payload;
   - regenerate openapi and api-client.
2. `ChatModule`: service (one path for REST and socket), controller, gateway (`@nestjs/websockets` + `@nestjs/platform-socket.io`, versions pinned per `minimumReleaseAge`), Redis adapter setup in `main.ts`, handshake auth and origin, and membership cache.
3. Quote creation creates the conversation in the same transaction (`QuotesService`).
4. Worker: none new. Notifications go through the existing `NotificationsService` with the offline check done in the API before `notify`.
5. Tests (integration against the stack, using `socket.io-client` in tests):
   - handshake rejects missing, invalid or foreign-origin sessions and accepts cookie and bearer;
   - a non-participant can't join, read, send or report (404);
   - a message over REST arrives on the socket and vice versa;
   - an unclean attachment gives 422, and someone else's upload gives 422;
   - unread count and read;
   - archive hides the conversation and a new message unarchives it for the recipient;
   - delete window;
   - rate limits give 429 and an error ack;
   - push only when offline and collapsed;
   - the typing throttle.
   - Coverage thresholds hold.
6. Preview: confirm WebSocket upgrade through Traefik on `footoo.bas.lu/v1/socket.io` after deploy (devops-engineer, smoke test in the runbook).
7. Security checkpoint (security-reviewer) before merge: handshake, membership, attachment access, rate limits and log redaction of message bodies.
