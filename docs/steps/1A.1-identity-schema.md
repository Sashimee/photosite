# Step 1A.1 – Identity, audit and notification schema

Plan reference: `docs/PLAN.md` step 1A.1. Owner: schema-migrator. Branch: `feat/1A.1-identity-schema`.

## Goal

Prisma models for `User`, `Account`, `Session`, `Verification` (auth tokens), `Device`, `ConsentRecord`, `AuditLog`, `Notification`, with migrations, enums mirrored from `packages/shared`, and seed users for every role.

## Auth library decision (D20)

`DATA-MODEL.md` says `Account` and `Session` are shaped by the auth library, which PLAN scheduled for 1A.2. Decided now to avoid migrating twice: Better Auth 1.7.5 (see `docs/DECISIONS.md` D20). Its core tables are `user`, `session`, `account`, `verification`, plus `twoFactor` from the two-factor plugin. Derive the exact required fields from the installed `better-auth` / `@better-auth/core` package (its schema for those models and plugin), map them onto our Prisma models with Better Auth's `modelName`/`fields` options in mind (e.g. its `emailVerified` boolean and `name`/`image` fields), and write the mapping into this file under "Field mapping" so 1A.2 configures the library to match. `session.token` stores a SHA-256 hash (wrapper lands in 1A.2); name the column `tokenHash` and map it.

## Tasks

1. `User`: uuid v7 id, `email` citext unique (migration enables the `citext` extension), `emailVerifiedAt`, `passwordHash` nullable, `locale` (enum `Locale`), `countryCode` FK to `Country`, `roles` as a Postgres enum array `UserRole[]`, `status` enum, `twoFactorEnabled`, `twoFactorSecret` encrypted-at-rest column note (encryption happens in 1A.2), `lastLoginAt`, `deletedAt`, timestamps. Index on `status`, partial index on `deletedAt IS NULL` via hand-written SQL.
2. `Account`, `Session` (`tokenHash` unique, `userId`, `userAgent`, `ip`, `expiresAt`, index on `userId` and `expiresAt`), `Verification` and `TwoFactor` per the library mapping. Do not add `better-auth` as a dependency of `packages/db`; inspect it from a temporary install outside the repo.
3. `Device`: `userId`, `expoPushToken` unique, `platform` enum (`ios`, `android`, `web`), `lastSeenAt`.
4. `ConsentRecord` append-only (no `updatedAt`): `userId` nullable, `anonymousId` nullable, check constraint exactly one set (hand-written SQL), `purpose` enum, `granted`, `policyVersion`, `ip`, `userAgent`, `recordedAt`.
5. `AuditLog` append-only: `actorType` enum (`user`, `admin`, `system`), `actorId` nullable, `action`, `targetType`, `targetId`, `before`/`after` JSON, `ip`, `occurredAt`; indexes on (`targetType`, `targetId`), `actorId`, `occurredAt`. Database trigger or revoked UPDATE/DELETE is out of scope; note it for 1A.14.
6. `Notification`: `userId`, `type`, `payload` JSON, `channels` enum array (`email`, `push`, `in_app`), `readAt`; index (`userId`, `readAt`).
7. `PlatformSetting.updatedByAdminId` becomes a relation to `User`.
8. Enums in `packages/shared/src/enums.ts` added or reused; a test asserts Prisma enum values equal the shared arrays.
9. Migrations via `prisma migrate diff` + `prisma migrate deploy` (local DB drift, see `docs/steps/human-followups.md`); review SQL.
10. Seed (idempotent): one user per role (`client@photoo.test`, `photographer@photoo.test`, `professional@photoo.test`, `admin@photoo.test`) with a dev-only password hashed with Argon2id, admin with `twoFactorEnabled=false` and a note that local admin login needs TOTP enrolment in 1A.2. Seed refuses to run when `NODE_ENV=production`.
11. Integration tests on `TEST_DATABASE_URL`: citext uniqueness (case-insensitive duplicate rejected), consent check constraint, seed idempotency, enum parity.

## Field mapping

Derived from `better-auth@1.7.5` / `@better-auth/core@1.7.5` (`getAuthTables` in
`@better-auth/core/dist/db/get-tables.mjs`) and the `two-factor` plugin's
`dist/plugins/two-factor/schema.mjs`, inspected under a temporary install outside
this repo. Field types below are better-auth's internal types (`string`, `boolean`,
`date`, `number`), which map onto Prisma `String`, `Boolean`, `DateTime`, `Int`.

### `user` → `User`

| better-auth field | type / required | our column | note |
|---|---|---|---|
| `id` | string, required | `id` | our `uuid(7)` default satisfies "string id"; 1A.2 sets `advanced.database.generateId` to defer to Prisma's default instead of better-auth's own id generator |
| `email` | string, required, unique | `email` (citext) | better-auth lowercases on write; citext makes DB-level comparison case-insensitive too, so both layers agree |
| `emailVerified` | boolean, required, default false | *(none)* | we keep `emailVerifiedAt: DateTime?` instead (richer: also records *when*). 1A.2 must bridge these: either a `user.fields.emailVerified` pointing at a new boolean shadow column, or a `databaseHooks` conversion so writes to the boolean flip `emailVerifiedAt` |
| `name` | string, **required** | `name` | **Resolved (1A.2b task 1)**: migration `auth_user_name` adds `User.name String?`. Better-auth's schema hardcodes `required: true` on its side; the column is nullable on ours because pre-existing rows (e.g. seed users created before this migration) start without one — the application layer (seed, sign-up) always supplies a value, defaulted from the email local part, so better-auth never actually receives `null`. DATA-MODEL.md's User entity updated to match |
| `image` | string, optional | *(none)* | no equivalent column; avatars live on `PhotographerProfile.avatarKey` today. Leave unset (`null`) unless 1A.2 decides otherwise |
| `createdAt` / `updatedAt` | date, required | `createdAt` / `updatedAt` | direct |
| `twoFactorEnabled` (two-factor plugin) | boolean, default false | `twoFactorEnabled` | direct |

Not part of better-auth's schema, kept because DATA-MODEL.md and this subplan's
task 1 require them: `locale`, `countryCode`, `roles`, `status`, `lastLoginAt`,
`deletedAt`.

**Deviation (resolved):** task 1 also asked for a `passwordHash` column on
`User`. Better Auth verifies email+password logins against the credential
`Account` row (`providerId = 'credential'`, `accountId = user.id`), not
against `User`, so `User.passwordHash` would have been dead weight the
library never reads — the seed users as first written couldn't have signed
in once 1A.2 wired the library. Migration `user_password_to_account` drops
`User.passwordHash`; the Argon2id hash lives only on `Account.password`
(see below). DATA-MODEL.md's User entity has been updated to match.

**Deviation:** task 1 also asks for a `twoFactorSecret` column "encrypted-at-rest"
on `User`. The two-factor plugin already stores the TOTP secret on its own
`twoFactor.secret` field (see below), so a second copy on `User` would be a
second source of truth for a security-sensitive value. This migration does
**not** add `User.twoFactorSecret`; 1A.2 should encrypt `TwoFactor.secret` at
rest instead. Flagging for confirmation rather than guessing further.

### `account` → `Account`

| better-auth field | type / required | our column |
|---|---|---|
| `id`, `createdAt`, `updatedAt` | — | same |
| `userId` (references `user.id`, cascade, indexed) | string, required | `userId` (FK, cascade, indexed) |
| `providerId` | string, required | `providerId` |
| `accountId` | string, required | `accountId` |
| `accessToken` / `refreshToken` / `idToken` | string, optional | same |
| `accessTokenExpiresAt` / `refreshTokenExpiresAt` | date, optional | same |
| `scope` | string, optional | `scope` |
| `password` | string, optional | `password` — the sole store for the Argon2id hash of the `credential` provider row (`providerId = 'credential'`, `accountId = user.id`); `User.passwordHash` was removed by `user_password_to_account` so there is exactly one place a password hash can live |

**Hardening beyond the library:** added `@@unique([providerId, accountId])`.
Better-auth's own schema doesn't declare this constraint (it relies on
application-level lookups), but it is the standard invariant for OAuth account
linking and costs nothing to enforce at the database level.

### `session` → `Session`

| better-auth field | type / required | our column | note |
|---|---|---|---|
| `token` | string, required, unique | `tokenHash` | renamed per this subplan; the 1A.2 adapter wrapper SHA-256-hashes it on write and lookup (D20, SECURITY.md) |
| `userId` (references `user.id`, cascade, indexed) | string, required | `userId` (FK, cascade, indexed) |
| `expiresAt` | date, required | `expiresAt` (indexed) |
| `ipAddress` | string, optional | `ip` | renamed to match this subplan's task 2 wording; 1A.2 sets `session.fields.ipAddress = "ip"` |
| `userAgent` | string, optional | `userAgent` | direct |
| `createdAt` / `updatedAt` | date, required | same |

### `verification` → `Verification`

| better-auth field | type / required | our column | note |
|---|---|---|---|
| `identifier` | string, required, indexed | `identifier` (indexed) | direct |
| `value` | string, required | `value` | **Compliance gap, not fixed here**: SECURITY.md requires verification tokens "hashed at rest", but better-auth stores `value` as the raw token and this subplan only asked for the `session.token` → `tokenHash` rename, not an equivalent for `verification.value`. 1A.2 should apply the same hash-on-write/lookup wrapper to `Verification.value` that it applies to `Session.token` |
| `expiresAt`, `createdAt`, `updatedAt` | date, required | same |

### `twoFactor` → `TwoFactor` (two-factor plugin)

| better-auth field | type / required | our column | note |
|---|---|---|---|
| `userId` (references `user.id`, indexed) | string, required | `userId` (FK, cascade, indexed) | plugin doesn't specify `onDelete`; we use cascade for consistency with `Account`/`Session` |
| `secret` | string, required, indexed | `secret` | we do **not** mirror the plugin's `index: true` on this column — no query needs to look up a row by secret value, and indexing sensitive material with no functional need is avoided |
| `backupCodes` | string, required | `backupCodes` | direct |
| `verified` | boolean, default true | `verified` | direct |
| `failedVerificationCount` | number, default 0 | `failedVerificationCount` (`Int`) | direct |
| `lockedUntil` | date, optional | `lockedUntil` | direct |

### Not part of better-auth's schema

`Device`, `ConsentRecord`, `AuditLog`, `Notification` are our own tables (DATA-MODEL.md
"Identity and roles" / "Platform"); better-auth has no equivalent and nothing to map.
