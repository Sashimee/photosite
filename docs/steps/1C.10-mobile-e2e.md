## What exists

- **No Maestro, Android SDK or emulator** on the dev host. Flows are written here but run in CI only, and `apps/mobile/e2e/README` documents how to run them locally.
- **The app reads its env at build time.** `apps/mobile/src/lib/env.ts` validates `EXPO_PUBLIC_API_URL` (required) and the optional Stripe and Sentry values. `eas.json` has `development`, `preview` and `production` profiles. EAS builds need an Expo account (1C.9d gate), so the e2e build must not go through EAS.
- **Web e2e (1B.12)** already settled the fixture philosophy, in its Decisions section: sign up fresh where no human-gated state is needed, and reuse one seeded identity where it is (`sofia.martins@photoo.test`, the verified, published photographer). Seed data used by api integration tests must not be mutated. Mailpit polling exists in `apps/web/e2e/fixtures/users.ts` and `apps/api/src/testing/mailpit.ts`.
- **CI's `e2e` job** (`.github/workflows/ci.yml`) already boots the stack, migrates, seeds, and starts the api and worker with `STRIPE_FAKE: 'true'`. The mobile job copies that block.
- `testID`s already exist on several screens (`requests/new.tsx`, `quotes/[id].tsx`, `bookings/[id].tsx`, `consent.tsx`, `studio/*`).

## Decisions

- **Android only in CI.** It runs on an `ubuntu-latest` runner with KVM and `reactivecircus/android-emulator-runner`. iOS needs macOS runners (10x the minutes) and adds no coverage of app logic. iOS gets checked on a device (human-followups, 1C.4/1C.5 device sitting).
- **Build locally in CI, not with EAS.** The job runs `expo prebuild --platform android --clean`, then `./gradlew assembleRelease`, with the JS bundled into the APK so no Metro server is needed.
  - The emulator reaches the host API at `EXPO_PUBLIC_API_URL=http://10.0.2.2:4000`.
  - Cleartext HTTP is allowed only when an `E2E_BUILD=1` env flag is read in `app.config.ts`. No EAS profile sets that flag, so store builds stay HTTPS-only.
  - The release build is signed with the debug keystore.
- **Not a required check, and not on every PR.** The job runs on pushes to `dev`, on `workflow_dispatch`, and on PRs that touch `apps/mobile/**` or the workflow itself. It does not block merges during burn-in, the same as the web `e2e` job.
  - Budget: 30 minutes for the job. Cache Gradle and the AVD snapshot.
  - Maestro's screenshots and logs upload as an artifact when the job fails.
- **Fixtures run through Maestro `runScript` (GraalJS `http`).** Small scripts in `apps/mobile/e2e/scripts/` create a user through the API, fetch the verification link from Mailpit (`http://10.0.2.2:8025`), and create quotes and chat messages as the seeded photographer. The flows pass values to each other through `output`. No production code is added for tests.
- **English only, consent pre-answered.** A flow taps through the consent prompt once in `launch.yaml` and the others start after it, so locale coverage stays with `packages/i18n`'s checks.
- **Selectors use `testID`s, not copy.** 1C.10a–d add missing `testID`s as their only change to app code.

## 1C.10e payment gate

PaymentSheet is native Stripe UI and needs a real test-mode PaymentIntent. CI's API runs `STRIPE_FAKE`, which creates no PaymentIntent the SDK can present. 1C.10e needs Stripe test keys as CI secrets: `STRIPE_SECRET_KEY` (test), `STRIPE_WEBHOOK_SECRET`, `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY` (test), and a way to deliver webhooks to the CI API (`stripe listen`, which needs the key). The step is recorded in `docs/steps/human-followups.md` and waits on the same Stripe test account as the preview release.
