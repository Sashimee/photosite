## What the API gives us

Reading the contract rather than the plan's one-line summary:

- **Public, anonymous:** `GET /v1/job-offers` (keyset by `publishedAt desc, id`; filters `category`, `countryCode`, `city`, `remote`, `q`) and `GET /v1/job-offers/{slug}`. Both already filter out `deletedAt`, unpublished and expired rows server-side — the web app does not need to re-check any of that.
- **Public payload (`PublicJobOfferSummary`/`PublicJobOffer`):** `company` is `{ id, companyName, website, logoUrl, verified }` — note **`website` is in the public shape**, not just name/logo/badge as the plan brief assumed. Never `email`, `phone` or `vatNumber`. `location` is `LatLng | null` (coarsened to `LOCATION_GRID_DEGREES`, ~1 km), null whenever the professional didn't set one, which the schema only allows when `remote: true`.
- **Owned (`/me/professional-profile`, `/me/job-offers*`):** full CRUD plus `publish`/`close`, `OwnProfessionalProfile` adds `vatNumber` on top of the public shape, `JobOffer` (owner view) carries exact `location`, `status`, `publishedAt`, `expiresAt`.
- **Applications:** `POST /job-offers/{id}/applications` (photographer, `message` + optional `portfolioLink`), `GET /job-offers/{id}/applications` (professional, paginated, includes `photographer: { id, slug, displayName, avatarUrl, city, countryCode }`), `GET /me/job-applications` (photographer's own, includes `jobOffer: { id, slug, title, status }`), `POST /job-applications/{id}/status` (`shortlisted | rejected` by the professional, `withdrawn` by the photographer; `submitted` is not a valid target — it's the creation default only).
- **No employment type, no salary requirement.** `JobOffer` has no full-time/freelance/contract field at all, and `compensation` is optional. Neither is a gap to fix here — `docs/steps/human-followups.md` already tracks whether compensation should become mandatory (pay-transparency law).
- **No notification on takedown or on offers with received applications beyond the two 1A.13 types** (`job_application_received`, `job_application_status_changed`). There is no `job_offer_expired` notification either — already tracked as a follow-up in `docs/steps/human-followups.md` ("Job board (1A.13)").

## Decisions for this step

- **Having the `professional` role is not the same as having a profile, and the UI must not conflate them.** `professional` is in `SIGNUP_ROLES`, so `POST /v1/auth/roles` (the existing `RolesPanel` in `/account`) lets an account acquire the role with **no profile behind it** — `GET /v1/me/professional-profile` then 404s. `POST /me/professional-profile` is written to be idempotent about the role (it only adds it "when the account doesn't already carry it"), so the fix is cheap: the professional area's entry point checks for the *profile*, not the role, and always routes a missing profile to the same create form regardless of how the account got the role. This mirrors the "no profile vs no results" defect the 1B.8d review already flagged for empty states — same trap, one level up.
- **The professional area lives under `/{locale}/account/`, not a `/dashboard`-style top-level section.** The task brief fixes the applications inbox at `/{locale}/account/job-offers/{id}/applications` specifically so it never collides with the public `[slug]` segment at `/job-offers/{slug}`; the rest of the owner-facing tree follows the same prefix for one consistent rule instead of a special case for one page:
  - `/{locale}/account/professional-profile` — create/edit the company profile.
  - `/{locale}/account/job-offers` — list of the professional's own offers (draft/published/closed/expired, `GET /me/job-offers`).
  - `/{locale}/account/job-offers/new` and `/{locale}/account/job-offers/{id}/edit` — create and edit.
  - `/{locale}/account/job-offers/{id}/applications` — the inbox (fixed by the brief).
  - This is a deliberate split from `/dashboard` (photographer): the photographer side is a multi-page app with its own nav shell built in 1B.8, and a company posting one or two offers doesn't need a second nav shell — it hangs off the existing `/account` hub the same way roles and sessions do, as a handful of linked pages rather than a `DashboardLayout` clone. If a professional's needs grow (Phase 2+), promoting `/account/job-offers` to a real `/dashboard`-equivalent is a route move, not a rewrite of any form or API call.
  - All of `/account/*` is already `noindex`, dynamic, sign-in gated — nothing new to add there.
- **The public job board is a new route tree, `/{locale}/job-offers` and `/{locale}/job-offers/{slug}`, not folded into `/{locale}/photographers`.** 1B.4's discovery pages are keyed to `PhotographerProfile` search; a job offer is a different entity with a different filter set (`category`, `countryCode`, `city`, `remote`, `q` — no language, no price-from, no rating) and a different result shape (`PublicJobOfferSummary`, not `PhotographerSummary`). Forcing one route tree to serve both would mean branching the filter form, the card component and the JSON-LD builder on entity type for no shared benefit. What *is* reused, deliberately, because it is generic: `city-autocomplete.tsx` (same `/v1/cities` endpoint), the cursor "load more" pattern from `lib/search-params.ts`, and the noindex-when-filtered / noindex-when-empty rules from `lib/robots.ts`. No landing-page combinatorics (`/job-offers/{country}/{city}/{category}`) are built — the plan only asks for board + detail pages, and country/city/category landing pages for job offers are not in `docs/PLAN.md` 1B.9's scope; if wanted later, that is a new step, not a silent addition here.
- **The public offer page shows company name, logo, the `verified` badge and, when set, the company website — nothing else.** No email, phone or VAT number exist in the public payload to accidentally leak. The page states plainly that applying is the only way to contact the poster; there is no "message the company" link, because none exists in the API — chat is never opened by a job application.
- **Applying happens inline on the public offer page, behind sign-in, not a dedicated route.** A photographer reads the offer and applies in one place; splitting it into `/job-offers/{slug}/apply` would need the offer refetched or passed through a query string for no benefit, since the form is two fields (`message`, optional `portfolioLink`). Signed-out visitors see the form with fields disabled and a sign-in link carrying `next` back to the offer, the same redirect-with-`next` pattern as 1B.5's request form. A second application attempt reuses the 409 → "you already applied, see it in My applications" mapping rather than re-showing the form.
  - `portfolioLink` is validated client-side with the same `https`-only rule as `PortfolioLinkSchema` before submit (server remains authority), and it is rendered everywhere the professional sees it — the applications inbox — as `<a rel="nofollow noopener" ...>`, per the 1A.13 decision that this is a web-app responsibility, not something the API enforces on render.
- **`EMAIL_NOT_VERIFIED` gets a real prompt, not a dead-end error, and 1B.9 builds it — closing the web half of #290 for this step's two call sites.** Tracing where the guard can actually fire here: `POST /me/professional-profile` requires a verified email, and since it is also what grants the `professional` role, **a professional cannot reach draft-offer creation at all without already being verified** — draft create/update/close/delete do not call `requireVerifiedEmail`, so that exemption is moot in practice once a profile exists, but `publish` still checks it defensively and so does 1B.9b's publish action. The one path that is genuinely reachable by an unverified, already-signed-in account is a photographer applying (`POST /job-offers/{id}/applications`) — OAuth sign-up can leave `emailVerifiedAt` null indefinitely (see #290's own analysis). So: a small `EmailVerificationRequired` component (message plus a button calling `POST /v1/auth/verify-email/resend` with the session's own `email`, rate-limited server-side, success state "check your inbox") is built once and used at both call sites — the create-profile form and the apply form. It reads `user.emailVerifiedAt` from the session up front to disable the action pre-emptively where the session is already known server-side (no need to wait for the 403 on the professional-profile page, since that page already has the session), and falls back to catching the 403 where the session is read client-side. This is 1B.9's contribution to #290, not the whole issue — the mobile prompt stays open there, and any already-shipped web flow that hits the same guard (1B.5's request form, 1B.8d's send-quote) is a one-line note in Human follow-ups below, not fixed in this branch.
- **A taken-down offer disappears from the owner's own list and detail (`deletedAt` is filtered in `getOwnById` and `listOwn`, not just the public reads), and there is currently no notice.** This was checked directly in `job-board.repository.ts` and `job-board-rate-limit.service.ts`: moderator takedown and the professional's own `DELETE` are indistinguishable to the professional today — both just make the row vanish. `docs/steps/1D.6-moderation.md` already names this exact gap generally ("No decision notice", #191) as its own deliverable; 1B.9 does not build a workaround. The applications list and job-offer list treat a vanished id exactly like "never existed" (404 on direct navigation, simply absent from the list), and this is stated in the UI copy as "not found" rather than implying a bug.
- **A closed, expired or (once #191 lands) taken-down offer's applications inbox stays reachable read-only.** `GET /job-offers/{id}/applications` has no status precondition in the contract, and a professional who closed an offer still needs to review who applied and reject/shortlist them — the inbox route works for any owned offer regardless of `status`, only the "apply" action on the *public* page is gated to `published`.
- **Remote offers with no location get a `remote`-specific card and detail treatment, never a blank map or a "0 km away" line.** `location` is `null` exactly when `remote: true` is possible per the refined create schema; the UI never assumes one is present. No map is built in this step (1B.4 deferred maps entirely as an open decision, `docs/DECISIONS.md`), so this is about text and iconography only: a city/country line for non-remote offers, a "Remote" badge for remote ones, and both together when a remote offer still names a city.
- **Money.** Compensation is entered by the professional as whole currency units and converted to cents client-side before submit, same rule as 1B.5/1B.8's products; currency is locked to the offer's `countryCode` (`Country.currency`), never a free picker, and every displayed amount — on the owner's edit form re-render and on the public page — comes back from the API through `lib/money.ts`, never recomputed. `compensation` stays optional; the create form does not force it.
- **Rate limits (429) show a countback, not a retry-after header check.** The job board's limiter returns `{ code: 'TOO_MANY_REQUESTS', details: { retryAfterSeconds } }` in the body — there is no `Retry-After` HTTP header to read (confirmed in `job-board-rate-limit.service.ts`). A small `jobBoardErrorMessage` helper mirrors the existing `authErrorMessage` shape (same `retryAfterSeconds` extraction, same "try again in N seconds" copy) rather than importing `lib/auth-errors.ts`'s private helper, since that module is scoped to `web.auth` translations and this one needs `web.jobBoard`/`web.professional` namespaces.
- **SEO is metadata plus `JobPosting` JSON-LD, and 1B.9 owns both — 1B.11c only adds the sitemap entries.** Per `docs/steps/1B.11-seo.md`, `lib/site-url.ts` (`absoluteUrl`/`localeAlternates`) and `lib/robots.ts` already exist and are reused directly, matching the profile and landing pages' pattern. `JobPosting` fields are filled honestly against what the contract actually returns:
  - `title`, `description`, `datePosted` (`publishedAt`), `validThrough` (`expiresAt`), `hiringOrganization: { name, logo, sameAs: website }`, `directApply: true` (the apply flow is on this page, not an external link).
  - `jobLocation.address` uses `addressLocality: city`, `addressCountry: countryCode` only — **no `geo` (`GeoCoordinates`) property is emitted**, even though the API does return a coarse lat/lng. A city-level address is honest about what we know; a `geo` point — even snapped to the ~1 km grid — reads to a JobPosting consumer as a precise pin, and Luxembourg is small enough that a 1 km grid cell is not meaningfully anonymous if it's presented as *the* coordinate rather than a search filter's fuzzing. Compliance's reasoning for one shared grid was about search/distance filtering, not about publishing a point as structured data.
  - `jobLocationType: 'TELECOMMUTE'` when `remote: true` and no location; both `jobLocation` and `jobLocationType` when a remote offer still names a city.
  - `baseSalary` is emitted only when `compensation` is present (`min`/`max`/`currency` → `QuantitativeValue`), never fabricated when it's null.
  - No `employmentType` — the field does not exist in the contract, and it's optional for Google's rich result, so it's simply omitted rather than guessed.
  - noindex/no-sitemap-entry rule: this step's pages are indexable (subject to `NEXT_PUBLIC_ALLOW_INDEXING`, matching every other public page), but **this step does not touch `app/sitemap.ts`** — that file, and the "must not list what robots disallows" invariant, belongs to `1B.11c` once this step's slugs exist to list.
  - Canonical + hreflang on the detail page via `localeAlternates('/job-offers/' + slug)`; the list page is `noindex` whenever any filter param is present or the result set is empty, mirroring 1B.4's landing-page rule (thin/filtered pages are not indexed).
- **`robots`.** `/job-offers` and `/job-offers/{slug}` behave like every other public page (`buildRobotsMetadata(allowIndexing)`); every `/account/*` page here reuses the existing `noindex`, dynamic default — nothing new to configure.
- **Distinct empty states, on purpose.** Three states that must not render the same thing:
  1. No `professional` role and no profile yet → `/account/professional-profile` shows the create form with explanatory copy ("post a job offer as a company"), not a 404 or a blank page.
  2. A profile exists but zero job offers → `/account/job-offers` shows "no offers yet, post your first one" plus the create CTA, not the same empty-list component the public board uses for zero search results.
  3. The public board with no results for the current filters → "no offers match, clear filters", never conflated with #1 or #2 — this is the exact defect class the 1B.8d review found ("no profile" and "no results" looking identical").
  Applications inbox gets its own fourth: zero applications on an existing, published offer ("no applications yet") is not an error and not the same copy as "this offer was not found".

## 1B.9a tasks

1. `/{locale}/account/professional-profile`: `professional-profile-form.tsx` (`companyName`, `website`, `vatNumber`, logo upload reusing the 1A.3/1B.8b presigned upload flow with `purpose: 'logo'`), calling `POST`/`PATCH /v1/me/professional-profile`. Handles all three profile states (no role, role-but-no-profile, has-profile) by checking the profile fetch result only.
2. `EmailVerificationRequired` component (`components/email-verification-required.tsx` or similar) wrapping the resend call, used here for the 403 on create and reused by 1B.9c.
3. `web.professional.*` i18n keys (`en` source of truth); i18n-maintainer drafts the rest.
4. Tests: profile-state routing (no role vs role-without-profile vs existing profile look identical to the user, both land on the same form); logo upload reuses the existing scanning/progress states; the resend component calls the right endpoint and shows a distinct success/rate-limited state; a second `POST` (already has a profile) maps 409 to "you already have a profile, edit it here".

## 1B.9b tasks

1. `/{locale}/account/job-offers` (list, `GET /me/job-offers`, cursor "load more", status badges for `draft | published | closed | expired`), `/new` and `/{id}/edit` (`job-offer-form.tsx`: title, description, category, city + country (reusing `city-autocomplete.tsx`), remote toggle that hides/requires location accordingly, start/end date, compensation range with cents conversion), publish and close actions with confirmation dialogs that state the consequence (publish: "visible on the public board for 60 days"; close: "no longer visible, existing applications stay").
2. Delete action (draft only in practice, but the API allows deleting any owned offer) with a confirmation naming that applications are removed with it (cascade).
3. Error mapping: 409 (already published / already closed), 422 (field errors, including the date-range and location-vs-remote refinements mirrored client-side), 429 via `jobBoardErrorMessage`.
4. Tests: remote toggle disables/clears location and re-enables the location picker when unchecked; compensation cents conversion and currency lock to `countryCode`; publish is disabled/hidden once already published; the list distinguishes empty-because-no-offers from empty-because-filtered (there is no filter here, but from "not started yet" — state #2 above).

## 1B.9c tasks

1. Public offer page apply form (built in 1B.9d's route, listed here because it's the same feature as the inbox): sign-in gate with `next`, `EmailVerificationRequired` reuse, 409 → "already applied, see My applications" with a link.
2. `/{locale}/account/job-offers/{id}/applications`: list (`GET /job-offers/{id}/applications`, cursor "load more"), each row linking the photographer's public profile (`/{locale}/photographers/{slug}`), the `portfolioLink` rendered as `rel="nofollow noopener"`, and shortlist/reject actions (`POST /job-applications/{id}/status`) with confirmation — rejecting is not reversible via a UI action (no "un-reject" status transition exists).
3. `/{locale}/account/job-applications` — "my applications" for the photographer role (`GET /me/job-applications`), status badge, withdraw action (confirmed) linking back to `/job-offers/{jobOffer.slug}`, and a distinct empty state ("you haven't applied to anything yet").
4. i18n under `web.jobApplications.*`.
5. Tests: apply form blocks a second submission client-side once 409 is seen once (still lets the server be the real authority); shortlist/reject require confirmation and disable once the application is no longer `submitted`; withdraw only shown for the applicant's own `submitted`/`shortlisted` rows; portfolio link always carries `rel="nofollow noopener"`.

## 1B.9d tasks

1. `/{locale}/job-offers`: `job-offer-filters.tsx` (`category`, `countryCode`, `city` via the shared autocomplete, `remote`, `q`), `job-offer-card.tsx` (title, company name + logo + verified badge, city/remote, compensation range if present, relative "posted N days ago" from `publishedAt`), cursor "load more", noindex-when-filtered-or-empty.
2. `/{locale}/job-offers/{slug}`: full detail, `buildJobPostingJsonLd()` (new, alongside `lib/profile-jsonld.ts`/`lib/landing-jsonld.ts`, same escaping/CSP-nonce treatment), metadata via `absoluteUrl`/`localeAlternates`, the apply form from 1B.9c, and the "not found" state for an expired/closed/deleted/never-existed slug — one 404, since the public endpoint already can't tell those apart and shouldn't.
3. Nav: a "Post a job" or "For businesses" entry point from the header linking to `/account/professional-profile`, and "Job board" linking to `/job-offers`, i18n under `web.nav.*` (existing namespace, new keys only).
4. i18n under `web.jobBoard.*`.
5. Tests: `buildJobPostingJsonLd` output shape and escaping (mirroring `profile-jsonld.test.ts`'s structure), including the remote/non-remote/compensation-present/absent branches; no `geo` property ever appears in the emitted JSON-LD; noindex rules (filtered, empty, and the normal indexable case); the expired/closed/deleted/unknown-slug cases all render the same not-found state.

## Human follow-ups

Added to `docs/steps/human-followups.md`:
- **Seed data is not enough to render every state without manual setup.** `seedProfessionalJobOffer` gives exactly one professional profile with exactly one *published* offer, and creates zero `JobApplication` rows and no photographer that has applied to it. Missing to exercise every state built here without clicking through the UI by hand: a draft offer, a closed offer, an expired offer (or one close to `expiresAt`), and at least one seeded application (ideally one `submitted` and one `shortlisted`/`rejected`) from an existing seeded photographer. Flagging for schema-migrator to extend in a follow-up, not building it here.
- **No `job_offer_expired` notification and no takedown notice exist yet** — already tracked in `docs/steps/human-followups.md` under "Job board (1A.13)" and `docs/steps/1D.6-moderation.md` (#191) respectively; 1B.9 builds against their absence (silent status change, silent disappearance) rather than duplicating the tracking here.
- **1B.5's request form and 1B.8d's send-quote flow predate the `EMAIL_NOT_VERIFIED` guard (#273)** and do not special-case that error code today (checked: their error mapping lists only 409/422/429). They are reachable by the same realistic unverified-OAuth-account path this step handles for job applications. Out of scope for 1B.9 to touch already-merged branches, but worth a follow-up ticket so the same `EmailVerificationRequired` component gets reused there instead of showing those users a generic error toast.
