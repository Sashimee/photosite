# Step 1C.5 – Mobile chat and push

Plan reference: `docs/PLAN.md` step 1C.5 — "Socket.IO client, conversation UI, image/PDF attachments from camera/gallery/files, Expo push registration, notification deep links". Owner: mobile-developer. Blocked by 1C.2 (merged), 1A.6 (merged) and 1A.7 (merged); `apps/mobile/app/(tabs)/messages.tsx` is still a `TabPlaceholderScreen`.

The web equivalent is `docs/steps/1B.6-chat-ui.md`, merged and shipped. As with 1C.4, **the chat decisions are ported, not redesigned**: optimistic send with deduplication by message id, plain-text bodies with no auto-linking, day grouping, "load older" via the `before` cursor, read receipts only when the thread is actually visible, typing throttled to once per 2 s, images and PDF only up to 10 per message, and a non-participant getting a 404. ## Where native differs from 1B.6

- **The socket authenticates with a bearer token, not a cookie.** The web relies on the session cookie and `withCredentials`; mobile holds its token in `expo-secure-store` and `apps/mobile/src/lib/api.ts` already attaches it per request. The socket handshake needs the same token supplied explicitly, and it must be re-read on reconnect rather than captured once — a token refreshed mid-session would otherwise reconnect with a stale credential forever.
- **A backgrounded app loses its socket, and that is normal.** iOS suspends sockets on background. The client disconnects on `AppState` leaving `active` and reconnects on return, refetching the first page and rejoining, exactly as the web does on reconnect. **Push, not the socket, is what delivers a message to a backgrounded app** — the socket is an optimisation for the foreground, never the delivery guarantee.
- **The unread badge is the API's number, not a local tally.** `GET /v1/conversations/unread-count` already exists. A locally incremented badge drifts the moment a notification is missed or a message is read on the web.

## Push: the decisions that matter

- **The push token is unregistered on sign-out, and this is a hard requirement.** `POST /v1/me/devices` registers an Expo token against the signed-in user; `DELETE /v1/me/devices/{id}` exists. If sign-out does not call it, the device keeps receiving **the previous user's** message notifications — including the sender's name and message preview — on a shared or resold handset. `apps/mobile/src/lib/auth-context.tsx:45` is the single sign-out path and is where this belongs. It must also run when the session is revoked remotely (the 401 listener at line 69), not only on a deliberate sign-out.
  - Unregistration is best-effort and must not block sign-out: if the call fails, the session is still cleared locally and the failure is surfaced, not swallowed. A sign-out that hangs because the network is down is worse than a stale device row, which the API can expire on its own.
- **Permission is requested when it means something, not at launch.** Asking for notifications on first open, before the user has a conversation, is how an app gets a permanent denial on iOS — the OS only shows the system prompt once. The prompt comes after the first message is sent or received, with a one-line explanation of what will be sent.
- **A denied permission is a supported state.** Chat works fully without push; the app does not nag, and the settings screen offers a way to enable it later via the OS settings deep link.
- **Notification content assumes a lock screen.** The payload carries the sender's display name and a preview, which is what a chat app is expected to do — but it must never carry an email address, a token, or an attachment URL. The server owns the payload (1A.7); this step's job is to verify what actually arrives and to file an issue rather than compensate client-side if it carries more than it should.
- **Deep links must work from a cold start.** A notification tap when the app is not running has to route to `/messages/{conversationId}` after the session is restored, not land on the tab root. `expo-linking` and `expo-router` are configured; the ordering against `RequireSession` is the part that actually breaks, so it gets an explicit test.
- **The web's deep link path is `/{locale}/messages/{id}`; mobile has no locale segment.** 1A.6b chose the web path, and the server may send one URL for both. Confirm what the notification payload actually contains before assuming the app can consume it — if the server sends a web URL, mapping it belongs in the app's linking config, and if it sends something else, that is a contract question to raise, not to paper over.

## Attachments (1C.5b)

- Camera, photo library and document picker mean **new dependencies** — `expo-image-picker` and `expo-document-picker` — added via `expo install` so versions match the SDK, and satisfying pnpm's `minimumReleaseAge`. **`minimumReleaseAgeExclude` in `pnpm-workspace.yaml` is not to be touched**; pin an older release if the newest is too recent.
- Each picker needs its own permission with the same rules as push: asked at the point of use, denial is a supported state with a path to OS settings.
- The upload flow is the existing presigned PUT from 1A.3 — create with purpose `chat_attachment`, PUT, complete, then send with the attachment ids. Per-file progress, and the 422 "still being scanned" case renders as a state rather than an error, matching how 1D.3 treats an unscanned document.
- **A photo taken in-app is full-resolution and often many megabytes.** It is resized before upload on the client; a chat attachment is not a portfolio original, and uploading 12 MP over a mobile connection is a failed send on a train.

## Tasks

1. `app/(tabs)/messages.tsx` (list) and `app/messages/[id].tsx` (thread), reusing the existing component set; `src/lib/chat-socket.ts` for the single connection.
2. The three permission flows, each asked at point of use.
3. Device registration on sign-in and **unregistration on both sign-out paths**.
4. i18n under `mobile.chat.*` and `mobile.notifications.*`, English only, replacing the placeholder key.
5. Tests (jest-expo):
   - sign-out calls `DELETE /v1/me/devices/{id}`, **and still clears the session when that call fails**;
   - a remote session revocation unregisters too;
   - the socket reconnects with a freshly-read token, not a captured one;
   - backgrounding disconnects and returning refetches;
   - a cold-start notification tap lands on the right conversation after session restore;
   - a denied push permission leaves chat fully usable;
   - optimistic send deduplicates against the echoed `message:new`;
   - an oversized photo is resized before upload;
   - one test renders against the real `en` catalog.
   Keep an eye on runtime: the existing `apps/mobile/app/(auth)` suites have already timed out once on a loaded CI runner at jest's 30s limit.
6. Manual check on the local stack: two accounts, a real exchange, attachment from each source, and a foreground/background/cold-start notification.

## Human follow-ups

- **An Expo account is required before push can be tested end to end**, already tracked in this file for 1C.1 (`EAS_PROJECT_ID`, optional `EXPO_ACCESS_TOKEN`). 1C.5a and 1C.5b are fully implementable and testable without it; **1C.5c can be written but not verified**, so it should not be called done on CI alone.
- **Push on a physical device** — the simulator does not deliver real APNs notifications. This is the same real-device check 1C.4 already raised, and the two should be done in one sitting.
- **What the notification preview shows on a lock screen** is a product and privacy call: sender name plus message preview is the convention, but it means a message is readable without unlocking. If that is not wanted, the server payload changes (1A.7), not the app.
