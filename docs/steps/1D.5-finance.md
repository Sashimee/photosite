## What the API gives us (1D.5a)

All on the `finance` permission:

- `GET /v1/admin/bookings` — keyset, no filters yet. `GET /v1/admin/bookings/{id}`. `AdminBooking` = booking base (total as `{amountCents, currency}`, status, release/delivery/cancel timestamps) plus `paymentIntentId`, `chargeId`, `transferId`, `refundedCents`, `reversedCents` (ledger sums, ≥ 0) and the latest `disputeStatus`.
- `POST /v1/admin/bookings/{id}/refund` `{ amountCents, reason }` — **fresh 2FA**, released bookings only (409 otherwise), reverses the transfer first then refunds; 422 before any Stripe call if the amount exceeds what is refundable or left on the transfer; 429 on the admin mutation limit.
- `POST /v1/admin/bookings/{id}/reverse-transfer` `{ reason }` — **fresh 2FA**, released (or disputed after release) only; reverses whatever is left without refunding the client; 422 when nothing is left; booking keeps its status.

## Decisions for this step

- **The UI never computes money it then sends.** The refund amount is what the admin types (in major units, converted to integer cents with the shared money helper); the "refundable" hint is `total − refundedCents` from the API and is only a hint — the API is authoritative (422). No fee maths in the admin app.
- **Amount input is in the booking's currency, entered as a decimal and converted exactly** (no float multiply: parse the string into cents). A value with more than the currency's minor-unit digits is rejected client-side.
- **Both actions are confirm dialogs naming the booking, the amount and the currency**, with a required reason labelled as internal (it goes to the audit log, not to the client or photographer).
- **Refund and reverse buttons are shown only in the states the API accepts** (refund: `released`; reverse: `released`, or `disputed` with a `transferId`), and a 409 still maps to a clear message because the state can change while the page is open.
- **Fresh 2FA**: `TWO_FACTOR_REQUIRED` already redirects through `lib/api.ts` to the reverify sign-in and returns to the page. The dialog says before submit that the action asks for the second factor again, and a draft amount/reason is not kept across the redirect (re-entering a refund amount on purpose is acceptable friction).
- **Double submit**: the submit button disables while in flight; no client retry on a network error — the admin reloads and sees the ledger sums before trying again, because a retried refund is real money.
- **Stripe ids are shown as text** (copyable), not links to the Stripe dashboard: the dashboard account is not decided (O2), and test/live mode would make the link wrong half the time.
- **No client PII beyond ids.** The booking schema has client/photographer ids only; this step does not add names. If reviewers need names, that is an API change for 1D.5b.
- **Nav**: the existing `finance` entry (currently "available after 1A.8") becomes available and points at `/finance`.

## 1D.5b – ledger, disputes, filters (issue #551)

Owner: payments-engineer (API: anything reading the ledger, disputes or Stripe), then web-developer (admin UI), test-writer, code-reviewer + payments-engineer review + security-reviewer.

### API (payments-engineer)

- **List filters on `GET /v1/admin/bookings`**: `status` (repeatable, `BookingStatus`), `createdFrom`/`createdTo` (ISO dates, half-open `[from, to)`, `to > from`, max span 366 days), `dispute` (`any` | `open` | `none`). Keyset paging stays correct under filters (the cursor encodes the same sort key; a cursor from a different filter set is rejected with 400).
- **Detail adds** `ledger: LedgerEntry[]` (type, signed `amountCents`, currency, `stripeObjectId`, `occurredAt`, oldest first, capped at 200 with a `ledgerTruncated` flag) and `disputes: Dispute[]` (status, reason, resolution, `amountRefundedCents`, opened/updated timestamps; `openedById`/`adminId` as ids only, no names or emails).
- **Payout status on the detail**: the photographer's Connect account state as the API already knows it (account id present, onboarding complete / payouts enabled, as stored or as the gateway reports — payments-engineer picks the existing source; never a live Stripe call per list row) plus the booking's own `payout` ledger entries. If the data does not exist, `payout: null`, never a guess.
- **Server-computed money hints**: `refundableCents = max(0, min(total − refunded, transferred − reversed))` for released bookings (0 otherwise) and `reversibleCents = max(0, transferred − reversed)`. The UI shows these; it never computes them (no fee maths in the admin app).
- **Concurrency guard on both POSTs**: optional `expectedRefundedCents` / `expectedReversedCents`; when present and the ledger has moved, 409 with code `LEDGER_CHANGED` before any Stripe call. The admin UI always sends them from the page it rendered.
- **Audit**: the `booking.refund_reversal` audit row carries the admin's reason (`booking-refund.service.ts:331`).
- **Docs**: `docs/PAYMENTS.md` §5 describes the actual admin flow (refund after release = reverse then refund in one call, capped at what is left on the transfer; standalone reversal is chargeback recovery).
- Contract first in `packages/shared`, regenerate `openapi.json` and the api-client.

### Admin UI (web-developer)

- Filters on `/finance` as search params (status multi-select, created date range, dispute), validated with the contract schema; invalid params fall back to no filter and are not sent.
- Detail: ledger table (signed amounts via `formatCents`, type labels, Stripe ids as copyable text), disputes table, payout status block (or "not available"), refundable/reversible from the API in the money summary.
- Refund and reverse dialogs send `expectedRefundedCents` / `expectedReversedCents` from the rendered booking; `LEDGER_CHANGED` shows "the booking changed since you opened it; reload" and does not retry.

### Tests

- API: each filter alone and combined, date boundaries, cursor reuse across filter sets → 400, ledger cap + flag, dispute rows without PII, `refundableCents` for released / not released / partially reversed, `LEDGER_CHANGED` on both POSTs with no gateway call, audit reason present; non-finance admin 403 on list/detail.
- Admin: filter params round-trip and invalid params dropped, ledger/dispute/payout rendering incl. empty and truncated states, expected values sent, `LEDGER_CHANGED` message.

## 1D.5c – CSV export, refund 409 codes, money rate limit (issue #551)

Owner: payments-engineer for the API (it owns `admin-bookings.service.ts` and `booking-refund.service.ts`). Then web-developer for the admin button and error mapping, then test-writer, plus code-reviewer, payments-engineer review and security-reviewer.

### Decisions

- **Export endpoint:** `GET /v1/admin/bookings/export.csv`.
  - It takes the same `status` / `createdFrom` / `createdTo` / `dispute` filters as the list; there is no cursor or limit.
  - It needs the `finance` permission and **fresh 2FA**. It has its own rate limit (below), because an export is a bulk read of financial data.
  - It is **fetch-only**: `Sec-Fetch-Mode: navigate`, or a `Sec-Fetch-Site` that is present and not `same-origin`/`same-site`, gets 403 `FORBIDDEN` before the audit row and the rate limit. `OriginGuard` lets GETs through and the `SameSite=Lax` cookie rides a cross-site top-level link, so without this a link on another site could spend the admin's budget. admin.photoo.lu and api.photoo.lu are same-site (dev on localhost ports too). Requests without Sec-Fetch headers (curl, old browsers) are allowed; permission and 2FA still apply.
  - CORS exposes `Content-Disposition`, so the admin app's cross-origin fetch can read the filename.
- **The export is streamed.** It reads in keyset batches of 500, in the list order (`createdAt desc, id asc`), and writes rows as they are read. Nothing is buffered in memory.
  - It is capped at 50 000 rows. Past the cap, the stream ends with one final `#truncated` line, so a cut file is never mistaken for a complete one.
  - Headers: `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="photoo-bookings-<from>-<to>.csv"`, `Cache-Control: no-store`.
- **Columns are the list fields, ids only, no PII:**
  - id, status, currency, total, refunded, reversed;
  - dispute status;
  - created, released, delivered and cancelled times, in ISO UTC;
  - the payment intent, charge and transfer ids.
- **Money columns use decimal major units in the booking's currency** (e.g. `12.34`). They come from integer cents through the shared money helper; there is no float maths.
- **Cells are protected against CSV injection.** Any cell starting with `=`, `+`, `-`, `@`, a tab or a carriage return is prefixed with `'`. Every cell is quoted per RFC 4180. Money cells are written as plain numbers; a negative is impossible in these columns.
- **Audit:** one `AuditLog` row, `admin.bookings_exported`, is written before streaming starts. It holds the canonical filter set and the cap, and contains no row data.
- **Distinct 409 codes** replace the generic `CONFLICT` on the admin refund and reverse paths:
  - `BOOKING_BUSY`: the money lock is held; retry shortly.
  - `BOOKING_STATE`: the booking is not in a state that allows the action (`details.status`).
  - `PENDING_REVERSAL_MISMATCH`: a reversal is waiting for its refund (`details.pendingCents`). This gives the admin the amount that unblocks the stuck case in #495.

  `LEDGER_CHANGED` stays as it is. The client refund path keeps its own messages; only the codes change if they share the helper.
- **Money rate limit:** refund and reverse-transfer share a per-admin rule, `admin:mutation:money`, of 5 requests per 10 minutes. This is on top of the shared 30/min admin mutation limit. The export has its own per-admin rule, `admin:export`, also 5 per 10 minutes, so exporting can never lock an admin out of refunds. The response is a 429 `TOO_MANY_REQUESTS` with `retryAfterSeconds`.
- **Contract first.** The export query schema, the new error codes and the OpenAPI entries change first: the endpoint is `text/csv` with documented 400/401/403/429 responses. Then regenerate the api-client.
- **Admin:**
  - An "Export CSV" action on `/finance` exports the active filters. It uses the same auth path as `lib/api.ts`. A stale 2FA goes through the reverify redirect and comes back to `/finance` with the same filters.
  - The new 409 codes map to `admin.finance.errors.*`.
  - `PENDING_REVERSAL_MISMATCH` shows the pending amount and offers to prefill it in the refund dialog.

### Tests

- **API:**
  - Export headers and the CSV body: quoting, the injection prefix, decimal money for EUR, empty results with only the header row, filters applied.
  - Paging across more than one batch, and the cap with its `#truncated` line.
  - The audit row and its filters.
  - Errors on export: 403 for a non-finance admin, `TWO_FACTOR_REQUIRED` on stale 2FA, a 400 on invalid filters.
  - The 429 after the money budget on refund and reverse, the 429 after the export budget, and neither budget spending the other.
  - A navigation or cross-site export gets 403 and writes no audit row.
  - Each of the three 409 codes and its details.
  - `TWO_FACTOR_REQUIRED` on refund and reverse; this is the outstanding item from #551.
- **Admin:**
  - The export link carries the active filters only.
  - Each new 409 message, and the pending amount being prefilled.
  - The 429 message, which already exists.
