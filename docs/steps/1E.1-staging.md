# Step 1E.1 – Staging environment

Plan reference: `docs/PLAN.md` step 1E.1 — "all services, Stripe test keys, Brevo sandbox, staging buckets, seed data, Stripe CLI webhook forwarding docs". Owner: devops-engineer. Blocked by 0.5 (merged: the preview at `footoo.bas.lu` runs from `main`).

Staging tracks **`dev`** and serves **`staging.photoo.lu`**. It unblocks 1E.5 (load testing) and is where Stripe test-mode webhooks can actually be received, which no local setup can do without a tunnel.

## Why 1E.1a comes first

`infra/dokploy/preview/compose.yml` is ~500 lines defining twelve services. Copying it to `infra/dokploy/staging/compose.yml` would create a second copy that drifts from the first, and the preview file already carries hard-won fixes that a copy would silently fork — `API_INTERNAL_URL: http://api:4000`, the `internal` network membership, `BACKUP_AGE_RECIPIENT` written without `:?` because one unset `${VAR:?}` aborts the deploy of the **entire** stack, and the two scoped MinIO users.

Compose's `include:` (or a shared base plus per-environment overrides) keeps one definition and lets each environment state only its differences. The differences are the interesting part of this step and should be readable in one screen, not diffed across two 500-line files.

## What staging must *not* inherit from preview

These are the decisions; everything else is deliberately identical.

- **Mailpit goes away.** Preview swallows mail in a container and sets `SMTP_INSECURE_INTERNAL_RELAY: 'true'` to opt out of TLS enforcement for it. Staging sends through **Brevo's sandbox** over real TLS, with that opt-out **removed** — otherwise the one environment that should prove the production mail path keeps the local shortcut, and the first real send happens in production.
- **Seeding is not automatic, and the seeded password is not a shared constant.** The preview seeds well-known accounts. Staging is reachable at a guessable hostname, so an auto-seeded `client@photoo.test` with a known password is an open door. The seed profile stays **manual** (run deliberately, like the preview's), and `SEED_USER_PASSWORD` is generated per environment. `SEED_USER_PASSWORD` for the preview also needs rotating (already in the follow-ups; I leaked it).
- **`NEXT_PUBLIC_ALLOW_INDEXING` stays `false`.** Staging is `noindex` for the same reason preview is: two indexable copies of the marketplace compete with the real one and split its ranking. Only production (2.4) sets it true.
- **Its own buckets, its own database, its own Redis.** Not a shared instance with a prefix. A staging migration that corrupts data must not be able to reach preview's, and `1E.5`'s load test will deliberately push this environment hard.
- **Its own backup target, or none at all.** The 1E.3 backup container encrypts to `BACKUP_AGE_RECIPIENT`. Staging data is disposable and re-seedable; backing it up costs storage to protect nothing. The honest default is **no backup service in staging**, stated explicitly rather than left as an oversight — with the caveat that this makes staging a poor rehearsal for the restore drill, so the drill stays on preview.
- **Deploys on green CI on `dev`**, mirroring `deploy-preview.yml`'s `workflow_run` guard — the same `conclusion == 'success' && event == 'push'` check, so a red run never reaches staging, and a fork PR can never trigger a deploy.

## Stripe (1E.1c)

- Staging is the first environment with a **public HTTPS URL that Stripe can reach**, so it is where `POST /v1/webhooks/stripe` gets a real endpoint and a real signing secret. Test mode only.
- `STRIPE_WEBHOOK_SECRET` is per-endpoint: the staging endpoint's secret is not the local CLI's. Documenting that distinction prevents the failure where signature verification passes locally and fails on staging.
- The runbook covers `stripe listen --forward-to localhost:4000/v1/webhooks/stripe` for local development, and states that the CLI's secret is printed once at start and differs per session.
- **Nothing in this step weakens webhook signature verification** to make an endpoint work. If a signature fails, it is a configuration bug to fix, not a check to relax.
- Real payment behaviour is 1A.8's; this step only makes the environment able to receive events.

## Capacity — the risk worth naming before this is built

The preview stack already runs twelve services on `dok.seil.pro`, including ClamAV, which is memory-hungry, and issue **#131 (worker OOM)** is open against it. Staging doubles that footprint on the same host.

If the VPS cannot hold two full stacks, the failure mode is not a clean "staging did not start" — it is the OOM killer taking a process from **either** stack, which would make the preview flaky and look like a code bug. So: check the host's memory headroom *before* deploying staging, and if it is tight, the options are a bigger VPS, or a reduced staging (sharing ClamAV, or omitting it and disabling the scan path in staging config, which weakens fidelity and must be stated rather than silently done). **This is a question for Alex, not something to guess at.**
