## Decisions for this step

- **Requirements come from `Country.requiredDocuments`**, never code branches. `GET /v1/countries/{code}/verification-requirements` returns the list, localised label and description, and accepted MIME types for enabled countries, 404 otherwise. The seeded Luxembourg list stays the source; changes happen through admin settings (1D.7).
- **One active case per photographer.**
  - `VerificationCase` is unique on `userId` where status is in `draft|submitted|in_review` (partial unique index).
  - A rejected or expired case stays for history, and a new `POST` starts a fresh `draft`.
  - The case country is the photographer profile's `countryCode`, set by the server and never by the client. A photographer profile is required first (403 otherwise).
- **Documents.**
  - `VerificationDocument(caseId, documentKey, uploadId, createdAt)` references an `Upload` with purpose `verification_document` owned by the caller. The DATA-MODEL `storageKey/mime/size/virusScanStatus` fields come from `Upload` instead of being duplicated, and DATA-MODEL is updated first.
  - `documentKey` must exist in the country's `requiredDocuments`, the MIME type must be in its accepted types, and the upload must already be `virusScanStatus: clean` (422 otherwise, matching submit's own check).
  - Re-attaching the same key replaces the previous document while the case is `draft`; in the same transaction the old upload is expired (`status: failed`, `expiresAt: now`) and, once the transaction commits, its storage object is deleted, so it doesn't stay retrievable forever (issue #116, compliance).
  - Documents are immutable after submit.
- **Submit.**
  - Requires every required document to be attached with its upload `clean` (ClamAV passed), plus `businessName`. `vatNumber` and `businessRegistrationNumber` are optional and validated per country later (DAC7 scope with the accountant, see human follow-ups).
  - Submitting sets `submittedAt`, case `submitted`, and profile `verificationStatus = pending`.
- **Encryption of PII fields.**
  - `businessName`, `vatNumber` and `businessRegistrationNumber` are encrypted at the application level with `packages/shared/src/crypto.ts` (`@photoo/shared/crypto`, shared with `packages/db`'s seed; see issue #104).
  - The key is a new `VERIFICATION_ENCRYPTION_KEY`, separate from `AUTH_ENCRYPTION_KEY` so they rotate independently. It's required in production and generated locally in `.env.example` instructions, and added to the preview compose and `.env.example`.
  - Columns are `bytea`/text ciphertext, so no search on them.
- **Admin review** (`admin` role, 2FA session required, the same guard the admin API will use in 1A.11; add the guard now if it doesn't exist):
  - `GET /v1/admin/verification-cases` is keyset by `submittedAt asc` with filters `status` and `countryCode`, returning `AdminVerificationCaseSummarySchema`: no decrypted business fields and no per-document download links, only `photographer: { displayName, email }` — paging the queue never mass-decrypts PII or mass-issues presigned URLs, and carries no audit cost.
  - `GET /v1/admin/verification-cases/{id}` returns `AdminVerificationCaseSchema`: decrypted business fields plus a presigned GET URL (5 minutes) per document, but only for a document whose upload is `virusScanStatus: clean` and `status` in `clean`/`processed`; a still-scanning or infected document is returned without `downloadUrl` rather than blocking the whole case view.
  - `POST …/{id}/start-review`, `…/approve` and `…/reject` also return `AdminVerificationCaseSummarySchema` (no decryption, no download links needed for a transition response).
  - `POST …/{id}/start-review` moves `submitted → in_review` (assignee is the admin).
  - `POST …/approve` moves `in_review → approved`, and profile `verificationStatus = verified`.
  - `POST …/reject` with `{ reason }` (1–1000 chars) moves `in_review → rejected`, and profile `verificationStatus = rejected`.
  - Transitions are conditional `updateMany` on the expected status (409 otherwise).
  - Every transition and every document URL issuance writes `AuditLog`, including the caller's IP (verification mutations plus access to PII).
- **Publish effects.**
  - DATA-MODEL invariant: `isPublished` requires `verified` and `stripePayoutsEnabled`.
  - This step adds `PublishPolicy.canPublish(profile)` in one place, used by the existing publish path. Approve does **not** auto-publish, because Stripe (1A.8) is still needed.
  - Rejecting or expiring a verified photographer's case unpublishes the profile in the same transaction.
  - Seeded demo profiles stay published through the seed, which bypasses the policy explicitly and is marked in the seed. No code shortcut.
- **Expiry.** An approved case expires after the country's validity period (not modelled yet). Deferred: no expiry job in this step, and the status stays in the enum.
- **Notifications.** New types `verification_approved` and `verification_rejected` (email and in-app; the reason is shown in-app only, not in the email body) through `NotificationsService`.
- **Rate limits.** Case create 5 a day, submit 10 a day, case update 30 a day, document attach 30 a day, admin document URL issuance 120 an hour per admin charged per document actually presigned (not per case view).
- **Retention.** `docs/COMPLIANCE.md` already states account lifetime + 5 years. Deletion itself is 1A.12. Nothing is deleted here.

## 1A.9a tasks (schema-migrator)

1. DATA-MODEL first:
   - `VerificationCase` with encrypted columns, `assignedAdminId`, `decidedByAdminId`, `rejectionReason` and a status enum;
   - `VerificationDocument` referencing `Upload` (`uploadId` unique, `Restrict`), unique `(caseId, documentKey)`;
   - a partial unique active case index.
2. Migration via `migrate diff` (strip the known GiST index drift lines), applied to photoo and photoo_test.
3. Seed: one `submitted` case for a seeded unverified photographer (if none exists, add an unpublished one) with placeholder clean uploads. The fields are encrypted with the seed's dev key, and the seed reads `VERIFICATION_ENCRYPTION_KEY` with a dev fallback only outside production.
4. Tests:
   - partial unique index (a second active case is rejected, allowed after reject);
   - unique `(caseId, documentKey)`;
   - `Restrict` on the upload;
   - seed idempotency.

## 1A.9b tasks (api-developer)

1. Contract gaps in `verification.ts` and `admin.ts`: start-review, reject reason bounds, presigned document URLs on the admin case, error responses, and the new notification types. Regenerate openapi and api-client.
2. `VerificationModule`: photographer routes (`/me/verification-case`, documents, submit), admin routes with the 2FA admin guard, `PublishPolicy`, encryption service, and notifications.
3. Env: `VERIFICATION_ENCRYPTION_KEY` in api env validation, `.env.example`, preview compose and `.env.example`. The CI test env uses a dev value.
4. Tests (integration):
   - requirements per country;
   - document key and MIME validation;
   - unclean upload blocks submit;
   - someone else's upload gives 422;
   - immutability after submit;
   - admin guard (a non-admin gets 403, an admin without 2FA gets 403);
   - transitions and 409s;
   - approve sets verified and doesn't publish; reject of a verified photographer unpublishes;
   - AuditLog rows for transitions and URL issuance;
   - encrypted columns are not plaintext in the DB;
   - notifications created.
5. Security checkpoint (security-reviewer) before merge: PII encryption, access to documents, admin 2FA, and logs free of business fields and URLs.
