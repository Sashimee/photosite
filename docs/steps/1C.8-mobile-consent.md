# Step 1C.8 – Mobile analytics consent, Firebase Analytics and ATT

Plan reference: `docs/PLAN.md` step 1C.8 — "Analytics consent + Firebase Analytics + iOS ATT flow per `COMPLIANCE.md`". Owners: mobile-developer, then compliance-reviewer (1E.7 names this as a checkpoint). Sized **S**, listed as depending on 1C.1 alone.

**The stated dependency is incomplete.** Storing a consent decision needs an API that does not exist yet:

- `POST /v1/consents` (the anonymous, pre-sign-in path) is registered in the contract but sits in `NOT_YET_IMPLEMENTED` (`apps/api/src/common/http/not-yet-implemented.ts`).
- `GET`/`PUT /v1/me/consents` — the signed-in read and write that `docs/steps/1A.12-gdpr.md` specifies — are **not in the contract at all**. `packages/shared/src/contract/gdpr.ts` is a stub predating that plan, which is #197.

So 1C.8 depends on the consent half of **1A.12**, and so does 1B.10 on the web side. Two planned steps are waiting on the same unbuilt API, and the plan's dependency column records neither (#213). Either 1A.12's consent endpoints land first, or both consent steps store decisions only on-device and backfill later — and that second option is worse than it sounds, because a consent record with no server-side evidence is not proof of consent when someone asks for it.

## Decisions for this step

- **Analytics is off until it is switched on, and "off" means not initialised.** `COMPLIANCE.md:26` says Firebase Analytics is disabled at start and enabled after consent. Not "initialised but not sending" — the SDK collects on init. The app must start with collection disabled and enable it only after a granted decision.
- **ATT and GDPR consent are different things, and conflating them is the classic mistake.** ATT governs access to the IDFA for cross-app tracking; GDPR/ePrivacy consent governs analytics and ads processing regardless of identifier. Granting ATT is not consent to analytics, and denying ATT does not withdraw it. They are asked separately, and the copy for each says what it actually controls.
- **No ATT prompt at all unless ads attribution is actually used.** `COMPLIANCE.md:26` is explicit: "shown only if ads attribution is used". Nothing in the product uses it today. iOS shows the system prompt **once** — burning it before there is anything to attribute converts a future yes into a permanent no. So 1C.8 ships **without** an ATT prompt, and the plan records that as a decision rather than an omission; when ads attribution arrives, it gets its own step.
- **The consent categories match the web's exactly**: necessary (always on), analytics, ads/marketing (`COMPLIANCE.md:24`). A user who declines analytics on the website and is asked again in different words in the app will reasonably conclude we are shopping for a better answer.
- **`policyVersion` comes from the server, never the client** — the same rule 1A.12 sets for the web. A client-supplied version lets the caller forge what they agreed to.
- **Declining is one tap, and as easy as accepting.** Not a nested settings dive, not a pre-ticked box, no "Accept all" styled as the only real button. This is an explicit ePrivacy requirement and also the thing most likely to be quietly got wrong.
- **Consent is changeable afterwards from account settings**, and withdrawal takes effect immediately — collection stops, and the SDK is disabled again in the same session rather than at next launch.
- **A decision made before sign-in is linked at sign-up** via the `anonymousId` 1A.12 defines, so a user who chose on the onboarding screen is not asked twice.
- **Firebase Analytics needs a dev build, not Expo Go**, and config files (`google-services.json`, `GoogleService-Info.plist`) that do not exist yet. 1C.8a and 1C.8b are fully testable without any of it; 1C.8c is the sub-step that waits.
- **Whatever the SDK collects has to be declared** in the App Store privacy manifest and the Play data-safety form (1C.9). 1C.8's decisions therefore determine 1C.9's answers, and 1C.9 must not be filled in before this lands — a data-safety form that disagrees with what the app does is a store rejection at best.

## Tasks

1. **1C.8a** — consent screen at first launch and in account settings; on-device state in `expo-secure-store` (it is the existing storage and this is not a secret, but it must survive restarts); a single `analyticsEnabled` gate every future call site reads; tests that no analytics call fires before a granted decision and that withdrawal disables it in-session.
2. **1C.8b** — persist through `POST /v1/consents` and the signed-in endpoints once 1A.12 ships them; link `anonymousId` at sign-up.
3. **1C.8c** — Firebase Analytics behind the gate, added via `expo install` and satisfying `minimumReleaseAge` (**`minimumReleaseAgeExclude` is not to be touched**).
4. i18n under `mobile.consent.*`, English only; the copy says what each category does in plain words, not "we value your privacy".
5. Tests: the gate blocks collection; withdrawal is immediate; declining is reachable in one tap from the prompt; no ATT prompt exists; `policyVersion` is never sent by the client.

## Human follow-ups

- **A Firebase project and its config files** — part of 0.6, already tracked. Blocking for 1C.8c only.
- **Confirm no ads attribution at launch.** The plan assumes none, and therefore no ATT prompt. If mobile install campaigns are planned, say so before 1C.9 — the answer changes the privacy manifest and the one-shot iOS prompt.
- **The consent copy is legal text.** Like the cookie policy in 1B.10, the categories and their descriptions want the lawyer's eye in the 0.7 conversation; this step ships the mechanism and plain-English drafts.
