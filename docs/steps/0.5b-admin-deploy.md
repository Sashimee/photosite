## #54 is a hard gate, not a checklist item

`packages/db/src/seed.ts` gives `admin@photoo.test` the **same** `SEED_USER_PASSWORD` as the demo users, with `twoFactorEnabled: false`. That password is currently leaked (I printed it during the outage investigation) and unrotated.

Mandatory 2FA does not save this, and it is worth being precise about why:

1. Signing in as the seeded admin with that password succeeds.
2. Every `/v1/admin/*` route correctly refuses — `requireAdminSession` demands a `twoFactorVerifiedAt` that only sign-in/totp and totp/verify ever stamp. **The guard holds.**
3. But `POST /v1/auth/totp/enroll` needs only a valid session plus the account password — the same leaked secret. The attacker enrols *their own* authenticator.
4. `totp/verify` stamps the session, and step 2 now passes.

2FA protects a compromised password only while the attacker cannot enrol a factor themselves. Here they can, because enrolment is gated on exactly what leaked. This is live on the preview **today**, without the admin UI existing — the admin API is already deployed.

So: rotate `SEED_USER_PASSWORD` and re-seed first (Alex), then fix the seed so a deployed environment never has a shared admin credential — a separate `SEED_ADMIN_PASSWORD`, or no seeded admin at all outside local development. Nothing else in this step proceeds until that is done.

## Decisions for this step

- **The admin app gets its own image and its own hostname.** `admin.footoo.bas.lu`, mirroring `web.Dockerfile`: multi-stage, non-root, standalone Next output. Not a path on the public site — a separate origin keeps its cookies, CSP and Traefik rules independent of the marketplace's.
- **It is `noindex` and it is never cached.** The admin app already sets `Cache-Control: no-store`; the deploy must not add a CDN or proxy cache in front of it.
- **`NEXT_PUBLIC_STORAGE_ORIGIN` must be set, or the document viewer silently fails** (#209). The viewer `fetch()`es a presigned storage URL, which needs that origin in the CSP `connect-src`. A CSP block surfaces as a generic error, so an unset value would make the verification screen report a broken document rather than a misconfiguration. Set it in the compose env at the same time as the service, not afterwards.
- **Exposure is the open question, and the honest default is restrictive.** An admin panel on a public hostname is reachable by anyone who resolves it. The host already runs Traefik with a CrowdSec bouncer, and the app enforces admin role plus 2FA — but defence in depth for an admin surface usually means not serving it to the open internet at all. Options, in the order I would take them: an IP allow-list at Traefik for Alex's addresses; failing that, accept public exposure and rely on the app's own guards, **stated as a decision rather than assumed**. This is a question for Alex, and it is why 0.5b-b is separate from 0.5b-a.
- **Capacity applies here too.** The 1E.1 note stands: the preview already runs twelve services on `dok.seil.pro` and #131 (worker OOM) is open. One more Next.js container is far smaller than a second full stack, but it is not free, and the same memory headroom question covers it.
- **The deploy is verified in a browser, not by status code.** Sign in with a real second factor, load the users list and the verification queue, open one document in the viewer, and confirm no console errors. The preview outage happened because status codes looked healthy while every page was broken; an admin panel verified only by `curl` would repeat that exactly.
