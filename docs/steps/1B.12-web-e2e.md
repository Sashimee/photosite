## What already exists — read before planning further

- **`tests/smoke/`** (`pages.ts`, `signed-out.spec.ts`, `signed-in.spec.ts`, `auth.setup.ts`, `assert-page-works.ts`): asserts a fixed route list *loads* — no uncaught error, no console error, no failed same-origin request, no error-boundary text — in every locale signed out, and in `en` only signed in as the seeded client. It asserts nothing about what a page *does*. `auth.setup.ts` already solved UI sign-in once, including a real pitfall (filling and submitting the sign-in form faster than React attaches its handler falls back to a native GET with the password in the URL, guarded by a 500 ms settle plus a `framenavigated` assertion) — this step reuses that pattern rather than rediscovering it.
- **`playwright.config.ts`**: root-level, Chromium only (WebKit doesn't install on this host), two projects (`smoke-public`, `smoke-authenticated` plus their `setup` dependency), `baseURL` from `SMOKE_BASE_URL`.
- **`.github/workflows/ci.yml`'s `browser-smoke` job**: boots Postgres/Redis/MinIO, creates and migrates `photoo_test`, seeds it, builds `apps/api`+`apps/web`, starts both as real servers, waits on them with a `curl -sS --max-time 5` loop that prints the response body on failure rather than a bare timeout (a lesson paid for once already — "a wait that hides its own error cost three diagnosis passes"), then runs `pnpm test:smoke`. 20-minute job timeout.
- **`docs/steps/1E.9-browser-smoke.md`**: the reasoning above; also the reason `apps/web/e2e` is the agreed location and why Playwright lives at the repo root.
- **`tests/lighthouse/`** (1B.11b): the most recent precedent for adding an isolated CI job to protect a flaky-prone check from CPU contention with everything else the runner does — see Decisions below for whether the same applies here.
- **`packages/db/src/seed.ts`**: the identities and states that already exist, checked directly rather than assumed:
  - `client@photoo.test` / `SEED_USER_PASSWORD` (`getSeedUserPassword()`, default `correct-horse-battery-staple`) — the one identity `tests/smoke` already signs in as. One `Request`/`Quote` pair (`seedRequestAndQuote`) and one `Conversation` (`seedQuoteConversation`) already exist on it, relied on by `apps/api`'s own integration tests (`requests-quotes.test.ts`) — **not to be mutated by this step's specs**.
  - `sofia.martins@photoo.test` (`sofia-martins`) — the **only** seeded photographer that is `verificationStatus: 'verified'`, `isPublished: true`, with real products/tiers, and shares the same `SEED_USER_PASSWORD` credential. `karim-diallo` and `lena-weber` exist too, covering disjoint categories/cities (event/corporate in Esch-sur-Alzette, real_estate/product in Ettelbruck) — useful for keeping a fixture request's routing unambiguous.
  - `noor.hassan@photoo.test` (`noor-hassan`) — unpublished, `verificationStatus: 'pending'`, and its `VerificationCase` is already `status: 'submitted'` **with every required document already attached** (`seedVerificationCase`). It exists to render 1B.8c's read-only submitted-state, and it cannot be used to exercise the interactive "upload a document, then submit" journey — that state doesn't exist for it anymore. This is a real trap worth naming so nobody reaches for this identity by name and gets confused when there's nothing left to upload.
  - `professional@photoo.test` — has the `professional` role and no `ProfessionalProfile`, exercising exactly the "role without a profile" case 1B.9 built around. `seedProfessionalJobOffer` gives a *different*, separately-created professional profile one published `JobOffer` and zero applications.
  - Every seed user's credential shares one password (`seedCredentialAccount`, one Argon2id hash for all of `SEED_USERS` and `SEED_PHOTOGRAPHER_PROFILES`), read the same way `tests/smoke/pages.ts` already documents it.
- **`apps/api/src/testing/mailpit.ts`**: `waitForLinkInEmail(to, linkPattern, timeoutMs)` — polls Mailpit's REST API (`127.0.0.1:8025`) every 200 ms up to a bounded timeout, throwing a named error on expiry. `apps/api`'s own auth/notification integration suites already prove this pattern works; this step needs the same capability from `apps/web`'s side, not a new design.
- **`apps/web/src/lib/consent.ts`**: `encodeConsentCookieValue()` is exported and produces the exact `photoo_consent` cookie value the banner reads — directly reusable to pre-seed consent without touching production code.
- **1B.5 / 1B.8d / 1B.9 decisions already on the record**, load-bearing for scoping the flows below: accept only records `accepted` ("Booking and payment arrive soon" is the literal, still-current copy); a professional cannot reach draft-offer creation unverified because the profile-creation call itself requires a verified email; a taken-down or expired job offer renders identically to "never existed".

## Decisions for this step

- **Relation to `tests/smoke`: a second, independent suite, not an extension.** Different directory (`apps/web/e2e/` vs root `tests/smoke/`), different Playwright project (`e2e`, no `setup`/`storageState` dependency on the smoke projects), different CI job, different failure semantics. `tests/smoke` asserts "the page rendered without erroring"; this step asserts "the flow reached the state it claims to." Concretely, this suite never re-asserts "no console error" as its own check — if a spec here happens to prove a page loads, that's incidental, not the point, and duplicating `assertPageWorks` per flow would double the maintenance surface for zero new signal. Locale breadth stays owned by `tests/smoke` too: 1B.12 runs in `en` only (mirroring `smoke-authenticated`'s own precedent), because a flow's mechanics don't change per locale and running six specs × five locales would 5x the runtime for translated-string coverage that `packages/i18n`'s own catalog-consistency check already owns.
- **Pay is out, and the boundary is asserted, not just documented.** 1B.12c drives the request/quote/accept flow through to the client seeing "Booking and payment arrive soon" and the request status becoming `booked`, and asserts that exact state. This is deliberate: when 1B.7 lands, this assertion has to be *edited* to add the payment step, which forces whoever builds 1B.7 to touch this spec rather than let it silently keep asserting a placeholder that no longer matches reality. The follow-on work (Stripe test-mode Payment Element, booking status pages, delivery acceptance, refund request) is named in Notes for later steps as a new sub-step, not squeezed in here.
- **No flow in this step is driven against the deployed preview.** `tests/smoke` already has a second post-deploy job for exactly the "does the environment work" question, and it deliberately stays read-only-ish (loads real seeded pages) precisely because footoo.bas.lu is a shared, real environment that other people and future 1B.12 runs will look at. Creating throwaway sign-ups, requests, job offers and chat messages against that same environment on every deploy would pollute the one environment humans actually eyeball. If a preview-only regression is ever suspected, it gets diagnosed by hand or by running this suite locally with `SMOKE_BASE_URL`-style pointing, not by adding it as a standing job.
- **Test data isolation: fresh identities via API + Mailpit for anything that only needs "a verified account", the one seeded verified photographer for anything that needs "an existing, quotable, published profile".** Nothing in the API lets an account self-serve past photographer verification (it's an admin queue, 1D.3/1A.9) or past professional-profile creation's own verified-email gate without going through real verification — so a flow that *needs* an already-published, already-verified photographer with real products (request → quote → accept, chat) has exactly one option: reuse `sofia-martins`. Every other flow (sign-up itself, professional posting an offer, a photographer applying to one, a photographer running the onboarding checklist from zero) creates its own throwaway identity per run through `createVerifiedUser(role)` (1B.12a), because nothing about those flows requires a seed-only, human-gated state. This is also why 1B.12e does **not** reuse `noor-hassan` (see above): the checklist/upload/submit journey needs a "nothing done yet" starting point, which a fresh sign-up gives for free and a seeded, already-submitted case cannot.
- **Sharing `sofia-martins` means her request/quote inbox is a shared, growing resource — every assertion against it is scoped by a run-unique marker, never by position or count.** This is the same lesson #225/#277/#288/#304 already paid for at the database and Redis layer, applied one level up: a spec that asserts "the first request in the inbox" or "there is exactly one quote" will eventually collide with another 1B.12 run (concurrent CI shards, or a developer running the suite twice locally without resetting the stack) or with `apps/api`'s own integration tests that read `sofia-martins`'s seeded, canonical request. 1B.12c and 1B.12d build their fixture request/offer titles and chat message bodies with `randomUUID()` (mirroring `uniqueEmail()` in `auth.integration.test.ts`) and locate everything by that marker. Choosing `portrait` + Luxembourg City coordinates for the fixture request also keeps routing unambiguous: `karim-diallo` and `lena-weber` cover different categories and cities, so only `sofia-martins` ever matches it.
- **No cleanup step, by design — uniqueness is the mitigation, not an `afterAll`.** `docs/ARCHITECTURE.md`'s testing section already commits integration suites to "never `TRUNCATE`... tests must be safe to run repeatedly against the same, growing database"; this step inherits that rule rather than inventing a stricter one. A cleanup hook that itself might not run after a crashed browser or a killed CI job is a worse guarantee than rows that simply never collide because their identifiers are unique. In CI the database is thrown away with the runner regardless; locally, accumulated throwaway sign-ups/requests/offers are an accepted, already-precedented cost of running integration-style tests against a shared, persistent stack.
- **Auth rate limits are reset before every test, not just documented as a risk (#316).** `apps/api`'s per-IP auth limits (sign-up 5/hour, verify-email 10/hour, sign-in 5/minute — `auth-rate-limit.service.ts`) apply to every real sign-up/verify/sign-in this suite's fixtures make from the one runner IP, and one full run across 1B.12b–f already needs more sign-ups than the sign-up budget allows. `apps/web/e2e/support/rate-limit.ts` connects to `REDIS_URL` directly and deletes both the `rate-limit:auth:*` counter keys and the `lockout:auth:*` exponential-backoff keys — the same key shapes and clearing logic as `apps/api`'s own `auth.integration.test.ts`, ported rather than imported across the app boundary this step already keeps closed. It runs as an autouse fixture in `apps/web/e2e/support/test.ts`'s own `test`, immediately before every test, not a `globalSetup` (only resets once per run, which doesn't cover a run whose specs collectively exceed the budget) and not a per-spec `afterEach` (skippable by a test that crashes before it runs — the same "hook a crashed run skips" shape this document already used to reject cleanup hooks, except here that gap would silently reintroduce the exact failure being fixed). **Every spec in this suite imports `test`/`expect` from `./support/test.js`, never `@playwright/test` directly** — 1B.12c–f must follow this or their specs run unprotected.
- **Email-dependent steps: Mailpit polling in one spec through the UI, everywhere else through a fixture.** Sign-up's own spec (1B.12b) is the only one that drives the real browser through "submit the form → check your email → open the Mailpit-delivered link → land verified", because that mechanism is itself the thing worth proving once. Every other spec that just needs *a* verified account calls `createVerifiedUser()`, which signs up and verifies over plain HTTP (via `@photoo/api-client`, same pattern `apps/api`'s own integration tests use) and polls Mailpit the same way — no browser navigation spent on a mechanism already proven elsewhere. The Mailpit client is a small, focused port of `apps/api/src/testing/mailpit.ts` into `apps/web/e2e/support/mailpit.ts` rather than an import across the app boundary (`apps/web` should not reach into `apps/api/src/testing`, and `tests/smoke`'s own `auth.setup.ts` already sets the precedent of re-implementing a small piece of UI mechanics locally rather than importing from `apps/web` internals). Every Mailpit wait keeps `waitForLinkInEmail`'s own discipline: a bounded timeout and an error message naming what didn't arrive and for whom — directly closing the failure mode #288's own comment records, where a Mailpit timeout got misread as a 409-vs-400 bug in an unrelated subsystem three diagnosis passes later.
- **Determinism: no bare sleeps for flow control, one narrow, named exception.** Every wait is on a selector, a URL, or a response — Playwright's own auto-waiting `expect(locator)` covers the large majority of this for free. The one sleep this suite keeps is `auth.setup.ts`'s already-proven `HYDRATION_SETTLE_MS`-style guard, reused wherever a spec fills and submits a form immediately after `page.goto()` (sign-up, sign-in, the request form, the job-offer form) — the same fast-fill-beats-hydration race applies to all of them, not just the one page it was first found on, and it is a documented, narrow exception rather than a general license to sleep. The `curl -sS` lesson generalises the same way here as it did for Mailpit above: a wait that times out silently is a debugging tax on whoever hits it next, so every custom wait in this suite's fixtures states what it was waiting for in its failure message.
- **The consent banner is pre-seeded, never clicked.** `photoo_consent` (`apps/web/src/lib/consent.ts`) is a plain cookie whose value `encodeConsentCookieValue()` already produces; the harness fetches the current `GET /v1/policy-version` and writes a "rejected" decision under that version via `context.addCookies()` before any flow spec navigates (rejected, not accepted, to match the realistic first-visit default 1B.11 already established for its own budget). This is a deliberate substitute for clicking "reject" on every spec: a banner is a transient overlay that can intercept a click meant for the page underneath it — exactly the shape of race `auth.setup.ts`'s own native-submit pitfall warns about — and removing it from the state entirely is more reliable than timing a dismissal correctly in six different specs.
- **CI shape: a new, separate `e2e` job, not a step inside `browser-smoke`.** 1B.11b already concluded that a flaky-prone check earns its own isolated job so its failures aren't confused with anything else's, and it applies again here for a different reason: `browser-smoke`'s entire value is being a **fast**, near-unconditional "did the page load" signal (its own doc sizes its 20-minute timeout around a ~2-minute suite plus boot overhead); folding in a much larger, network- and email-round-trip-heavy suite would both blow that budget and muddy what a red `browser-smoke` means. The new `e2e` job clones `browser-smoke`'s stack-boot/build/seed/serve steps (same env vars, same `wait_for` loop) rather than inventing a second way to bring the stack up, and runs `pnpm test:e2e` in its place.
- **Gating is staged, not immediate.** A flaky e2e suite that blocks merges is worse than no suite at all — people learn to re-run rather than read, exactly the failure mode #201/#277/#288/#304 already describe for other suites, and browser e2e is a strictly higher-flake category than any of those (real navigation, real sockets, real email round-trips, all at once). The `e2e` job ships **non-blocking** (reports its result, is not a required status check) for an initial burn-in period; it is promoted to required only once it has passed repeatedly across real PRs with no failure traceable to the harness itself — the same evidence bar #288's own "done when" criterion set (ten consecutive passes on a loaded machine) before trusting a fix. Toggling the required-check setting is a GitHub branch-protection change, so it's also named in Human follow-ups below rather than done silently by a future PR.
- **Runtime budget: a stated number, and a stated response to blowing it.** Target: the Playwright run itself under 10 minutes (six specs, `en` only, bounded workers), the whole job — stack boot, build, seed, server start, suite — under the 20-minute ceiling `browser-smoke` already uses, so the two jobs stay comparable. If a spec routinely pushes past that, the fix is to cut or split it, never to raise the timeout to make it pass quietly (`#201`'s own fix-options list ranks "raise the timeout" last for exactly this reason — it's honest about the cost being real but doesn't remove it). Workers are bounded explicitly (not left at Playwright's local default of one-per-core) because this job's runner is already running Postgres, Redis, MinIO, the API and the web server at once — the same CPU-oversubscription shape #201 named for `apps/mobile`, just with a browser added to the mix.
- **Which flows earn a browser test.** The bar is "a real browser, real navigation, real sockets, or a real multi-step file upload is the only way to see this break" — not "this page exists."
  - **Worth it:** sign-up + verify + sign-in (the one flow that is a real, multi-system round trip — browser form → API → Mailpit → link click → API → redirect — and the front door to every other flow); request → quote → accept (the literal headline flow's non-pay half, spanning two roles and two dashboards, with real `router.refresh()`-driven state transitions no API-only test can see); chat (Socket.IO's connection lifecycle and optimistic send/receive is real-browser-only — `jsdom` has no WebSocket handshake, which is exactly why `docs/ARCHITECTURE.md`'s coverage-exclusions section already names Playwright as covering what Vitest structurally cannot here); photographer onboarding through verification submit (a real multi-request presigned-upload sequence — create upload, PUT to MinIO, complete, poll scan state — plus the checklist's cross-cutting "Stripe not available yet" copy, one of 1B.8's most regression-prone pieces of UI honesty); the professional/job-board journey end-to-end once (post → publish → appears on the public board → apply → shortlist), because it is the one flow here that crosses an authenticated write on one side and an anonymous public read on the other.
  - **Deliberately excluded, with reasons:** password reset (mechanically identical fragment-token-off-a-Mailpit-link shape to verify-email, already covered by that spec's Mailpit-polling mechanics, and its component-level validation is already unit-tested — a second spec would double the email-polling flake surface for no new class of bug); 2FA sign-in / TOTP enrolment (no browser-only risk beyond the sign-in form already covered; the TOTP logic itself is integration-tested at the API using `apps/api/src/testing/totp.ts`, and coordinating a real clock-based code from Playwright only adds a new timing-flake source for no new coverage); OAuth sign-in (no provider credentials exist in CI or local dev per `docs/steps/human-followups.md`'s credentials table — untestable without secrets this environment doesn't have, and 1A.2 already gates providers off entirely when unconfigured); every other page-load-only concern (already `tests/smoke`'s job, not duplicated here); admin-side moderation/verification review (that UI lives in `apps/admin`, a different Next.js app — out of scope for a step titled "web e2e" against `apps/web`, and would be its own step if ever planned); the fuller job-board CRUD matrix — draft/close/expire/re-open, remote-vs-located rendering, compensation-present-vs-absent — already covered by 1B.9's own component tests and `buildJobPostingJsonLd`'s unit tests, so 1B.12f exercises exactly one lifecycle instead of re-asserting branches a browser adds nothing to.
- **Browser scope: Chromium only, inherited, not re-decided.** `tests/smoke` already established WebKit doesn't install on this host's dependencies; this step doesn't reopen that.

## 1B.12c tasks

1. `apps/web/e2e/request-quote.spec.ts`: a fresh client (`createVerifiedUser('client')`) signs in, submits `/{locale}/requests/new` with category `portrait`, Luxembourg City as the location source, and a `randomUUID()`-tagged title.
2. A second browser context signs in as `sofia.martins@photoo.test`, opens the dashboard quotes inbox, locates the new request by its unique title, sends a quote with line items.
3. Back in the client's context, `/{locale}/requests/{id}` shows the new quote; accept it (with the confirmation dialog), and assert the request status becomes `booked` and the page shows the literal "Booking and payment arrive soon" copy — the explicit, intentional stand-in for 1B.7.
4. A second case: decline a quote, assert the request's status reflects it and the quote is no longer actionable.
5. Error-mapping smoke: attempt to accept the same quote twice from two tabs (or a stale page + `router.refresh()`), asserting the 409 "no longer available" mapping — the closest this flow has to a double-accept race, worth proving once since 1B.5's own decisions document that exact mapping.

## 1B.12d tasks

1. `apps/web/e2e/chat.spec.ts`: build the fixture conversation directly over HTTP (fresh client + `sofia-martins`, a request/quote/conversation created the same shape as `seedQuoteConversation`, tagged with a unique subject) rather than through the browser — the flow under test is the socket layer, not how the conversation came to exist.
2. Two `BrowserContext`s (client, photographer) both open `/{locale}/messages/{conversationId}`; one sends a message with a `randomUUID()`-tagged body; assert it appears in the other's thread without a page reload (a socket push, not a poll) and that the conversation-list unread badge updates for the recipient.
3. A sub-case sending an attachment through the existing presigned-upload flow, asserting it renders in both threads.
4. Explicitly out of scope here: the socket-unavailable POST fallback (already covered by 1B.6's own component tests against a mocked socket) — this spec's only job is proving the real connection works.

## 1B.12e tasks

1. `apps/web/e2e/photographer-onboarding.spec.ts`: a fresh photographer (`createVerifiedUser('photographer')`) lands on `/{locale}/dashboard`, sees the checklist with nothing done and the Stripe row rendered as "not available yet" (not omitted — the exact regression 1B.8's decisions warn against).
2. Create the profile (`/{locale}/dashboard`'s profile editor): a sub-case submits a colliding/invalid slug first to prove inline validation fires before a happy-path submission.
3. Upload one portfolio image (a small real test fixture file) and assert the scanning → processed state transition via polling the DOM, not a sleep; add one product with a tier and assert the cents conversion round-trips correctly on re-render.
4. Verification: open the requirements (rendered from `GET /v1/countries/LU/verification-requirements`, not hardcoded), upload **two** of the four required document types (enough to prove the multi-document submit transition; the remaining two are mechanically identical and already covered per-type by 1B.8c's own tests), submit, and assert the case becomes read-only — attempting to navigate back to an upload control confirms none is offered, per 1B.8c's explicit no-edit-after-submit rule.
5. Assert the checklist now reports "verification submitted" without implying publication — 1B.8a's own decision that the UI reports state, never implies it publishes.

## 1B.12f tasks

1. `apps/web/e2e/job-board.spec.ts`: a fresh professional (`createVerifiedUser('professional')`) creates a company profile, then a job offer with a `randomUUID()`-tagged title, and publishes it.
2. A signed-out browser context opens `/{locale}/job-offers`, locates the offer by its unique title (not by list position, since the seeded `seedProfessionalJobOffer` offer and other concurrent runs' offers share the same board), and opens its detail page.
3. A fresh photographer (`createVerifiedUser('photographer')`) signs in, applies with a message; a second attempt at applying to the same offer asserts the 409 "already applied, see it in My applications" mapping 1B.9c built.
4. Back in the professional's context, the applications inbox shows the new application by the applicant's identity; shortlist it.
5. In the photographer's context, "my applications" shows the `shortlisted` status.
6. Explicitly out of scope: draft/close/expire transitions, remote/compensation rendering variants, and `JobPosting` JSON-LD shape — already covered by 1B.9's own component and unit tests; this spec proves the one lifecycle a browser adds real value to.
