# Step 1B.8 – Photographer dashboard (web)

Plan reference: `docs/PLAN.md` step 1B.8 — "onboarding wizard (profile, portfolio upload with provenance status, products + tiers, verification documents per country, Stripe onboarding link), quotes inbox, bookings, earnings". Owner: web-developer, with payments-engineer reviewing 1B.8e–f. Sized **XL**, and listed as needing 1A.4, 1A.8, 1A.9 and 1A.10.

**Two of those four dependencies are missing, but they only block two of the six sub-steps.** Checking `NOT_YET_IMPLEMENTED` in the API against the contract:

| 1A.4 profiles, portfolio, products | **implemented** | 1B.8a–b buildable now |
| 1A.9 verification | **implemented** | 1B.8c buildable now |

## Decisions for this step

- **The onboarding wizard is a checklist, not a linear wizard.** A photographer arrives with different things ready: some have a portfolio but no bank details, some the reverse. A forced sequence makes the one blocked step block everything behind it — and one of those steps (Stripe) does not exist yet. The dashboard home is a checklist of what is done, what is missing, and what each unlocks, with a clear statement that a profile is not published until verification passes.
- **The checklist names the gate honestly.** Publication depends on the API's rules (1A.9 owns the status effects). The UI reports state; it never implies an action publishes a profile when it does not.
- **Stripe's absence is shown, not hidden.** 1B.8e is blocked, so until it lands the checklist shows payouts as "not available yet" rather than omitting the row — a photographer who cannot find where to add bank details assumes the site is broken. When 1A.8 lands, the row becomes the real link with no restructuring.
- **Provenance degrades to nothing, visibly.** `docs/PLAN.md` asks for "portfolio upload with provenance status", but no photographer-facing provenance route exists and 1A.10 decided the photographer never sees scores, vendors or match URLs. So 1B.8b shows upload and scan state only (from the existing `Upload` status), and the provenance verdict is added later behind the same component. **No placeholder score, no invented badge** — a fabricated "verified" mark on an image nobody checked is worse than no mark.
- **Portfolio ordering is a real interaction and needs care.** `PUT /me/photographer-profile/portfolio/order` exists. Drag-and-drop must have a keyboard path (move up / move down), because a reorder-only-by-mouse control is unusable for some photographers and trivially avoidable here.
- **Images are uploaded through the existing presigned flow** (1A.3), with per-file progress and a clear scanning state — the same treatment 1D.3 gives documents, for the same reason.
- **Products and tiers carry money, so the client never computes it.** Prices are entered in whole currency units, sent as integer cents, and every displayed total comes from the API. Currency comes from the profile's country.
- **The quotes inbox is the photographer's side of 1B.5**, which already shipped the client's side. Same error mapping (409 / 422 / 429), same confirmation discipline. Sending a quote is where a photographer commits to a price, so the line items and the total are restated in a confirmation before it sends — a mistyped price here is a real financial loss for them, and `Booking.feePercent` snapshots at acceptance.
- **Withdrawing a quote is confirmed and explains its effect** (`POST /v1/quotes/{id}/withdraw`), because the client may already be looking at it.
- **The dashboard is `noindex` and dynamic throughout.** It is private, per-user, and must never be cached or crawled.
- **Verification uploads are the most sensitive thing a photographer sends us.** 1B.8c reuses 1A.9's rules: upload, then submit deliberately; the required documents come from `GET /v1/countries/{code}/verification-requirements`, never a hardcoded list, because they differ per country and `Country.requiredDocuments` is the source of truth. A submitted case is read-only — the UI shows its state and the rejection reason rather than offering an edit the API would refuse.

## Tasks

1. **1B.8a** — `/{locale}/dashboard` shell and nav, the checklist home, and the profile editor (`GET`/`PATCH /v1/me/photographer-profile`): display name, bio, languages, categories, location, slug rules surfaced as validation rather than a silent server rejection.
2. **1B.8b** — portfolio grid with upload, delete, reorder (mouse **and** keyboard), scan state; products and tiers CRUD (`/v1/me/products`).
3. **1B.8c** — verification: requirements per country, document upload, submit, and the case state with its reason.
4. **1B.8d** — quotes inbox: incoming requests, `POST /v1/quotes` with line items, `GET /v1/quotes/mine?role=photographer`, withdraw.
5. i18n under `web.dashboard.*`, `en` source of truth; i18n-maintainer drafts the rest.
6. Tests per sub-step, including: the checklist reports publication state without implying it can publish; a blocked Stripe row renders as unavailable rather than vanishing; reorder works from the keyboard; cents conversion on product prices; sending a quote requires confirmation and never sends a client-computed total; a rejected verification case shows its reason and offers no edit.

## Human follow-ups

- **1B.8e and 1B.8f wait on O2** — the operating entity and the Stripe platform account, already tracked in this file as the biggest schedule risk. They are the *only* parts of this step that wait, which is worth knowing when deciding how urgent O2 is: it holds back a photographer's ability to get paid, not their ability to set up a profile.
- **Provenance vendor choice (1A.10)** determines what, if anything, a photographer eventually sees about their own images. Until then 1B.8b deliberately shows nothing.
