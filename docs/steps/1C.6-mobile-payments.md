# Step 1C.6 – Mobile payments and bookings

Plan reference: `docs/PLAN.md` step 1C.6: "Payments: Stripe React Native PaymentSheet with Apple Pay/Google Pay, booking screens, delivery acceptance". Owner: mobile-developer. payments-engineer reviews 1C.6b, 1C.6c and 1C.6d. security-reviewer runs its 1E.6 checkpoint after 1C.6b. Blocked by 1C.4 (merged) and 1A.8 (merged).

The web equivalent is `docs/steps/1B.7-checkout.md`, and 1B.7a and 1B.7b are merged. The server side is `docs/steps/1A.8-payments.md` and `docs/PAYMENTS.md`. **The decisions are ported, not redesigned**:

- The client secret comes from `POST /v1/bookings/{id}/payment-intent`.
- The app never marks a booking paid. Only the webhook moves it to `paid_held`, and the app re-reads the booking.
- No amount is computed on the device. Totals, refunds and payouts are shown as the API returns them.
- The status-to-action mapping is `apps/web/src/components/requests/booking-status-actions.ts`.
- Actions run with the 1C.4 mutation pattern: confirm, in-flight guard, i18n error mapping for 409, 422 and 429.
- The photographer sees no payout figure; the fee invoice is the source.
- `platformFee` is not shown to the client.

No contract change is planned. Every endpoint used below already exists in `packages/shared/src/contract/bookings.ts` and `payments.ts`. This document only covers what a native app answers differently.

## Decisions

- **Dependency.**
  - `@stripe/stripe-react-native` is added with `pnpm --filter @photoo/mobile exec expo install @stripe/stripe-react-native`. SDK 57's `bundledNativeModules.json` pins it to `0.64.0`. It stays on whatever `expo install` resolves, not a hand-picked version.
  - The config plugin goes into `app.config.ts` as `['@stripe/stripe-react-native', { merchantIdentifier, enableGooglePay: true }]`.
  - `merchantIdentifier` is read at build time from `EXPO_PUBLIC_STRIPE_MERCHANT_IDENTIFIER`, the same way `EAS_PROJECT_ID` is read. When it is unset, it is omitted.
  - A native module and a plugin change mean a new development build. Expo Go cannot show Apple Pay.
- **Env** (`src/lib/env.ts`, `.env.example`).
  - `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY` is optional and must match `pk_test_…`. A `pk_live_…` key fails env validation loudly until a launch decision allows it.
  - `EXPO_PUBLIC_STRIPE_MERCHANT_IDENTIFIER` is optional and must match `merchant.…`.
  - Both are baked into the build, so for EAS builds they live in the EAS environment.
- **Unset key is a state, not a crash.**
  - Without the publishable key, the pay panel shows "Payment is not available in this environment". `StripeProvider` is not mounted, and `payment-intent` is not called.
  - This is the normal case in local dev and CI, where the API runs `STRIPE_FAKE`. The fake's `…_secret_fake` can't initialise a PaymentSheet, so there is no pretend payment on the device either, same as the web.
  - When the key is set but the API runs the fake, `initPaymentSheet` fails and renders as the error state.
- **Where Stripe is mounted.**
  - `StripeProvider` wraps the pay panel only, not the root layout. A cold start never initialises the Stripe SDK, and a client-only booking screen without a pending payment never loads it.
  - Props: `publishableKey`, `merchantIdentifier` when set, and `urlScheme` = `photoo` (from `app.config.ts`).
- **Flow (1C.6b).**
  1. Quote accept already creates the booking in the same transaction (1A.8c). `POST /v1/quotes/{id}/accept` returns `bookingId`. 1C.6a sends the client to `/bookings/{bookingId}` instead of 1C.4's "payment arrives soon" notice. If `bookingId` is null, the notice links to the bookings list.
  2. On a `pending_payment` booking, the pay panel calls `POST /v1/bookings/{id}/payment-intent` when it mounts and gets `{ clientSecret, amount }`.
     - The secret lives in component state for that booking only. It is never persisted, logged, or attached to a Sentry event or breadcrumb.
     - A 409 means the booking has moved on, so the panel re-reads the booking.
  3. Before init, `retrievePaymentIntent(clientSecret)` runs. A status of `processing`, `succeeded` or `requires_capture` goes straight to the processing state. This is the web's return check: the PaymentIntent can be paid while the webhook hasn't landed yet, and a PaymentSheet on a succeeded PaymentIntent fails.
  4. `initPaymentSheet` gets:
     - `paymentIntentClientSecret`;
     - `merchantDisplayName: 'Photoo'`;
     - `returnURL: Linking.createURL('stripe-redirect')`, which is `photoo://stripe-redirect` in builds;
     - `applePay: { merchantCountryCode }`, only when the merchant identifier is set;
     - `googlePay: { merchantCountryCode, testEnv: true }`;
     - `allowsDelayedPaymentMethods: false`.

     `merchantCountryCode` is the platform Stripe account's country, not the buyer's. It is one constant (`LU`) next to the Stripe setup, tied to O2, not a per-country branch.
  5. `presentPaymentSheet` results:
     - `Canceled` returns to ready with no error.
     - `Failed` shows Stripe's localised message, or `mobile.bookings.pay.failed` if there is none.
     - No error means the processing state, not success.
  6. Processing polls `GET /v1/bookings/{id}` with the web's back-off (2, 4, 8, 16 and 32 s). It also re-reads when the screen regains focus or the app becomes active (`use-screen-visible.ts`).
     - Any status other than `pending_payment` ends the poll and renders that status.
     - Running out of attempts shows "still processing" with a refresh button.
     - The screen says "paid" only when the API returns `paid_held`.
- **3-D Secure and bank redirects.**
  - Most 3-D Secure challenges stay inside the sheet. Bank-app redirects come back on `photoo://stripe-redirect`.
  - `app/+native-intent.tsx` `redirectSystemPath` hands any `stripe-redirect` URL to Stripe's `handleURLCallback` and returns `null`, so expo-router stays on the booking screen instead of hitting `+not-found`. Every other path passes through unchanged.
  - It catches its own errors, because an error thrown there crashes the app (expo-router docs).
- **Double submission is impossible.**
  - The pay button is disabled from tap until `presentPaymentSheet` resolves, with an in-flight ref as in `QuoteActions`.
  - Server-side, the PaymentIntent is idempotent per booking (`booking_<id>_pi`), and the booking row is locked.
- **No saved cards.** The API returns no Customer or ephemeral key. PaymentSheet runs without a customer, so every payment enters its card or wallet afresh. Saving cards would be a contract change (Customer and ephemeral key on the payment-intent response), and it is not part of this step.
- **Booking screens (1C.6a).**
  - Client screens: `app/bookings/index.tsx` and `app/bookings/[id].tsx`, entered from the Requests tab next to "Quotes received".
  - Photographer screens: `app/studio/bookings/index.tsx` and `app/studio/bookings/[id].tsx`, entered from Studio.
  - `GET /v1/bookings` returns both roles mixed. Like the web, each list filters client-side, on `clientId === user.id` or on `photographerId ===` the own profile id from `use-own-photographer-profile`. Each list uses `use-cursor-list`. #523 tracks the server-side role filter.
  - On the client route, a booking whose `clientId` is not the user renders as not found, as on the web.
  - The status badge and timeline come from `BOOKING_STATUSES`:
    - the main path is `pending_payment → paid_held → in_progress → delivered → released`;
    - the side exits are `cancelled`, `refunded` and `disputed`.
  - `disputed` shows an explanation and no actions. Disputes come from Stripe chargebacks, and the web offers no client-side dispute action either.
  - The detail shows `releaseDueAt` on `delivered`, so the client knows when payment releases automatically.
  - `booking-status-actions.ts` is ported to `src/lib/booking-status.ts` together with its tests.
- **Delivery (1C.6c).**
  - Photographer, in `paid_held` and `in_progress`: `POST /v1/bookings/{id}/delivery` with a message and `externalLink`. File delivery (`fileIds`) is out of scope, as on the web.
  - Client, in `delivered`: `POST /v1/bookings/{id}/accept-delivery` behind a confirm that says accepting releases the payment to the photographer.
  - Release, ledger and `AuditLog` all happen server-side in `BookingReleaseService`. The app re-renders the returned booking.
  - #526: the booking API does not expose the delivery message or link, so the client accepts without seeing them in the app. The web has the same gap. The confirm text tells the client to check the link the photographer sent in chat.
- **Refund, cancel and documents (1C.6d).**
  - The refund is requested in `paid_held`, `in_progress` and `delivered`, full or partial, with a reason.
    - The amount text goes through the existing `toAmountCents` (`src/lib/product-form.ts`, moved to `src/lib/money.ts` if a second caller makes that cleaner).
    - The server is the authority: a 422 means an over-refund, and a 409 `BOOKING_BUSY` asks the client to retry.
  - Cancel is offered on `pending_payment` only, with an optional reason.
  - Documents, only on `released`: the receipt for the client and the fee invoice for the photographer.
    - The presigned URL is fetched on tap, checked with `isHttpsUrl`, and opened with `expo-web-browser`.
    - A 409 shows "document is being prepared".
- All user-facing text goes under `mobile.bookings.*` and `mobile.studio.bookings.*` in `packages/i18n/messages/en.json`. Every screen handles loading, empty, error and 401.

## API gaps

None block this step. Both are already tracked:

- #523: no role filter on `GET /v1/bookings`, and no `bookingId` on `GET /v1/quotes/{id}`. An accepted quote opened later links to the bookings list rather than its booking.
- #526: the booking does not carry the delivery content.

There is also no booking deep link in push payloads; `notification-links.ts` maps conversations only. A payment-confirmed push therefore opens the app without routing, and the screen's focus re-read covers it.

## Verification

- jest-expo tests with `@stripe/stripe-react-native` mocked. CI runs against the fake gateway and never reaches Stripe. Tests cover:
  - the status-to-action mapping for every status;
  - the client list hiding bookings where the user is the photographer, and the reverse;
  - quote accept navigating to `/bookings/{bookingId}`, and the null fallback;
  - no key → the unavailable state, with neither `StripeProvider` nor `payment-intent` reached;
  - a `pk_live_` key rejected by env validation;
  - `presentPaymentSheet` success → processing and polling, never "paid" until a mocked `GET` returns `paid_held`;
  - `Canceled` → no error, and `Failed` → error;
  - a `succeeded` PaymentIntent on mount → processing without init;
  - a second tap while in flight → one `payment-intent` call and one `presentPaymentSheet` call;
  - `returnURL` = `photoo://stripe-redirect`;
  - `redirectSystemPath` passing a stripe URL to `handleURLCallback` and returning `null`, and leaving other paths untouched;
  - the accept-delivery confirm;
  - refund amount parsing (more than two decimals and zero rejected) and the 422 / `BOOKING_BUSY` mapping;
  - a non-https document URL refused.
- `pnpm --filter @photoo/mobile typecheck`, `lint` and `test` pass, with the coverage thresholds held.
- These can't be verified without Stripe test keys and a development build on a device, so 1C.6b stays "code done; device check pending" until they are run:
  - the PaymentSheet rendering;
  - a 3-D Secure test card (`4000 0027 6000 3184`) through the challenge and back;
  - a bank redirect returning through `photoo://stripe-redirect`;
  - Google Pay in test mode on an Android device with a Google account;
  - Apple Pay, which also needs the merchant ID;
  - `paid_held` arriving after a real signed webhook.

  These pair with the 1A.8 live checklist and the 1C.4/1C.5 device sitting in `human-followups.md`. 1C.10 automates the test-mode payment with Maestro.
