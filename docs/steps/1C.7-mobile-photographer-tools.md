## Decisions

- **Which screens exist depends on `user.roles`, which the session already returns.**
  - A user with `photographer` sees a "Studio" entry on the account tab. Studio is a stack of screens, not a new tab. The tab bar stays the same for every role, so a client-only user never sees an empty tab.
  - A client without the role is not offered the role switch in this step. `POST /v1/auth/roles` exists, but becoming a photographer stays a web flow until a product decision says otherwise.
  - The API enforces the role on every call. The client gate is presentation only.
- **One upload helper, parameterised by purpose.**
  - `src/lib/chat-attachments.ts` already does prepare, presigned PUT with progress, complete, then scan polling with `isScanningError`. It is generalised to take the purpose and its limits from `UPLOAD_PURPOSE_LIMITS`. It is not copied.
  - Chat behaviour must not change, and its tests are the regression net.
- **Portfolio images are not shrunk to chat size.**
  - Chat resizes to a 2048 px edge. A portfolio image is the photographer's work, and provenance analysis (EXIF, C2PA, reverse search) runs on the original.
  - Portfolio uploads therefore go up as picked, within the 25 MB limit. Re-encoding would strip the C2PA and EXIF evidence the provenance pipeline relies on.
  - Location data in a portfolio original is the photographer's choice and is already handled server-side: the worker's sharp derivatives (`apps/worker/src/processing/image-processor.ts`) do not carry metadata over. The pre-upload screen says so in one line.
  - This is the opposite of chat (#578), and the difference is deliberate.
- **Verification documents are re-encoded like chat images.** An ID photo needs no provenance evidence, and its GPS position is personal data that nobody reviewing the document needs. PDFs go up unchanged.
- **Stripe onboarding opens in an in-app browser, and the return is a status re-read, not a deep link.**
  - `STRIPE_CONNECT_RETURN_URL` and `STRIPE_CONNECT_REFRESH_URL` are fixed per environment and point at the web payouts page. A client-supplied return URL would be an open-redirect surface on a money flow.
  - The app opens the account link with `expo-web-browser` (`openBrowserAsync`, a new dependency added via `expo install`). When the browser closes, the app re-reads `GET /v1/me/photographer-profile`.
  - Only the `account.updated` webhook marks onboarding complete, so an immediate re-read may still show "incomplete". The screen says that verification can take a moment and offers a refresh. It never shows a success that the server has not confirmed.
  - The link URL must be https before it is opened, as on the web. `EMAIL_NOT_VERIFIED` and the 409 for "no account yet" render as states.
- **Quotes reuse the 1C.4 screens where the shape matches.**
  - `quotes/index.tsx` and `quotes/[id].tsx` are client views. The photographer's incoming requests (`GET /v1/requests`) and sent quotes (`GET /v1/quotes/mine`) get their own Studio screens.
  - Sending uses `POST /v1/quotes/preview` to show the fee and net amount before `POST /v1/quotes`. Fee maths is never done on the device.
  - Withdrawing uses `POST /v1/quotes/{id}/withdraw` behind a confirm.
- **Money input is integer cents.** Price fields parse a decimal string to cents the way the web's `toAmountCents` (`apps/web/src/app/[locale]/dashboard/products/product-form-helpers.ts:111`) does, ported with its tests, and reject more than two decimals. A float never reaches the request body.

## Tasks

1. **1C.7a**
   - The Studio entry and stack, gated on `roles`.
   - Profile view and edit (`GET/PATCH /v1/me/photographer-profile`).
   - Portfolio list, upload from the library with per-file progress and status badges, reorder, and delete with confirm.
   - Generalise the upload helper.
2. **1C.7b**
   - Product list, create, edit and delete with tiers.
   - The duplicate-usage rule ported from `product-form-helpers`.
3. **1C.7c**
   - Per-country requirement slots.
   - Camera, library or file capture per slot.
   - Case status, and submit.
4. **1C.7d**
   - Incoming requests, a send-quote form with the server preview, the sent-quotes list, and withdraw.
5. **1C.7e**
   - Payouts screen with the three states, account creation, the account link in an in-app browser, and a re-read on close.
   - Payments-engineer review.

All user-facing text goes under `mobile.studio.*` in `packages/i18n/messages/en.json`. Every screen handles loading, empty, error and 401.
