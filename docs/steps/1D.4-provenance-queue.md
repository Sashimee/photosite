## What the API gives us

On the `moderation` permission (no fresh-2FA requirement):

- `GET /v1/admin/provenance` — keyset, oldest first, filterable by `verdict` (`pass`, `review`, `fail`) and `status` (portfolio image status). Summary rows carry the public thumbnail, photographer `displayName`/`slug`, verdict, score, checked/reviewed timestamps.
- `GET /v1/admin/provenance/{id}` — adds the signals: `aiScore`, `aiVendor`, `reverseMatches` (URLs), `c2paValid`, `exifCamera`, `exifCapturedAt`, the reviewer, the internal `note` and the photographer-facing `decisionReason`/`decisionReasonText`.
- `POST /v1/admin/provenance/{id}/decision` — `{ status: approved | flagged | rejected, note, decisionReason?, decisionReasonText? }`. `note` is always required and admin-internal. `decisionReason` is required for flag/reject and forbidden for approve; `decisionReasonText` is required when the reason is `other`.
- `POST /v1/admin/provenance/{id}/recheck` — re-runs the pipeline (`409` while one is running).

## Decisions for this step

- **The queue defaults to `status=pending_review`, oldest first.** Same reasoning as 1D.3: newest-first starves the photographer who has waited longest. Filters for verdict and status sit beside it.
- **Two notes, two audiences, labelled as such.** The internal note ("only admins see this") and the statement of reasons ("shown to the photographer", DSA Art. 17) are separate fields with explicit labels, so a reviewer never writes evidence links into the text the photographer reads.
- **Reverse-match URLs are third-party pages and render as plain text with a copy button, not as links.** Clicking an unknown URL from a privileged admin session leaks the admin origin via `Referer` and opens attacker-chosen content. If they are ever made clickable it is `rel="noopener noreferrer"` with `referrerPolicy="no-referrer"`; this step keeps them as text.
- **Missing signals are a state, not an error.** With null vendors `aiScore`, `aiVendor` and `reverseMatches` are `null`; the detail shows "not checked (no vendor configured)" rather than `0` or a blank.
- **Bulk actions are client-side loops over the single-item decision endpoint**, limited to approve and reject, with one shared note/reason applied to every selected row. There is no bulk endpoint and this step does not add one: each decision stays individually audited by the API. Requests run sequentially, the dialog reports per-row success/failure, and a failed row stays selected. Bulk flag is left out — flagging is a per-image judgement.
- **Recheck is offered on the detail page only**, disabled while a recheck is in flight, and a `409` says "already running".
- **Thumbnails only.** The queue and detail use the public `thumbnailUrl` the API returns; this step never fetches the original.
- **No score maths in the UI.** Scores are displayed as returned (as a percentage); the verdict comes from the API, never recomputed.

## Tasks

1. `app/(admin)/provenance/page.tsx` — `DataTable` with thumbnail, photographer, verdict, score, checked-at, row selection, verdict/status filters, default `pending_review` oldest-first, keyset paging.
2. `app/(admin)/provenance/[id]/page.tsx` — larger thumbnail, photographer link, every signal with its null state, reverse matches as copyable text, decision history from the audit log (`targetId={checkId}`) if the existing audit query supports it, the decision form and the recheck button.
3. Decision dialog: status, internal note (required), reason category (required for flag/reject, hidden for approve), reason text (required for `other`), labels naming who sees each field. Mirrors `ProvenanceDecisionRequestSchema` by validating with it.
4. Bulk approve/reject dialog over the selection, sequential, with a per-row result list.
5. Navigation entry in the admin shell, behind the `moderation` permission like the existing moderation entry.
6. i18n under `admin.provenance.*`, English only (admin is en-only).
7. Tests:
   - the queue requests `status=pending_review` by default and keeps oldest-first;
   - approve sends no `decisionReason`; reject without a reason is blocked client-side;
   - `other` requires reason text;
   - null `aiScore`/`reverseMatches` render the "not checked" state;
   - reverse matches render as text, not `<a href>`;
   - bulk reject applies the same note/reason to each selected id, reports a failed row and keeps it selected;
   - recheck `409` shows "already running";
   - one test renders against the real `en` catalog.
