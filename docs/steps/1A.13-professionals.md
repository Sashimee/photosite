## Decisions for this step

- **`Listing` exists from day one and is always `plan: 'free'`.** Every published `JobOffer` gets a `Listing` row, even though nothing is charged. Phase 3 (`docs/PLAN.md` 3.2) then only adds plans, a price and a Stripe Checkout session — it never has to backfill listings for offers published in Phase 1, which is the whole point of D8.
  - `Listing.priceCents` is 0 and `paidAt` is set at creation for a free plan, so "is this listing live" is one predicate (`expiresAt > now`) rather than a plan-dependent branch.
  - The API refuses to create a listing with any plan other than `free` in Phase 1, in the service and not only in the schema, so switching it on later is a deliberate change.
- **A job offer's lifecycle is the listing's lifecycle.** `published` while its listing is unexpired, `expired` when the listing lapses, `closed` when the professional closes it, `draft` before first publish. Publishing sets `publishedAt`, creates the listing and sets `expiresAt = now + 60 days` (the same window as `Request`, so the platform has one "stale content" rule rather than two). Re-publishing an expired offer creates a **new** listing rather than extending the old one, because in Phase 3 that is the moment money would change hands.
- **Applications are photographer-only and one per offer.**
  - `POST /v1/job-offers/{id}/applications` requires the `photographer` role and a published offer, and a unique index on `(jobOfferId, photographerId)` makes a double application a 409 rather than a duplicate row.
  - `JobApplication.status` is `submitted`, `shortlisted`, `rejected`, `withdrawn`. The professional moves it forward; the photographer may only withdraw. No hiring or payment flow exists in Phase 1 — a professional who wants to hire goes through the normal request/quote path, and that is stated in the plan rather than half-built here.
  - `portfolioLink` is a URL the photographer supplies; it is validated as `https` and normalised, and it is rendered as a link with `rel="nofollow noopener"` by the web app (noted for 1B.9, not enforceable in the API).
- **The professional profile is not a photographer profile.** `ProfessionalProfile` is company data (`companyName`, `website`, `vatNumber`, `logoUploadId`, `verified`), 1:1 with the user, created by `POST /v1/me/professional-profile` which also adds the `professional` role to the account (D13: one account, more roles).
  - `verified` is a manual admin flag with no self-service path in this step; it is displayed on the public job board as a badge and nothing more. The real verification machinery (1A.9) is photographer-specific and is not reused here — a business-document flow for professionals is a Phase 2 question, recorded as a follow-up.
  - `vatNumber` is stored as given and never used for tax logic in Phase 1. No VIES lookup, because nothing depends on it yet.
  - `logoUploadId` reuses the existing `Upload` flow (`purpose: 'logo'` added to `UPLOAD_PURPOSES`), so scanning, variants and the private/public split all come for free rather than being reinvented.
- **Public endpoints are genuinely public and cheap to cache.**
  - `GET /v1/job-offers` (keyset by `publishedAt desc, id`, filters: category, country, city, `remote`, and a free-text match on title) and `GET /v1/job-offers/{slug}` return only published, unexpired offers with the company name, logo and `verified` badge — never the professional's email, phone or VAT number.
  - A slug (`title` slugified plus a short suffix) rather than a raw id in the public URL, because 1B.11 puts these pages in the sitemap and an id-shaped URL is a worse landing page. Slug rules follow the existing `SlugSchema` in `packages/shared`.
  - Location filtering reuses the `City`/PostGIS work from 1A.4/1B.4a — the same city lookup, not a second free-text city column. `remote: true` offers match every location filter. **Deviation (D24, issue #274):** 1A.13b's `city` filter shipped as case-insensitive exact text (`lower(jo.city) = lower($1)`), the same shape `ProfilesRepository.search`'s `city` filter already uses, not a `City`/PostGIS radius lookup — there is no canonical `City` table in this codebase, only the grouped-by-name `cities` endpoint (1B.4a). Coordinates are still stored and exposed (coarsened) for a future radius filter; see D24 for why this was deferred rather than built in the fix-up PR that found it.
- **Rate limits and abuse.** Creating a draft is limited to 20 a day per account, publishing to 10 a day per account, and applications to 30 a day per photographer, all through `RedisRateLimiter`. A free job board is a spam target, and the limits are the only defence in Phase 1 — moderation (`Report`, DSA notice-and-action) is 1A.11's queue, and this step just makes sure a `JobOffer` is reportable by id. A limiter is consumed only after the request is known to be a valid, existing, owned or open target — never before — so probing dead ids can't lock a legitimate caller out of their own daily budget.
- **Notifications.** New types `job_application_received` (professional) and `job_application_status_changed` (photographer) on the existing 1A.7 machinery — the `NOTIFICATION_TYPES` enum grows, the DB column is already a `String`, so no migration. Payloads carry ids, the offer title and the counterpart display name only.
- **Expiry is a repeatable job, not a read-time filter.** `listing-expiry` (repeatable, hourly) flips offers whose listing lapsed to `expired` and notifies the professional once. Public reads still filter on `expiresAt` so a lagging job never leaks a stale offer, but the status in the database is kept true, because 1B.9's dashboard and the Phase 3 renewal flow both read it.
- **GDPR.** `JobApplication` and `ProfessionalProfile` join the 1A.12 export collectors and the anonymisation sweep: an application's message is the subject's own data, a closed offer's rows are kept only as long as the offer. This file lists them so 1A.12b does not have to rediscover the entities, and 1A.12's plan is updated in the same PR if it merges first.

## 1A.13a tasks

1. **Contract** (`packages/shared/src/contract/professionals.ts` and `job-board.ts`): professional profile create/read/update, job offer CRUD plus publish and close, application create/list/status, and the public list and detail schemas with error responses; `JOB_OFFER_STATUSES`, `JOB_APPLICATION_STATUSES`, `LISTING_KINDS` and `LISTING_PLANS` enums; `logo` added to `UPLOAD_PURPOSES`; the two new notification types; a `ListingExpiryJobSchema` and `listing-expiry` in `packages/shared/src/queues.ts`; regenerate `openapi.json` and the api-client; add the routes to `not-yet-implemented.ts`.
2. **Schema** (schema-migrator, `docs/DATA-MODEL.md` first): the four models as above, with `JobOffer.slug` unique, a unique `(jobOfferId, photographerId)` on applications, an index on `(status, publishedAt)` and one on `(countryCode, city)` for the public list, `Listing.expiresAt` indexed for the sweep, and cascade rules that keep an application when its offer is closed but remove it with the offer's hard deletion; migration via `migrate diff` applied to `photoo` and `photoo_test`; seed gains one professional with a published offer so the preview and 1B.9 have something to render.

## 1A.13b tasks

1. **API** (`apps/api/src/modules/professionals/` and `job-board/`): the routes above, `requireSession` on everything owner-facing and genuinely anonymous access on the two public reads, OriginGuard on mutations, role checks (`professional` to post, `photographer` to apply), the rate limits, and `AuditLog` on the `verified` flag only (it is an admin action; ordinary CRUD is not audited).
2. **Worker**: the `listing-expiry` processor and its notification.
3. **Tests**:
   - a non-professional cannot create an offer and a non-photographer cannot apply (403 each);
   - a second application is 409;
   - a draft offer is invisible on the public endpoints and 404 by slug;
   - an expired offer disappears from the public list before the sweep has run;
   - re-publishing creates a second listing rather than extending the first;
   - the public payload contains no professional email, phone or VAT number (assert on the serialised body);
   - the rate limits return 429 with `Retry-After`;
   - keyset pagination has no gaps or repeats and a malformed cursor is 400;
   - the sweep expires only lapsed listings and notifies once, and is idempotent across two runs;
   - `plan` other than `free` is refused.
