## Decisions for this step

- **Who creates which quote.** Photographers quote on a client `Request`, sending line items they set themselves. A *direct quote* from a `Product` and `ProductTier` is started by the **client**. The server builds it from the tier price with a single line item (`label` = product title in the client locale, `qty` 1, `unitCents` = `tier.priceCents`), so clients never send prices (SECURITY: amounts recomputed server-side). The current `POST /v1/quotes` mixes both paths and would accept client prices. It is split:
  - `POST /v1/quotes` (photographer role): `{ requestId, lineItems, validUntil, message? }`.
  - `POST /v1/photographers/{slug}/products/{productId}/quotes` (any signed-in user): `{ productTierId, message? }`. It is created as `sent` with `validUntil` = now + 7 days and `clientId` = caller.
- **Fee and totals.** `subtotalCents`, `platformFeeCents` and `totalCents` come only from `quoteTotals` in `packages/shared`, using `feePercent` read from `PlatformSetting` when the quote is created. The quote stores all three values, so later fee changes don't rewrite sent quotes.
- **Licence snapshot.** Product tiers are hard-replaced on product update (1A.4b), so a quote stores `licenceUsage` (from the request `usage` or the tier) and `licenceTextVersion` (tier only) at creation. `productTierId` may later become null; the snapshot is what the booking and licence use. `Quote.requestId` is `Restrict` on delete (requests are soft-deleted), and a CHECK requires `requestId` or `productId`.
- **Money limits.** Currency is the photographer profile country's currency. On a request quote it must also equal the request currency (422 otherwise). Line items are capped at 1–50, `qty` 1–1000 and `unitCents` ≤ 99 999 999, and `totalCents` ≤ 99 999 999 (the Stripe single-charge limit). A zero total gives 422.
- **Quoting eligibility.** A photographer needs a published, non-deleted profile to send quotes, and a direct quote needs a published profile plus an active product. Real profiles only become published after 1A.8/1A.9, so tests use fixture profiles. No shortcut in code. Users cannot quote on their own request or request a direct quote from their own profile (422). There is at most one `sent` quote per photographer per request (409).
- **State machines** (enforced in one service, with transitions done as conditional `updateMany` on the expected current status so concurrent calls can't both win):
  - Request: `open → quoted` (first sent quote), `open|quoted → booked` (quote accepted), `open|quoted → cancelled` (client), `open|quoted → closed` (expired by job). `booked`, `cancelled` and `closed` are terminal in 1A.5; 1A.8 may reopen on payment failure.
  - Quote: `sent → accepted` (client, before `validUntil`), `sent → declined` (client), `sent → withdrawn` (photographer), `sent → expired` (job, or rejected at accept time if past `validUntil`). `draft` is not exposed through the API in the MVP.
  - Accepting a request quote declines all other `sent` quotes on that request in the same transaction. Cancelling a request declines its `sent` quotes.
  - Accept is the hand-off point for 1A.8, which creates the `Booking` and PaymentIntent in the same transaction. 1A.5 only records `accepted`.
- **Request expiry.** `expiresAt` = the earlier of `eventDate` and `createdAt + 60 days`. A BullMQ repeatable job `quote-expiry` in the worker runs every 15 minutes: it marks `sent` quotes past `validUntil` as `expired` and `open|quoted` requests past `expiresAt` as `closed`. Reads don't wait for the job: accept re-checks `validUntil`.
- **Location privacy.** The exact request `location` and `address` are visible only to the client who owns the request (and later to the booked photographer, 1A.8). Photographers browsing requests get the city, country and a location snapped to 0.01° (same rule as profile search). This adds a `RequestSummarySchema` for the photographer view.
- **Photographer request feed.** `GET /v1/requests` (photographer role) lists `open|quoted`, non-expired, non-deleted requests. It matches one of the profile's categories within `radiusKm` (integer 1–200, default 50) of the profile location. Ordering is `createdAt desc, id` with a keyset cursor, and each item carries `hasQuoted`. Everything is parameterised `$queryRaw`.
- **Listings.** `GET /v1/quotes/mine?role=photographer|client` (default `photographer` when the caller has the role, otherwise `client`). `GET /v1/quotes/{id}` lets either party read it; anyone else gets 404. `GET /v1/requests/{requestId}/quotes` is for the owning client.
- **AuditLog.** Quote creation, accept, decline and withdraw write `AuditLog`, since each commits or releases a money amount (convention). The request cancel is logged too. Automatic expiry writes a single system-actor row per job run with counts, not one per quote.
- **Rate limits** (shared `RedisRateLimiter`, per account): request creation 10/hour, quote creation 30/hour, direct quotes 10/hour.
- **Not in 1A.5.** Chat conversations for requests and quotes (1A.6), email or push on new quote and accept (1A.7, which adds an event hook; leave a single `QuoteEvents` interface with a no-op implementation), `Booking` (1A.8).

## 1A.5a tasks

1. **Contract** (`packages/shared/src/contract/requests.ts`, `quotes.ts`), contract first:
   - Split quote creation as above. The request-quote body loses `productId` and `productTierId`, and `exactlyOneQuoteTarget` goes away. Add the direct-quote route with `DirectQuoteRequestSchema`.
   - Add `LineItemSchema` caps (`qty` max 1000, `unitCents` max 99 999 999) and `lineItems` max 50.
   - Add `GET /v1/requests` (feed, `RequestSummarySchema` with `city`, `countryCode`, coarse `location`, `hasQuoted`, no address), `GET /v1/quotes/{id}`, and a `role` query on `/quotes/mine`.
   - Error responses: 403 missing role, 404, 409 state conflicts, 422 business rules, 429.
   - Regenerate openapi and the api-client. New routes go into `not-yet-implemented.ts` until 1A.5b. Contract tests cover the split and the caps.
2. **Schema** (schema-migrator, DATA-MODEL first):
   - `Request` per DATA-MODEL: `location` as `Unsupported("geography(Point, 4326)")` with a GiST index, `address` JSON, `city` and `countryCode` columns copied from the address for the feed filter, a `RequestStatus` enum, and `expiresAt` and `deletedAt`. Indexes: `(clientId, createdAt)`, plus a partial index on `(status, expiresAt)` where `deletedAt` is null.
   - `Quote` per DATA-MODEL with a `QuoteStatus` enum, relations to `Request?`, `PhotographerProfile` (`photographerId` references the profile), `User` (client), `Product?` and `ProductTier?`, plus `feePercent` stored as a snapshot. A partial unique index on `(requestId, photographerId)` where `status = 'sent'` backs the one-sent-quote rule. Indexes: `(clientId, createdAt)`, `(photographerId, createdAt)`, and `(status, validUntil)`.
   - Check constraints in migration SQL: `subtotalCents >= 0`, `platformFeeCents >= 0`, `totalCents = subtotalCents`, `budgetMinCents <= budgetMaxCents`.
   - Update DATA-MODEL for the added columns (`city`, `countryCode`, `feePercent`) and note that `photographerId` on `Quote` references `PhotographerProfile`.
3. **Seed.** One open request in Luxembourg City from the seeded client and one sent quote from a seeded photographer, idempotently. The production guard stays in place.
4. **Tests.** The migration applies to a fresh test DB, and the seed runs twice without duplicates. The partial unique index rejects a second `sent` quote and allows one after withdraw. Check constraints reject bad totals.

## 1A.5b tasks

1. **`RequestsModule`:** create (currency equals the address country's currency, `countryCode` must be an enabled `Country`, `eventDate` in the future), mine, get (owner gets the full record; a photographer with a sent quote gets the summary; otherwise 404), cancel, and the feed.
2. **`QuotesModule`:** create on a request, direct quote from a product, mine, get, list for a request, accept, decline and withdraw, following the state machine and conditional updates above. Money goes through `quoteTotals` only. There is a `QuoteEvents` no-op hook.
3. **Worker:** the `quote-expiry` repeatable job (queue name constant in `packages/shared/src/queues.ts`) and its processor, with an idempotent registration on worker start.
4. **Access:** `requireSession` everywhere, `requireRole('photographer')` on request quotes and the feed, `OriginGuard` on mutations, `ZodValidationPipe` on body, query and params, and rate limits as above.
5. **Tests** (integration against the stack):
   - totals and fee match `quoteTotals` for several line-item sets, including rounding at 0.5 cents; the client cannot influence the direct-quote price (extra keys give 400);
   - currency mismatch, zero total and over-cap values give 422;
   - own request and own product give 422; an unpublished photographer gets 403;
   - a second sent quote gives 409, and one is allowed again after withdraw;
   - accept: only the client, not after `validUntil`, other sent quotes declined, request `booked`; two concurrent accepts on different quotes of the same request leave exactly one winner;
   - decline, withdraw and cancel transitions, with 409 on terminal states;
   - privacy: the feed and non-owner reads never contain `address` or unrounded coordinates; a third party gets 404 on request and quote reads;
   - the feed filters by category and radius, pagination is stable, and SQL injection in the cursor is treated as data;
   - the expiry job marks expired quotes and closes requests, and runs twice idempotently;
   - AuditLog rows are written; routes are removed from `not-yet-implemented.ts`; coverage thresholds hold.
6. **Security checkpoint (1E.6)** before merge. Focus: price tampering, the state-machine races, IDOR on request and quote reads, and location leakage.
7. **Manual check:** against the seeded stack, curl creating a request as the seeded client, the feed as a seeded photographer, quote, then accept.
