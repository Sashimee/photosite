## Decisions for this step

- **One export at a time, one a day.** `POST /v1/me/data-requests` with `{ type: 'export' }` returns the existing row when one is already `pending` or `processing` (200, not a second row), and is limited to one completed export per 24 hours per account through `RedisRateLimiter` (`apps/api/src/common/rate-limit/redis-rate-limiter.ts`). Building a full archive is expensive and an unlimited endpoint is a free amplification primitive.
- **The export is a zip in the private bucket, never a public object.**
  - The worker streams it: `archiver` -> S3 multipart upload, one entity at a time, so a photographer with a large portfolio never has the archive in memory.
  - `DataRequest.exportKey` holds the private key, `expiresAt = completedAt + 7 days` (COMPLIANCE: "download link expires in 7 days").
  - `GET /v1/me/data-requests/{id}/download` issues a **10-minute** presigned GET, owner only, only while `status = 'ready'` and `now < expiresAt`; 410 afterwards. The long-lived 7-day window is the row's validity, not a URL anyone can keep.
  - Every issue of a download URL writes an `AuditLog` row. The presigned URL is never logged.
  - **1A.12b added `403` to this route's contract error responses** (`packages/shared/src/contract/gdpr.ts`, previously 401/404/409/410 only): the sub-step brief's binding test list asks for "403 for a non-owner" specifically on download, distinct from `get`/`cancel`, which still return 404 for an ownership mismatch like the rest of this codebase. `download` now returns 404 only for an id that doesn't exist at all, 403 once it exists but belongs to someone else.
- **What goes in the zip.** One JSON file per entity plus a `README.txt` explaining the structure and a `manifest.json` with the generation time, the policy version and a per-file row count. JSON because Art. 20 wants a structured, commonly used, machine-readable format.
  - The subject's own rows: user and account (no password hash, no 2FA secrets, no backup codes), sessions and devices metadata, consent records, notifications, requests, quotes, photographer profile, products and tiers, portfolio images with their provenance verdict, uploads metadata, verification case and documents metadata.
  - Messages: every message in a conversation the subject participates in, since they received them, with the counterpart identified by `displayName` and profile slug only — never the counterpart's email, phone or address. A counterpart's data is not the subject's to export.
  - Binary files the subject provided: their portfolio originals, avatar and cover, copied into `files/` from the private bucket by key. **Verification documents are listed in the metadata but their bytes are excluded** — re-materialising ID scans into a second object, with a second access path, adds real risk for a copy the subject already holds. The README says how to request them, and that is a human follow-up.
  - Never exported: other users' rows, `AuditLog` (it is our accountability record, and it names admins), internal admin notes, provenance scores, vendors and match URLs (1A.10 decided the photographer does not see these).
- **Deletion is immediate, then irreversible after a grace period.**
  - `POST /v1/me/data-requests` with `{ type: 'delete' }` immediately: sets `User.deletedAt` and status, revokes every session, deletes every `Device`, unpublishes the photographer profile, and cancels the subject's `open`/`quoted` requests and `draft`/`sent` quotes. The account stops functioning at once — that is what the user asked for.
  - Anonymisation happens 30 days later, from a repeatable worker job, per COMPLIANCE's "PII anonymised after 30 days grace".
  - **Cancellable during the grace period** through `POST /v1/me/data-requests/{id}/cancel`. **Decision taken in 1A.12b: the fallback, not the adapter carve-out.** Deletion revokes every session outright (`Session.deleteMany`), and `User.status = 'deleted'` already fails the sign-in hook in `auth-instance.ts` (`databaseHooks.session.create.before`) for every provider, not just email/password — so admitting a soft-deleted user to sign back in would mean either weakening that hook (a global, security-sensitive change touching every account, not just ones mid-grace-period) or adding a second, route-scoped auth path that duplicates `requireSession` across every controller to keep the carve-out to exactly three routes. Both are more surgery than this step's scope justifies, especially with the shared compliance/security checkpoint (this file's task 5) still ahead of it. Instead: `DataRequestsService.create` mails a single-use cancel link at deletion time (`account-deletion-requested` email job, `apps/worker/src/email/templates/auth-email.ts`), carrying an HMAC token over `(dataRequestId, userId)` signed with `AUTH_SECRET` (`apps/api/src/modules/gdpr/deletion-cancel-token.ts`) — stateless, no schema change, no separate expiry to track: `DataRequestsController#cancel` uses `getOptionalSession` instead of `requireSession` and accepts the token in the request body as an alternative credential, and the token stops working the moment `DataRequest.status` leaves `pending` (used once, or the future sweep anonymises past the grace period), which doubles as single-use. `CancelDataRequestRequestSchema` (`packages/shared/src/contract/gdpr.ts`) adds this optional `token` field to the request body that 1A.12a's contract didn't yet have.
  - Sockets must drop with the sessions: this reuses whatever #101 (password reset does not disconnect sockets) lands, and 1A.12b does not invent a second mechanism.
- **Deletion can be blocked by an obligation, and says so.** `assertNoBlockingObligations(userId)` returns 409 with a machine-readable reason when the subject has something that legally cannot vanish mid-flight. Today, with no `Booking` in the schema, the only honest checks are an in-review verification case (must be decided or withdrawn first) and a conversation on an accepted quote younger than the withdrawal window. 1A.8 extends the same helper with held payments, undelivered bookings, pending payouts and open disputes; that extension is listed in this file so 1A.8 picks it up rather than rediscovering it.
  - **1A.12b found `Booking` already in `schema.prisma`** (merged in #198, ahead of 1A.8's service code, which still doesn't exist anywhere in `apps/api`). `assertNoBlockingObligations` still only checks the two things listed above, not `Booking` rows: the model existing is not the same as bookings existing yet, and 1A.8/payments-engineer owns that logic. Flagging this rather than adapting silently, per this task's instructions.
  - **No specific length is written down anywhere in this repo for "the withdrawal window".** `docs/COMPLIANCE.md` only says "right of withdrawal rules for services with a fixed date" with no number. 1A.12b used 14 days (`blocking-obligations.ts`), the standard EU distance-selling period (Directive 2011/83/EU), pending the lawyer follow-up already listed below. `Quote` also has no `acceptedAt` column, so the check reads `updatedAt` at the moment `status` became `accepted`, which would be wrong if a quote were ever updated again after acceptance — nothing in the current code path does that, but a future change touching an accepted quote's `updatedAt` would silently widen or shrink this window.
  - **`QuoteStatus` has no `cancelled` value.** For the subject's own `draft`/`sent` quotes, 1A.12b reused the existing terminal states instead of inventing one: `declined` for quotes where the subject is the client (mirrors `requests.service.ts`'s own cancel-cascade, and `quotes.service.ts`'s `decline`), `withdrawn` for quotes where the subject is the photographer (mirrors `quotes.service.ts`'s `withdraw`).
- **Anonymisation keeps what the law requires and destroys the rest.**
  - Overwritten on the `User` row: email -> `deleted-<userId>@deleted.invalid` (keeps the unique index honest), name, locale reset, image cleared, phone cleared.
  - Deleted: sessions, devices, accounts (OAuth links), two-factor rows, notifications, notification preferences, uploads that are not referenced by a retained record (their objects too), the photographer profile's free-text fields, products and portfolio images.
  - Retained, pseudonymised to the anonymised user id: ledger, receipts and fee invoices (10 years, Luxembourg accounting law), verification records for as long as required, and dispute records — exactly the COMPLIANCE exceptions, no more.
  - Chat messages and attachments are deleted **90 days** after account deletion, not at anonymisation, because that is what the retention table says. That means two different clocks, and the sweep handles both.
  - Every phase writes an `AuditLog` row with the counts it changed and no personal data.
- **One repeatable sweep, explicit phases.** A single `gdpr-sweep` queue rather than three near-identical repeatables: anonymise deletions past 30 days, purge chat past 90 days, delete expired export objects and clear their keys, fail exports stuck in `processing` for over an hour so the user can retry. Each phase logs its own counts, and a failure in one phase does not skip the others.
- **Export job shape carries the id only.** `{ dataRequestId }`, `jobId = dataRequestId`, attempts 3 with exponential backoff, and `status` on the row is the source of truth (`pending`, `processing`, `ready`, `failed`, `cancelled`, `completed`) so a retry resumes rather than duplicating. A failed export leaves `failureReason` as a stable code, not a stack trace.
- **Consent records.**
  - `GET /v1/me/consents` returns the current state per purpose (latest record wins), `PUT /v1/me/consents` appends new records for the purposes that changed — the table is append-only, so nothing is ever updated in place.
  - `POST /v1/consents` accepts an anonymous choice keyed by an `anonymousId` the web app generates, so the banner works before sign-in; on sign-up the records are linked to the new user by `anonymousId`.
  - `policyVersion` comes from `PlatformSetting`, never from the client — a client-supplied version would let the caller forge what they agreed to.
  - `ip` and `userAgent` are recorded as evidence of consent (data model), which makes them PII: both are added to the logger redaction list, and the retention is 5 years after the last update, enforced by the same sweep.
  - Withdrawal is just another append with `granted: false`. Nothing is deleted, because the record of withdrawal is itself the evidence.

## 1A.12a tasks

1. **Contract** (`packages/shared/src/contract/gdpr.ts`): data-request create/list/get/cancel/download and consent read/write schemas with error responses (including 409 blocking-obligation and 410 expired-download), `DATA_REQUEST_TYPES` and `DATA_REQUEST_STATUSES` enums; `GdprExportJobSchema` and `GdprSweepJobSchema` plus `gdpr-export` and `gdpr-sweep` in `packages/shared/src/queues.ts`; regenerate `openapi.json` and the api-client; add the routes to `not-yet-implemented.ts`.
2. **Schema** (schema-migrator, `docs/DATA-MODEL.md` first): `DataRequest` (`userId`, `type`, `status`, `requestedAt`, `completedAt`, `exportKey`, `expiresAt`, `failureReason`, `cancelledAt`), a partial unique index so one account cannot hold two open requests of the same type, an index on `(status, requestedAt)` for the sweep, and an index on `User.deletedAt` for the anonymisation scan; `ConsentRecord` gains an `anonymousId` index if it lacks one; migration via `migrate diff` applied to `photoo` and `photoo_test`.

## 1A.12b tasks

1. **API** (`apps/api/src/modules/gdpr/`): the routes above, `requireSession` everywhere, OriginGuard on mutations, the 24-hour export limit, `assertNoBlockingObligations`, the immediate deletion effects (sessions, devices, unpublish, cancel requests and quotes), `AuditLog` writes, and the consent endpoints (`PlatformSetting` policy version, `anonymousId` linking at sign-up).
2. **Worker** (`apps/worker/src/gdpr/`): the streaming export builder with one collector per entity, the S3 multipart writer, and the `gdpr-sweep` processor with its four phases.
3. **Logging**: `ip`, `userAgent`, `anonymousId`, `exportKey` and presigned URLs added to the redaction lists in both apps.
4. **Tests**:
   - a second export while one is pending returns the same row, and the 24-hour limit returns 429 with `Retry-After`;
   - the archive contains a file per entity and the manifest counts match the rows;
   - a counterpart's email never appears anywhere in the archive (assert on the whole zip, not per file);
   - verification document bytes are absent while their metadata is present;
   - download: owner only, 404 for another user, 410 after `expiresAt`, and the URL is not in the logs;
   - deletion revokes every session and deletes every device, and a blocked deletion returns 409 with its reason and changes nothing;
   - cancel during grace restores the account, and cancel after anonymisation is 409;
   - the sweep anonymises only rows past 30 days, purges chat only past 90, deletes only expired export objects, and its audit rows carry counts and no personal data;
   - anonymisation keeps ledger-class rows (asserted against whatever retained models exist at the time) and the anonymised email stays unique;
   - consent: append-only (two writes leave two rows), a client-supplied `policyVersion` is ignored, withdrawal appends rather than deletes, and an anonymous record links to the user at sign-up.
5. **Shared checkpoint** (compliance-reviewer and security-reviewer in one pass): the archive contents against Art. 15/20, the retention table against what the sweep actually does, IDOR on download and cancel, PII in logs, the soft-deleted-user auth carve-out being genuinely limited to three routes, and the anonymised account being unable to sign in.
