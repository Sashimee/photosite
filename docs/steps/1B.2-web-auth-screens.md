# Step 1B.2 – Web auth screens

Plan reference: `docs/PLAN.md` step 1B.2. Owner: web-developer; security-reviewer glance at the session handling. Blocked by 1B.1 (merged); integration checkpoint 1A.2 (merged as 1A.2b, #30).

## Goal

Web users can sign up with a role, verify their email, sign in (including the 2FA challenge), reset a password, and manage account basics, against the real API locally and the mock where the API lacks something.

## Decisions for this step

- The session lives only in the httpOnly `photoo_session` cookie set by the API. The web app never reads or stores the token, even though the sign-in response currently contains it (#25). Browser calls use `credentials: 'include'`; server components read the session by forwarding the incoming cookie to `GET /v1/auth/session`.
- API and web are different origins in development (`localhost:4000` vs `localhost:3000`). Cookie auth needs the API's CORS allow-list and the Origin guard to include the web origin (`WEB_ORIGINS`), which the API already supports; check SameSite=Lax works for same-site localhost and document the dev setup.
- Email links from the API point at `WEB_APP_URL/verify-email#token=…` and `…/reset-password#token=…`. Those pages read the fragment client-side and POST it, so tokens never reach the web server logs.
- OAuth buttons render only for providers the API reports as configured. #22 (state cookie) must be fixed before any provider is enabled, so buttons are hidden while no provider is configured (0.6 pending).

## Tasks

1. Routes under `/[locale]`: `sign-up` (email, password with the 10-character rule shown, role choice client/photographer/professional, locale default from the route), `sign-in`, `sign-in/two-factor` (TOTP or backup code), `verify-email` (fragment token), `forgot-password`, `reset-password` (fragment token), `account` (roles with add-role, 2FA enroll showing QR + backup codes once, disable with password + code, sign out, log out everywhere; delete account and data export are placeholders linking to 1A.12).
2. Forms: react-hook-form with zod resolvers built from the `@photoo/shared` request schemas (same validation as the API); API `ApiError` codes mapped to translated messages; 429 shows the retry time; uniform messages for enumeration-safe endpoints (reset request always shows "if an account exists…").
3. Session: a server helper `getSession()` and a client `useSession()`; protected routes redirect to sign-in with a `next` param (only same-origin relative paths accepted); signed-in users visiting sign-in/up are redirected to account.
4. Header shows sign-in or the account menu based on the session.
5. All strings in `packages/i18n/messages/en.json` under `web.auth.*` and `web.account.*`.
6. Tests: form validation and error mapping (Testing Library), `next` param sanitising, and session helper behaviour with mocked fetch. Coverage threshold for web must not drop. End-to-end flows are 1B.12 (Playwright).
7. Verify manually against the running API + Mailpit: sign up, receive and open the verification link, sign in, enroll TOTP, sign out, sign in with the 2FA challenge, reset the password, log out everywhere.
