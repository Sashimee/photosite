# Step 1E.3 – Backups (encrypted nightly dumps, retention, restore drill)

Plan reference: `docs/PLAN.md` step 1E.3. Owner: devops-engineer. `docs/PLAN.md` lists this as blocked by 1E.1 (staging), but the preview stack on `dok.seil.pro` already holds data that took real effort to produce — a seeded database and a populated MinIO — and has **no backup of any kind**. The step is therefore written for the preview first, with staging and production reusing the same compose fragment and the same script.

## What exists today

`infra/dokploy/preview/compose.yml` runs `postgis/postgis:16-3.5` with a named volume `postgres-data`, MinIO with `minio-data`, and Redis with `redis-data`. Nothing copies any of them anywhere. A `docker volume rm`, a bad migration or a disk failure loses the lot, and the seed — now crash-safe (#121) but still slow and dependent on MinIO credentials — is the only way back.

## Decisions for this step

- **`pg_dump` custom format, not a volume snapshot.** `pg_dump -Fc` restores selectively, survives a Postgres minor-version bump and is verifiable. A filesystem copy of `postgres-data` is only valid with the server stopped, which a backup must never require.
- **The dump runs in its own one-shot container on a schedule**, not in the Postgres container and not on the host. It joins `internal`, uses the same `postgis/postgis` image (so `pg_dump` matches the server version exactly), and exits. Dokploy's scheduled-task feature triggers it; a `restart: no` service with a cron sidecar is the fallback if scheduling is not available on this Dokploy version, and the plan records which one was used.
- **Encrypted before it leaves the container.** `pg_dump | age -r <recipient>` (or `gpg --encrypt` if `age` is unavailable in the image — decide at implementation time and record it), so the object storage never holds readable personal data. The **public key** lives in the compose env; the private key never touches the server. That is the whole point: a backup that the compromised host can decrypt protects against disk failure only, not against the compromise.
- **The private key is generated locally and stored by Alex.** This is the one genuinely human part, and it is handled by shipping the code first: until `BACKUP_AGE_RECIPIENT` is set, the service refuses to start and says so, rather than writing plaintext dumps. No environment silently falls back to unencrypted.
- **Destination is the existing MinIO**, bucket `photoo-backups`, created by `minio-init` alongside the other two, with a **dedicated scoped user** that can `PutObject` and `ListBucket` and **cannot delete**. A backup user that can delete is a backup that ransomware deletes. Retention pruning therefore runs as a separate, differently-scoped job.
  - Recorded honestly: on the preview, MinIO shares the host with Postgres, so this protects against a bad migration or a dropped database, **not** against losing the machine. Off-host replication is a production requirement, listed as a follow-up with a concrete option (a second S3 target, e.g. Hetzner Object Storage in the EU) rather than left vague.
- **Object naming** `photoo/<env>/<YYYY>/<MM>/<YYYY-MM-DDTHH-mm-ssZ>.dump.age`, so a prefix listing is chronological and one environment can never overwrite another's objects.
- **Retention**: 7 daily, 4 weekly, 6 monthly, pruned by a weekly job using a separate user that may delete only under that prefix. `COMPLIANCE.md` says ledger and invoices are kept 10 years; a 6-month backup horizon does not conflict, because backups are a recovery mechanism and the 10-year obligation is served by the live database. Stated here because the two numbers look contradictory at a glance.
- **A backup that is not verified is a guess.** Every run ends with `pg_restore --list` against the object it just wrote, which fails loudly on a truncated or corrupt dump, and records the size and table count. A run that produces a dump smaller than a floor (say 10 KiB, which an empty database already exceeds) fails rather than silently "succeeding".
- **Failure is visible without a person watching.** The job writes a heartbeat object and a log line; 1E.2 alerts on a missing heartbeat. Until 1E.2 exists, `GET /v1/health` gains nothing (a backup is not the API's business) and the gap is recorded rather than papered over with a fake success.
- **Redis is not backed up.** It holds queues, rate-limit counters and push tickets — all rebuildable. Stated explicitly so nobody later assumes it is covered.
- **MinIO objects are not covered by this step.** Uploads are user data and need their own replication; the decision is recorded and deferred to a follow-up rather than bundled in, because bucket replication and database dumps have different failure modes and schedules.
- **Secrets never reach the log.** The script uses `PGPASSWORD` from the environment, never a URL with the password in `argv`, because `ps` and container inspection expose command lines.

## 1E.3a tasks

1. `infra/dokploy/backup/` holding `backup.sh` (dump, encrypt, upload, verify, heartbeat) and `prune.sh`, both POSIX `sh`, `set -euo pipefail`, and each with a usage line naming every required variable.
2. Compose fragment: a `backup` service and the scoped MinIO users in `minio-init`, wired into `infra/dokploy/preview/compose.yml`.
3. Refuse-to-run guards: missing `BACKUP_AGE_RECIPIENT`, unreachable bucket, or a dump under the size floor all exit non-zero with a message naming the variable.
4. README section: what runs, where objects land, how to list them, and how to read a failure.
5. Tests: the scripts are shell, so a `bats`-style test is out of scope for this repo, but the CI workflow gains a job that runs `backup.sh` against a throwaway Postgres and MinIO in services containers and asserts an encrypted, restorable object appears. That is the real test and it runs on every change to the script.

## 1E.3b tasks

1. `docs/runbooks/restore.md`: restoring a whole database, restoring one table, and what to do when the dump is the only surviving copy. Written as commands to paste, with the destructive ones spelled out and flagged.
2. Perform the drill against a scratch database on the preview host, from a real backup object, and record the wall-clock time and the exact commands used. A restore procedure that has never been run is a hypothesis.
3. Record the recovery point (24 h, the backup interval) and the measured recovery time in the runbook, so the business risk is a number rather than a feeling.

## Human follow-ups

Appended to `docs/steps/human-followups.md`:

- **Generate the backup key pair and store the private key somewhere that is not the server** (`age-keygen`, keep the private key in a password manager; the public key goes in the Dokploy env as `BACKUP_AGE_RECIPIENT`). Claude generates and sets the public recipient, but the private key must live where a compromised host cannot reach it — so Alex holds it. Until it is set, the backup service refuses to run rather than writing plaintext.
- **Decide the off-host destination for production** (a second S3 target in the EU). The preview's backups share a host with the database, which covers a bad migration but not a lost machine.
- **Object storage replication for uploads** is a separate decision from database dumps and is not covered by this step.
