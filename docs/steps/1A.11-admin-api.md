## What already exists, and the gap it exposes

The contract was written in 0.11 and is complete: `packages/shared/src/contract/admin.ts` registers every route below, and each one carries `x-required-permission` (`support`, `moderation`, `verification`, `finance`, `superadmin`) and sometimes `x-requires-2fa`. `ADMIN_PERMISSIONS` is a real enum in `packages/shared/src/enums.ts`.

**Nothing stores those permissions.** `packages/db/prisma/schema.prisma` has no admin permission field anywhere: an admin is just a `User` with `admin` in `roles`. So today the contract promises a permission model the database cannot express, and `requireAdminSession` can only answer "is this an admin", not "may this admin issue a refund". Closing that is the first task of this step, not an afterthought — every route below depends on it.

The verification queue (`/admin/verification-cases/*`) is already implemented in `apps/api/src/modules/verification/admin-verification-cases.controller.ts` from 1A.9b. It currently authorises with `requireAdminSession` alone, so it must be migrated onto the permission check in 1A.11b rather than left as the one endpoint with different rules.

`Report`, `Booking` and `ProvenanceCheck` models do not exist. `Booking` belongs to 1A.8 and `ProvenanceCheck` to 1A.10, both already planned. `Report` belongs to no other step, so it is added here.

## Decisions for this step

- **Permissions live on a join table, not a string array.** `AdminPermissionGrant` (`userId`, `permission`, `grantedByAdminId`, `grantedAt`, unique on `(userId, permission)`) rather than a `String[]` column, because every grant is an auditable event and a revoke must be able to say who did it and when. A user with `admin` in `roles` and no grants can sign in and see nothing — that is the correct default for a freshly created admin.
- **`superadmin` is the only permission that can grant permissions**, and an admin can never grant or revoke their own. Both rules are enforced in the service, and both get a test, because the second one is the kind of thing that silently stops being true.
- **The first superadmin is created outside the API**, by the seed locally and by a one-off script in production. There is deliberately no bootstrap endpoint: an endpoint that can mint a superadmin is a permanent hole in the system for the sake of one minute of setup. Recorded as a human follow-up.
- **`requirePermission(session, permission)` builds on `requireAdminSession`**, which already enforces the admin role plus a second factor verified within 12 hours. `x-requires-2fa` operations additionally demand a *fresh* verification (15 minutes), so a refund or a role change re-prompts even inside a valid admin session. The freshness window is one constant next to the existing 12-hour one.
- **Every admin mutation writes `AuditLog`** — the convention in `CLAUDE.md` and the reason the model exists — with `actorType: 'admin'`, the actor, the target, and `before`/`after`. Two rules that are easy to get wrong and so are tested: the write happens **in the same transaction** as the change, so an audit entry can never describe a change that was rolled back; and `before`/`after` are **redacted projections**, never whole rows, so password hashes, tokens and verification document metadata cannot leak into a table the whole admin team can read.
- **The audit log is append-only.** No update or delete path exists in code, and the query endpoint is read-only with keyset pagination over the existing `occurredAt` index, filterable by actor, target and action.
- **Suspension is a status change with consequences.** `POST /admin/users/{id}/suspend` sets the status, writes the audit row, revokes every session, and disconnects the user's sockets. Suspending an account while its browser tab keeps working is the same class of bug as #127 and #101, so it is handled here rather than discovered later. Reactivation restores the status only — it never restores sessions.
- **Roles are set, not toggled.** `PUT /admin/users/{id}/roles` replaces the set. Removing `photographer` from a user with a published profile unpublishes it in the same transaction; the endpoint returns `409` if that would break a booking obligation, reusing the `assertNoBlockingObligations` helper 1A.12 defines (and defining it here first if 1A.12 has not merged, with 1A.12 then extending it).
- **Search is by exact identifiers or a prefix, never a free `contains` over email.** `q` matches an id, an exact email, or a `displayName` prefix. A substring search over every user's email is a data-exfiltration primitive handed to the least privileged admin tier, and it is also the query that will not survive a real user table.
- **Platform settings are typed.** `PlatformSetting` is a key/value `Json` table; the contract's `PlatformSettingsSchema` is the single source of truth for which keys exist and what shape each value has. Writes validate against it, unknown keys are rejected with `422`, and each write records `updatedByAdminId` and an audit row with the old and new value. Settings are read through a small cached service so the fee helper and auto-release job do not query per request.
- **Reports (`Report`) implement DSA notice-and-action.** Anyone — including a signed-out visitor — can report content; the queue is admin-side. Fields: reporter (nullable for anonymous), `targetType`/`targetId`, free-text reason, status (`open`/`resolved`/`dismissed`), the resolving admin, the decision and its reason, and timestamps. **No `category`** (D23): an enum invented before any real report exists would be guessed taxonomy shipped in a migration, so the free-text reason plus admin triage carries it until the buckets are known. 1A.11c must also make `AdminReportSchema.reporterId` nullable in the contract, which #148 filed — the model is already nullable. A resolution always records a statement of reasons, because DSA requires one and reconstructing it later is impossible.
- **Takedown is a status change on the target, never a delete**, so a wrongly removed profile or job offer can be restored and the audit trail stays meaningful.
- **Rate limits.** Admin endpoints use the default API limits except the mutations, which are limited per admin account, so a compromised admin session cannot mass-suspend at machine speed.

## 1A.11a tasks (schema-migrator)

1. `AdminPermissionGrant` as above, with `DATA-MODEL.md` updated first.
2. `Report` as above, with indexes on `(status, createdAt)` and `(targetType, targetId)`.
3. Seed: the local admin gets every permission; document that production does not.
4. Migration via `migrate diff`, applied to `photoo` and `photoo_test`.

## 1A.11b tasks (api-developer)

1. `AdminModule`: `requirePermission`, the fresh-2FA check, and an `AuditService` whose write takes the transaction client so it cannot be called outside one.
2. Users: search, get, suspend (with session revocation and socket disconnect), reactivate, set roles.
3. Platform settings: typed get and patch, plus the cached read service.
4. Audit log query.
5. Migrate `admin-verification-cases.controller.ts` onto `requirePermission('verification')` and remove its ad-hoc check.
6. Remove the implemented routes from `not-yet-implemented.ts`; regenerate openapi and the api-client.
7. Tests: permission matrix per route (each permission allowed, every other one 403), self-grant refused, non-superadmin grant refused, stale 2FA on an `x-requires-2fa` route, audit row written in the same transaction and absent after a rollback, `before`/`after` redaction, suspension kills sessions and sockets, role removal unpublishes, settings reject unknown keys, audit query pagination.

## 1A.11c tasks (api-developer)

1. Public `POST /v1/reports` (rate-limited, works signed out) and the admin queue, resolve and takedown endpoints.
2. Tests: anonymous reporting, duplicate reports from one reporter, resolution requires a statement of reasons, takedown hides the target from public reads but keeps it readable in admin, and the audit trail.

## 1A.11d tasks (blocked)

Bookings list/detail, refunds and transfer reversals (after 1A.8) and the provenance queue (after 1A.10). Both are already specified in `docs/steps/1A.8-payments.md` and `docs/steps/1A.10-provenance.md`; this sub-step only exposes them under `/admin` with the `finance` and `moderation` permissions and the fresh-2FA rule.

## Security checkpoint

Not one of the listed 1E.6 checkpoints, but this step creates the most powerful role in the system, so a security-reviewer pass before merge covers: privilege escalation through the grant endpoints, the 2FA freshness window, audit completeness and redaction, IDOR on every `{id}` route, and whether any admin read returns more personal data than the screen needs.
