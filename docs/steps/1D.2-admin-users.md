## What the API gives us (1A.11b)

- `GET /v1/admin/users` — keyset paginated; `q` matches an **id, an exact email, or a `displayName` prefix**, plus `role` and `status` filters. Permission: `support`.
- `GET /v1/admin/users/{id}` — permission `support`.
- `POST /v1/admin/users/{id}/suspend` `{ reason }` — permission `support`. Revokes every session and disconnects the user's sockets.
- `POST /v1/admin/users/{id}/reactivate` — permission `support`. Restores status only, never sessions.
- `PUT /v1/admin/users/{id}/roles` `{ roles }` — permission **`superadmin`**, and it unpublishes a published photographer profile when `photographer` is removed.
- `GET /v1/admin/audit-log` — permission `superadmin`, filterable by `actorId`, `entityType`, `targetId`, `from`, `to`.

Two consequences the UI has to respect rather than discover: **roles need `superadmin` while everything else needs `support`**, so a support admin must not be shown a control they cannot use; and **there is no grant/revoke endpoint at all** (PR #159, and the same gap as #148), so this step cannot offer permission management and must not pretend to.

## Decisions for this step

- **Search is explained, not just offered.** Because the API matches an id, an exact email or a name prefix — deliberately not a substring search over email — the empty state says exactly that. Otherwise an admin types half an address, gets nothing, and concludes the tool is broken. The placeholder text carries the same information.
- **Controls are hidden when the permission is missing, and the API is still the authority.** The shell knows the admin's permissions from the session, so a support admin never sees the roles control. The server rejects it regardless; hiding it is a courtesy, never the enforcement.
- **Suspension states its consequences in the confirm dialog**: this signs the user out of every device and drops their chat connections, and it does not delete anything. That is what the endpoint does, and an admin should not have to infer it.
- **A reason is mandatory** for suspension (the API requires it) and the field says it is recorded in the audit log with the admin's name. People write better reasons when they know that.
- **Reactivate does not restore sessions**, and the dialog says so, because "undo" is the natural assumption and it is wrong here.
- **Roles are a set, replaced wholesale.** The dialog shows the resulting set, not a series of toggles, and warns explicitly when removing `photographer` from a user with a published profile — the API unpublishes it in the same transaction, which is a side effect worth naming before the click rather than after.
- **The detail page shows the user's own audit trail** — `GET /v1/admin/audit-log?targetId={id}` — for admins with `superadmin`. The most common question about an account is "what happened to it", and the answer already exists.
- **No email address is shown in a list view.** The list shows display name, roles, status and a masked email (`a***@example.com`); the full address appears on the detail page, which is one deliberate click and one audit-relevant page view. A support admin scrolling a list does not need every address on screen, and screenshots of admin tools leak.
- **No impersonation, no password reset on behalf of a user, no email change.** None of those endpoints exist, and this step does not invent client-side approximations of them.
- **Every mutation goes through the shell's fetch wrapper**, so a stale second factor produces the re-verification flow from 1D.1a rather than an error toast. Roles and suspension are exactly the operations where a 15-minute-fresh 2FA prompt will fire in practice.
- **Pagination is server-side only**, on the existing cursor. No client-side sorting of one page, which would lie about the ordering of the whole set.

## 1D.2a tasks

1. `app/(admin)/users/page.tsx` — search field, role and status filters, `DataTable` (1D.1b) with cursor pagination, masked email, empty state explaining the match rules.
2. `app/(admin)/users/[id]/page.tsx` — identity, roles, status, timestamps, the audit trail panel (superadmin only), and the action buttons.
3. Confirm dialogs for suspend, reactivate and roles, each naming the subject and its consequences as above.
4. Permission-aware rendering from the session's grants.
5. i18n keys under `admin.users.*` in `en`.
6. Tests:
   - a support admin sees no roles control; a superadmin does;
   - suspend posts the reason and renders the API's error codes (including `TWO_FACTOR_REQUIRED` routing to re-verification, not a toast);
   - the roles dialog warns when removing `photographer` from a published profile;
   - the list shows a masked email and the detail page the full one;
   - pagination advances by cursor and does not refetch page one on back;
   - the empty state explains the match rules;
   - a render against the real `en` catalog.
