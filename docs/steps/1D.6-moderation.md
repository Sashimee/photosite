## What the API gives us today

Stale as of #263/#270/#308/1D.6a/1D.6b — updated below.

`apps/api/src/modules/admin/admin-reports.controller.ts`, all on the `moderation` permission:

- `GET /v1/admin/reports` — keyset page, filterable by `status`, `targetType`, `targetId`.
- `GET /v1/admin/reports/{id}` — a report with `createdAt`, `resolvedAt` and a `target` summary (never the reporter's or the owner's email), 404 for an unknown id.
- `POST /v1/admin/reports/{id}/resolve` — `status` of `resolved` or `dismissed` plus a required `resolution` string.
- `POST /v1/admin/reports/{id}/takedown` — required `resolution`; sets `deletedAt` on the target and resolves the report in one transaction (`report-targets.ts`).
- `POST /v1/admin/reports/{id}/restore` — clears `deletedAt` on the target, audits `report.restored`, 409 if the target was never taken down, 422 for an unsupported `targetType`.
- `POST /v1/admin/reports/direct-takedown` — 1D.6c (D25): takes down a `photographer_profile` or `job_offer` a moderator found without a prior report. Synthesises a `Report` (`reporterId: null`, already `resolved`) in the same transaction as the takedown, so it gets the identical audit trail, statement of reasons and restore path.
- Every decision (resolve, dismiss, takedown, restore, direct-takedown) enqueues a `notify` job to the reporter (when `reporterId` is not null) and to the target's owner (`notifyDecision`, `admin-reports.service.ts`).

`REPORT_TARGET_TYPES` is `photographer_profile`, `portfolio_image`, `request`, `job_offer`, `job_application`. `REPORT_STATUSES` is `open`, `resolved`, `dismissed`. `targetType` is a free-text column with no foreign key (D23), so an unknown value is a 422 on takedown/restore rather than a crash — the UI must expect that too. `direct-takedown`'s own request schema restricts `targetType` to `photographer_profile` and `job_offer` only (D25), so an unsupported value there is a 400, not a 422.

## Why 1D.6a comes first

`AdminReportSchema` is `{id, reporterId, targetType, reason, targetId, status, adminId, resolution}`. A moderator handed that screen sees a reason written by a stranger and a UUID. Five gaps, each filed as its own issue (#187–#191):

1. **No target snapshot** (#187). Nothing in the report response describes the reported content. Deciding whether a portfolio image is illegal requires *seeing the image*; there is no admin endpoint that returns one. Without this the screen can only take the reporter's word, which is exactly the failure mode notice-and-action exists to prevent — and the most likely abuse is a competitor reporting a rival's profile.
2. **No `createdAt`** (#188). The list is keyset-ordered by `createdAt`, but the DTO omits it, so the UI can neither show how long a report has waited nor explain its own ordering. A queue that cannot show age silently starves its oldest item — the same failure 1D.3 called out for verification.
3. **No detail endpoint** (#189). There is no `GET /v1/admin/reports/{id}`; a deep link into one report has to list-and-filter by `targetId` and hope. A moderator's URL must survive being pasted to a colleague.
4. **No restore** (#190). `report-targets.ts` deliberately sets `deletedAt` so "a wrong takedown stays reversible", but nothing exposes the reversal. Reversible in the database is not reversible in practice.
5. **No decision notice** (#191). `resolve`/`takedown` write an `AuditLog` row and nothing else. The DSA obligation in `docs/COMPLIANCE.md:51` is to give the reporter *and* the content owner a statement of reasons with redress information. An audit log is an internal record, not a notice to an affected person.

1D.6a closes all five: `createdAt` and a `target` summary object on the report DTO, `GET /v1/admin/reports/{id}`, `POST /v1/admin/reports/{id}/restore`, and a `notify` worker job on every decision. Contract first — `packages/shared` and the OpenAPI change before the admin app is touched.

## Decisions for this step

- **The queue defaults to `open`, oldest first**, for the reason in gap 2. Not a user preference in this step.
- **The target summary is a summary, not the row.** Enough to decide (an image's variant URL, a profile's display name and slug, a request's title and body), never the owner's email or other users' data. A report on a *photographer* profile does not entitle a moderator to the reporting client's account.
- **`reason` is attacker-controlled text and is rendered as text.** It is typed by whoever filed the report; it goes through the same escaping as any user content, and never into `dangerouslySetInnerHTML`, a URL, or a link target.
- **Takedown is confirmed, names the target, and warns that the owner is notified.** Resolve and dismiss both require the text that becomes the statement of reasons, and the field label says it is sent to the reporter and the owner — the same reasoning as 1D.3's reject dialog. A moderator writing "spam" into a field they think is internal is how an unusable notice gets sent.
- **`restore` is a moderation action with the same weight as takedown**: its own confirmation, its own audit entry, its own notice. It does not reopen the report; it records that the decision was reversed.
- **A 409 is an expected outcome, not an error toast.** Two moderators opening the same open report is normal; the second one gets "already resolved by <admin>" and a refreshed view.
- **No bulk actions in 1D.6.** `docs/PLAN.md` lists bulk actions under 1D.4 for provenance, where a vendor score makes batching defensible. A bulk takedown of human-filed reports means deciding many cases without reading them. If a moderation backlog ever justifies it, it gets its own step and its own review.
- **1D.6c handles moderation without a report** — taking down a profile or job offer a moderator found themselves. It has no `Report` row to hang the audit trail and the notice on. **Resolved as D25** (`docs/DECISIONS.md`): the API synthesises a `Report` (`reporterId: null`, `reason: MODERATOR_INITIATED_REPORT_REASON`, already `resolved`) and takes down the target in the same transaction, reusing 1D.6a's audit trail, notice and restore path rather than building a parallel action. Scoped to `photographer_profile` and `job_offer` only, per the plan; `portfolio_image`, `request` and `job_application` are out for now (see D25's reasoning).

## 1D.6a tasks (api-developer)

1. `AdminReportSchema` gains `createdAt`, `resolvedAt` and `target` (a discriminated union on `targetType`, each variant carrying only what the decision needs; `null` when the target row is gone).
2. `GET /v1/admin/reports/{id}` on the `moderation` permission, 404 for an unknown id.
3. `POST /v1/admin/reports/{id}/restore` — clears `deletedAt` on the target, audits `report.restored`, 409 if the target was never taken down, 422 for an unsupported `targetType`.
4. A `notify` job on resolve, dismiss, takedown and restore, to the reporter (when `reporterId` is not null) and to the target's owner, carrying the resolution text and a redress pointer. Reuses 1A.7's notification service; no new transport.
5. Regenerate `packages/api-client/openapi.json` and the typed client.
6. Tests: the target summary for each of the three target types and for a missing target; the summary contains no email; `restore` round-trips a takedown; both decisions enqueue notices to both parties; an anonymous report (`reporterId: null`) notifies only the owner.

## 1D.6b tasks (web-developer)

1. `app/(admin)/moderation/page.tsx` — `DataTable` with status and target-type filters, defaulting to `open` oldest-first, showing age and reporter presence.
2. `app/(admin)/moderation/[id]/page.tsx` — the reason, the target summary rendered per type, the decision history from the audit log (`targetId={reportId}`), and the actions.
3. Decision dialogs for resolve, dismiss, takedown and restore, each with the notice-text field labelled as visible to both parties.
4. The 409 path and the 422 unsupported-target path.
5. i18n under `admin.moderation.*`, English only.
6. Tests: the default sort; a report whose target is gone renders a removed state rather than a broken viewer; `reason` renders as text (an HTML-looking reason is not parsed); takedown requires confirmation naming the target; a 409 shows who resolved it; the notice field says who receives it; one test renders against the real `en` catalog.

## 1D.6c tasks (api-developer, API half only)

1. `DirectTakedownRequestSchema` (`targetType` restricted to `photographer_profile` | `job_offer`, `targetId`, `resolution`) and `MODERATOR_INITIATED_REPORT_REASON` in `packages/shared`; `POST /admin/reports/direct-takedown` registered in the OpenAPI contract, `moderation` permission, 201 on success.
2. `AdminReportsService.directTakedown`: 404 if the target doesn't exist, otherwise creates the synthesised `Report` and calls the same `takeDownReportTarget` as a reported takedown, both inside one transaction; audits `report.direct_takedown` with `before: null` (there is no prior report state) and the same `after` shape `report.takedown` writes; calls the same `notifyDecision` (owner only, since `reporterId` is null).
3. Regenerated `packages/api-client/openapi.json` and the typed client.
4. Tests: permission matrix, 401, empty resolution, a target type outside the two named ones (400, not 422 — contract-level, not runtime), 404 for a missing target, a `photographer_profile` takedown (public 404, synthesised report `reporterId: null`, audit row, owner notified and no `report_decision` notice sent to anyone), and a `job_offer` takedown that round-trips through the *existing* `GET /admin/reports`, `GET /admin/reports/{id}` and `POST /admin/reports/{id}/restore` endpoints unchanged.
5. Left for 1D.6c's UI half (web-developer): the profile and job-offer detail pages' "take down" entry point, its confirmation dialog (naming the target, warning the owner is notified, same weight as 1D.6b's takedown dialog), and — if useful — a way to tell a moderator-initiated queue row apart from a public one (the `reason` field carries `MODERATOR_INITIATED_REPORT_REASON` for exactly this, but nothing renders it specially yet).

## Human follow-ups

- **A moderation policy**, and specifically what the statement of reasons says. 1D.6a ships the mechanism; the words are a legal question and the DSA expects them to name the ground for the decision and the redress route. Belongs with the 0.7 lawyer conversation, alongside 1D.3's review standard.
- **Who moderates.** The `moderation` permission exists; nobody holds it. A queue with no assignee is a queue nobody empties.
