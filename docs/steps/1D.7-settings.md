## What the API gave us before 1D.7a

`apps/api/src/modules/admin/admin-settings.controller.ts`, on the **`superadmin`** permission (not a lesser one — changing the fee changes what every future booking charges):

- `GET /v1/admin/settings` → `{ feePercent, autoReleaseDays }`.
- `PATCH /v1/admin/settings` → the same two fields, partial, audited as `platform_settings.updated` with before/after.

That was the whole surface. Of the six subjects `docs/PLAN.md` names, **four had no API at all**: feature flags, countries enable/disable, legal text versions, email template preview. `PlatformSetting` is a key/value table so flags and versions had somewhere to live, and `Country` already had `enabled`, `legalTexts` and `vatRate` columns — but nothing wrote any of them.

## What the API gives us after 1D.7a

- `GET /v1/admin/settings` → `{ feePercent: number | null, autoReleaseDays, featureFlags: [{ key, description, enabled }] }`. `feePercent` is `null`, not `5`, when the row is unconfigured (`packages/shared/src/contract/admin.ts`, `PlatformSettingsSchema`).
- `PATCH /v1/admin/settings` → partial update of `feePercent`, `autoReleaseDays` and/or `featureFlags` (an array of `{ key, enabled }` against the code-defined `FEATURE_FLAG_KEYS`), audited as `platform_settings.updated` with before/after (`apps/api/src/modules/admin/admin-settings.service.ts`).
- `GET /v1/admin/countries` → every country (including disabled ones) with `accountCount`, the blast radius a confirmation dialog needs (`apps/api/src/modules/countries/admin-countries.service.ts`).
- `PATCH /v1/admin/countries/{code}` → partial update of `enabled`, `vatRate`, `defaultLocale`; 404 on an unknown code; audited as `country.updated` with before/after including the recomputed `accountCount`.
- `GET /v1/admin/countries/{code}/legal-texts` and `POST /v1/admin/countries/{code}/legal-texts` → append-only legal text versions per country (see below), audited as `country.legal_text_published`.
- `GET /v1/policy-version` (public, uncached) → `{ policyVersion: string | null }`, the value 1B.10's consent banner compares against a stored decision.

Feature flags currently defined: `maintenanceMode`, `newSignupsPaused` (`packages/shared/src/enums.ts`, `FEATURE_FLAG_KEYS`) — nothing in the API or worker reads either yet; that consumption is separate, unblocked work, not part of 1D.7a.

## The fee has two readers that disagree (#193) — resolved in 1D.7a

This was the finding that reshaped the step. It is fixed; the account of the problem is kept below because it explains *why* `PlatformSettingsService` has no cache — a future reader should not "optimise" one back in without re-reading this.

- `apps/api/src/common/platform-settings/platform-settings.service.ts` reads `feePercent` through a **30-second in-process cache**, and falls back to `DEFAULT_PLATFORM_SETTINGS.feePercent = 5` when the row is missing or not a number.
- `apps/api/src/modules/quotes/quotes.service.ts:626` reads the same row **directly from the database on every quote**, and throws `quotes: PlatformSetting "feePercent" is missing or invalid` when it is absent.

Two consequences, both real:

1. **A missing row shows the admin a fee that quoting refuses to use.** The settings screen would display 5 % as though it were configured, while every attempt to create a quote fails. The screen must distinguish "configured" from "defaulted", which means the API must tell it which one it is.
2. **`invalidate()` only clears the instance that served the `PATCH`.** It is an in-memory field. The moment the API runs more than one replica — or the worker computes a payout, being a separate process entirely — a fee change is live on one instance and up to 30 seconds stale on the others. Money computed at two rates concurrently is not a rounding difference, it is two different answers to "what did we charge".

The preview runs a single API container, so this was latent rather than currently broken. It would have stopped being latent the first time anything scaled. 1D.7a resolved it by making one reader authoritative rather than by adding a third: `quotes.service.ts:573` now calls `platformSettings.getFeePercent()`, and `DEFAULT_PLATFORM_SETTINGS` no longer exists in non-test source.

`Booking.feePercent` is a snapshot taken at creation (`schema.prisma:721`), so a fee change never rewrites an existing booking. That part is already right, and the settings UI should say so — an admin editing a fee needs to know whether it is retroactive, and the honest answer is no.

## Decisions for this step

- **The fee has one reader.** 1D.7a deletes the divergence: `quotes.service.ts` goes through `PlatformSettingsService`, and the service adopts quoting's loud failure instead of its own silent default. A missing `feePercent` is a misconfiguration, not a 5 %.
- **Cross-process invalidation, not a shorter TTL.** Shortening the TTL narrows the window and keeps the bug. The write publishes on Redis (already a dependency) and every instance drops its cache. If that proves larger than this step, the fallback is to drop the cache entirely and read the row per use — a single indexed primary-key lookup, which is what quoting already does today without complaint. Either is correct; a tuned TTL is not.
  - **1D.7a took the fallback: the cache is gone.** `PlatformSettingsService` reads `feePercent`/`autoReleaseDays` straight from `PlatformSetting` on every call, the same primary-key lookup quoting already made with no complaint. A Redis publish/subscribe invalidation channel would still leave a window between the write committing and every subscriber processing the message, plus a new failure mode (a subscriber that missed the message, or reconnects mid-flight, serving stale data indefinitely instead of for at most 30s) — solving that properly means the write side has to wait for every instance to ack, which is more machinery than a single-digit-millisecond read. Reading the row on every call has no window at all: the value returned is whatever's in the row at the moment the transaction that changed it committed, everywhere, always. `quotes.service.ts` now calls `PlatformSettingsService.getFeePercent()` instead of keeping its own copy of the same query, so there is exactly one reader for the fee.
- **Changing the fee is confirmed, and the confirmation states the blast radius**: the new percentage, that existing bookings keep their snapshot, and that every quote created from now on uses it. Typed confirmation, not a bare OK. — **1D.7b's job**: the API takes the new value on `PATCH`; the typed confirmation is UI.
- **Every setting screen shows who changed it last and when.** `PlatformSetting.updatedByAdminId` is recorded but never surfaced on the settings/country responses themselves, and every write is already audited. A settings page with no history is where an unexplained fee change becomes unattributable. — 1D.7a did not add `updatedByAdminId`/`updatedAt` fields to `PlatformSettingsSchema`/`AdminCountrySchema`; the existing `GET /v1/admin/audit-log` endpoint (`actorId`, `targetType`, `targetId`, `occurredAt` filters) already carries this and is generic across every audited entity, `PlatformSetting` and `Country` included. 1D.7b can query it filtered to `targetType: 'PlatformSetting' | 'Country'` rather than the API duplicating that data on every settings response; flag this back here if 1D.7b finds that insufficient.
- **Feature flags are booleans with a description, and the list is defined in code.** A free-text key/value editor on a table the API reads by key is a way to create a flag nothing reads, or to typo a live one into being off. The API publishes the known flags; the screen toggles those. — **done**: `FEATURE_FLAG_KEYS`/`FEATURE_FLAG_DESCRIPTIONS` in `packages/shared/src/enums.ts` and `contract/admin.ts`.
- **Disabling a country is not deleting it.** `Country.enabled` gates new sign-ups, new profiles and new requests in that country; it never hides existing users or breaks their bookings. The confirmation says which of the two it is, with the count of accounts affected. — **done**: `AdminCountrySchema.accountCount`; enforcement and the "existing request still readable" behaviour are integration-tested.
- **Legal text versions are append-only and stored per country** (`Country.legalTexts` is already a `Json` column). Publishing a new version does not overwrite the old one, because `ConsentRecord.policyVersion` points at what a user actually agreed to — 1B.10's consent records are meaningless if the version they name can be edited afterwards. This is the same append-only reasoning as consent itself. — **done**, see "Append-only enforcement" below.
- **`policyVersion` is read by 1B.10 and written here.** The two steps must agree on the shape before either ships; 1B.10a is planned and unstarted, so 1D.7a defines it and `docs/steps/1B.10-consent.md` gets a pointer. — **done**: `GET /v1/policy-version`, `docs/steps/1B.10-consent.md` updated in the same PR.
- **The email template preview renders, and never sends.** 1D.7c renders the worker's existing email templates (plain TypeScript render functions, not react-email) server-side with sample data and shows the HTML in a sandboxed frame. No "send test to me" button in this step — a preview endpoint that can be made to send mail is an open relay with extra steps. If a real send is wanted later it is its own step, rate-limited and restricted to the signed-in admin's own address. — still 1D.7c, unstarted.
- **`superadmin` stays the permission for all of it.** Nothing here is a routine support action. — every route in this file's "after 1D.7a" section above is on `superadmin`, including the two `GET`s; only `GET /v1/countries` and `GET /v1/policy-version` are public.

## Append-only enforcement for legal texts

`AdminCountriesService.publishLegalText` (`apps/api/src/modules/countries/admin-countries.service.ts`) is the only write path to `Country.legalTexts`: it reads the current `versions` array inside the transaction, appends one new entry (`version` = `String(existingVersions.length + 1)`), and writes the whole array back — there is no update-by-index or delete path in the service or the controller, so an existing entry can only be read, never replaced. The same transaction bumps `PlatformSetting('policyVersion')` to the next integer. `countries.integration.test.ts` ("starts with no versions, then publishes append-only, never overwriting an earlier version") publishes twice and asserts both the first and second version's `content` survive unchanged after the second publish.

## Human follow-ups

- **The launch fee.** The seed sets `feePercent = 5`, matching `CLAUDE.md` (`DEFAULT_PLATFORM_SETTINGS` no longer exists in source since 1D.7a — the fee is a real, single row, not a code default). Confirm 5 % is the number the platform launches with before anything charges a real card, because `Booking.feePercent` snapshots it and changing it later does not revisit bookings already taken.
- **Which countries are enabled at launch.** Luxembourg first is decided; whether the neighbours are open on day one is not, and `PATCH /v1/admin/countries/{code}` (via curl/Postman today, a screen once 1D.7b ships) is the switch.
- **Legal text ownership — publishing is no longer blocked on a human editing the database.** As of 1D.7a, `POST /v1/admin/countries/{code}/legal-texts` (superadmin) takes `{ kind, locale, content }`, appends a new version to `Country.legalTexts`, and bumps `PlatformSetting('policyVersion')`. Concretely, once a superadmin's session exists, publishing Luxembourg's terms is one authenticated `POST` (today via curl/Postman/an admin API client, a form once 1D.7b ships): confirm the lawyer's text is the source of what goes in `content`, and that this endpoint only versions it rather than drafting it — with the 0.7 lawyer conversation. This is the fix for a real, current gap, not a theoretical one: `ConsentsService.record`/`updateForUser` (`apps/api/src/modules/gdpr/consents.service.ts`) **fail with a 500 by design** — "publish a legal text version before consent can be recorded" — whenever `PlatformSetting('policyVersion')` is unset, because writing a made-up version into a `ConsentRecord` would fabricate legal evidence of what someone agreed to. On a fresh environment nothing has ever called the publish endpoint, so `policyVersion` is null and every consent write 500s until a superadmin calls `POST /v1/admin/countries/{code}/legal-texts` at least once. `GET /v1/policy-version` (the read side 1B.10's banner uses to decide whether to re-ask) is unaffected either way — it already returns `{ policyVersion: null }` rather than throwing. `ConsentsService` was changed in this pass to read through `CountriesService.getPolicyVersion()` instead of its own duplicate `PlatformSetting` query (a `TODO(#226)` left by the original PR now that #226 is in `dev`), with no change to the 500-on-null behaviour.
