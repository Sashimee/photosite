## Decisions for this step

- **Email over SMTP, not the Brevo HTTP API.**
  - The worker sends through nodemailer with `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD` and `SMTP_FROM`.
  - The preview and local dev use Mailpit, and production uses Brevo's SMTP relay (same code, different env).
  - This removes the account dependency (0.6) from the code path. Recorded in `docs/DECISIONS.md`.
  - In production, missing SMTP env fails worker startup. Nothing falls back silently.
- **The worker owns delivery.**
  - The `email` queue gets a real processor in `apps/worker`, and the API's `DevMailWorker` plus its `DEV_MAIL_WORKER` flag are deleted.
  - Auth emails (verify, reset, account-exists) keep their current job shapes, so sign-up works on every environment including the preview.
- **Templates.**
  - Plain TypeScript render functions in `apps/worker/src/email/templates/`, producing text and HTML. react-email is deferred until the brand kit (0.8) exists and is recorded as such.
  - All strings come from `packages/i18n` in the recipient's `User.locale`, falling back to `en`.
  - Every interpolated value is HTML-escaped.
  - Links are built only from `WEB_APP_URL` plus ids, never from user input.
- **Notification jobs carry ids, not personal data.**
  - A new `notify` queue job is `{ notificationId }`. The worker loads the user, locale, preferences and devices at send time, so emails and names don't sit in Redis.
  - The auth jobs are an existing exception, because the user may not exist yet (account-exists). That is documented in the queue schema.
- **Creation and idempotency.**
  - `NotificationsService.notify(userId, type, payload)` inserts the `Notification` row, then enqueues with BullMQ `jobId = notificationId`.
  - New nullable `emailSentAt` and `pushSentAt` columns record delivery per channel. The processor skips a channel that is already sent, so retries never double-send.
  - A `notify-sweep` repeatable job re-enqueues rows older than 5 minutes that are still pending a wanted channel. This covers an enqueue lost after the insert.
  - `channels` holds the channels chosen at creation after preferences.
- **Types for this step.**
  - `quote_received` (client, quote on their request or a direct quote).
  - `quote_accepted` and `quote_declined` (photographer).
  - `quote_withdrawn` (client).
  - `quote_expired` (both parties, from the expiry job, one per quote).
  - The type is a zod enum in `packages/shared`. The DB column stays `String` so later steps (chat, booking, verification) add types without a migration.
  - The payload holds ids and non-sensitive display values only: quote id, request title, total and currency, counterpart display name.
- **Preferences.**
  - A new `NotificationPreference` table (`userId`, `type`, `channel`, `enabled`, unique on the three). A missing row means the default: every channel on for this step's types.
  - `in_app` can't be disabled. Auth and security emails aren't notification types and always send.
  - Endpoints: `GET /v1/me/notification-preferences` (full matrix with defaults filled) and `PUT` (full replacement, strict).
- **In-app.** `GET /v1/notifications` (keyset by `createdAt desc, id`, `unread` filter), `GET /v1/notifications/unread-count`, `POST /v1/notifications/{id}/read` (owner only, 404 otherwise), and `POST /v1/notifications/read-all`.
- **Push.**
  - `POST /v1/me/devices` `{ expoPushToken, platform }` upserts on the token. A token seen with another user moves to the caller, because the device changed hands. The token is validated with Expo's token format.
  - `DELETE /v1/me/devices/{id}` is owner only.
  - The worker sends through `expo-server-sdk` (version pinned per `minimumReleaseAge`), with an optional `EXPO_ACCESS_TOKEN`.
  - Push content is a localised title and short body with no amounts or message text, plus a `data.url` deep link path.
  - Tickets are stored briefly in Redis. A `push-receipts` repeatable job checks them after about 15 minutes and deletes `Device` rows on `DeviceNotRegistered`.
- **Quote events.** `NoopQuoteEvents` is replaced by an implementation calling `NotificationsService`. The expiry job in the worker creates `quote_expired` notifications through a shared helper, not by calling the API.
- **Emails that aren't auth mail** include a link to the preferences page (`/{locale}/account/notifications`, built in lane B later) and a `List-Unsubscribe` header pointing to the same page. No marketing email exists, so no consent record is needed (COMPLIANCE: marketing requires consent).
- **Retention.** Notifications are deleted 12 months after creation by a line added to the existing cleanup sweep, or a small `notifications-cleanup` repeatable job. Recorded in `docs/COMPLIANCE.md` retention.
- **Rate limits.** Device registration is limited to 20 an hour per account through `RedisRateLimiter`. Read endpoints use the default API limits.

## 1A.7a tasks

1. **Contract** (`packages/shared/src/contract/notifications.ts`):
   - notification, preference matrix and device schemas plus the routes above, with error responses;
   - `NOTIFICATION_TYPES` enum;
   - a `NotifyJobSchema` plus `notify`, `notify-sweep`, `push-receipts` and `notifications-cleanup` in `queues.ts`;
   - regenerate openapi and the api-client, and add the routes to `not-yet-implemented.ts`.
2. **Schema** (schema-migrator, DATA-MODEL first):
   - `Notification.emailSentAt`, `pushSentAt`, and an index on `(userId, createdAt)`;
   - a partial index for the sweep on pending rows;
   - `NotificationPreference` as above;
   - migration via `migrate diff`, applied to photoo and photoo_test, and the tests updated.

## 1A.7b tasks

1. **Worker:**
   - email processor for the auth jobs and `notify`;
   - push sender and receipts job;
   - sweep and cleanup jobs;
   - env validation for the SMTP and Expo variables (Mailpit defaults only when `NODE_ENV` isn't production);
   - templates with i18n keys added to `en` (other locales through i18n-maintainer drafts).
2. **API:**
   - `NotificationsModule` (service, in-app routes, preferences, devices);
   - replace `NoopQuoteEvents`;
   - remove `DevMailWorker`, `DEV_MAIL_WORKER` and their env, docs and CI references;
   - OriginGuard on mutations, `requireSession` everywhere.
3. **Preview:** remove `DEV_MAIL_WORKER` from `infra/dokploy/preview/compose.yml` and pass SMTP env to the worker (Mailpit). The README's "verification email isn't delivered" limitation is removed.
4. **Tests:**
   - templates escape HTML and use the locale fallback;
   - a retry doesn't double-send (sent-at guards);
   - preferences suppress a channel, and in-app can't be disabled;
   - the sweep re-enqueues only stale pending rows;
   - device token reassignment, and deletion on `DeviceNotRegistered` (Expo client faked at its boundary);
   - read and read-all ownership, 404 for other users;
   - quote accept, decline, withdraw and expiry create the right notifications for the right users;
   - the auth sign-up integration test still reads the verification link from Mailpit, now sent by the worker.
5. **Security checkpoint** (not a listed 1E.6 checkpoint, but short and worth it): HTML injection in templates, open-redirect or link injection, device token hijack, notification IDOR, and personal data in Redis and logs.
