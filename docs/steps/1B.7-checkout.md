## Decisions for this step

- **Stripe on the web.**
  - Add `@stripe/stripe-js` and `@stripe/react-stripe-js` to `apps/web`. Load Stripe.js with `loadStripe` from the official CDN only (Stripe forbids self-hosting it).
  - `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` is validated in `lib/env.ts` as optional, `pk_test_…` or `pk_live_…`. It is baked at build time, so it is a Docker build arg in `web.Dockerfile` and is declared in `turbo.json` `env`.
  - When the key is absent (local dev against `STRIPE_FAKE=true`, CI), the checkout panel shows "Payment is not available in this environment" instead of mounting Elements. The fake gateway's `…_secret_fake` client secret can't be confirmed by Stripe.js, so there is no pretend payment in the browser.
  - CSP (`lib/csp.ts`), only on pages that need it would be ideal, but the header is global, so it is added globally and kept minimal per Stripe's CSP guide: `script-src https://js.stripe.com`, `frame-src https://js.stripe.com https://hooks.stripe.com`, `connect-src https://api.stripe.com`. Only when the publishable key is set. Security-reviewer checks the diff.
  - The Payment Element uses `clientSecret` from `POST /v1/bookings/{id}/payment-intent`; confirmation uses `stripe.confirmPayment` with `return_url` = the booking page. The web never marks a booking paid: the page shows "Payment processing" until the webhook moves the booking to `paid_held`, and refreshes on return.
- **Routes** (behind the sign-in redirect, `noindex`, `dynamic`):
  - `/{locale}/bookings`: my bookings as client (`GET /v1/bookings`, cursor "load more"), status badge, total, date.
  - `/{locale}/bookings/{id}`: status timeline (`pending_payment` → `paid_held` → `in_progress` → `delivered` → `released`; side exits `cancelled`, `refunded`, `disputed`), total, scheduled date and location, and the action for the current status (checkout on `pending_payment`, the rest in 1B.7b).
  - `/{locale}/dashboard/bookings` and `/{locale}/dashboard/bookings/{id}`: the photographer's view of the same data. 1B.8's "bookings, earnings" builds on these rather than duplicating them.
  - Quote accept (1B.5) replaces "Booking and payment arrive soon" with a link to the booking's checkout.
- **Actions (1B.7b)**, same mutation pattern as 1B.5 (api-client from client components, `router.refresh()`, i18n error mapping for 409/422/429):
  - photographer: deliver with a message and an external link (`externalLink`); file delivery via `fileIds` waits for the upload UI and is out of scope;
  - client: accept delivery (confirm dialog, states that it releases the payment); refund request, full or partial with a reason, only in `paid_held`, `in_progress`, `delivered`; cancel with an optional reason where the API allows it;
  - documents: receipt for the client, fee invoice for the photographer, only once `released`; the button fetches the presigned URL on click (it expires after 10 minutes) and opens it. 409 shows "document is being prepared".
- **Money.**
  - All amounts are shown as the API returns them via `lib/money.ts`. The client never computes totals, fees, refunds or payouts.
  - The refund amount input is whole currency units with cents, converted to integer cents; the server is the authority (422 on over-refund).
  - The photographer's payout after release must come from the ledger (API), never from `payoutAmount()`; until the API exposes it on the booking, the photographer page shows no payout figure and links the fee invoice. It must match the fee invoice to the cent.
  - `platformFee` isn't shown to the client.
- **Human follow-up.** Alex sets the Stripe publishable test key in the Dokploy preview env (build arg) together with the secret and webhook keys already listed in `human-followups.md`.
- **Tests.** Unit tests for the status-to-action mapping, the refund amount conversion and the CSP header with and without the key. Playwright with a real Stripe test payment is 1B.12.
