# Step 1E.2 – Monitoring (error reporting, uptime, alerting)

Plan reference: `docs/PLAN.md` step 1E.2. Owner: devops-engineer, with api-developer for the API wiring. `docs/PLAN.md` lists this as blocked by 1E.1 (staging); as with 1E.3, the preview already runs the full stack and is the environment where failures are actually happening tonight, so this targets the preview first and staging/production inherit it.

## The gap this step closes

`apps/web` initialises Sentry (`instrumentation.ts`, `instrumentation-client.ts`, `global-error.tsx`) and `apps/mobile` has `src/lib/sentry.ts`. **`apps/api` and `apps/worker` have neither** — a grep for Sentry in `apps/api/src` finds one comment in `logger.options.ts` and no SDK. So the two processes that hold auth, uploads, chat and (soon) payments report nothing when they throw: an unhandled API exception becomes a 500 in a log file nobody is reading, and a worker crash is only visible as a restarting container.

Tonight's two preview outages make the case concretely. The worker crash-looped on a missing `@photoo/i18n` (#124) and every public image 404'd from a disabled Traefik router (#129); both were found by hand, from the outside, hours later. Either would have been a single alert.

## Decisions for this step

- **Sentry in the API and worker, initialised before anything else** (`instrument.ts` imported first in `main.ts`), so an error thrown during bootstrap is still captured. A reporter that only works after startup misses exactly the failures that matter most.
- **No DSN is a no-op, never a crash and never a fallback that pretends.** Same rule `apps/web` and `apps/mobile` already follow: `SENTRY_DSN` absent means the SDK is not initialised and the app runs normally. Staging and production set `SENTRY_REQUIRED=true` so a missing DSN fails the boot there — the existing convention in `docs/steps/human-followups.md`, applied to two more apps.
- **Scrubbing is configured explicitly, not trusted to defaults.** `beforeSend` drops `authorization`, `cookie`, `set-cookie` and any `token`/`password`/`secret`-shaped key, and request bodies are not sent at all. The repo already redacts in `logger.options.ts`; the same list is shared rather than written twice, because two divergent redaction lists is how a token eventually reaches a third party. `sendDefaultPii` is false.
- **The error id is surfaced, the error is not.** An unhandled API exception returns the existing generic 500 shape plus the Sentry event id, so Alex can quote an id from a screenshot and find the trace. The message and stack never reach the client.
- **The worker reports job failures with context, not payloads.** Queue name, job id, attempt number and the error — never the job data, which can carry ids that map to people. A BullMQ job that exhausts its retries is an event worth seeing; the three intermediate failures are noise and are captured as breadcrumbs instead.
- **Uptime checks live outside the host.** A checker running on `dok.seil.pro` cannot report that `dok.seil.pro` is down. The preview gets an external HTTP check against `https://footoo.bas.lu/health` and `/ready`, and this is the one part that needs an account — see the follow-ups. Until then, 1E.2b ships a self-hosted check that still catches *service*-level failure (a dead API behind a live host) and says plainly in the README that it cannot catch host-level failure.
- **What is actually checked matters more than that something is checked.** `/health` is liveness. `/ready` must mean "this process can serve traffic": database reachable, Redis reachable, and for the worker, queues attached. A readiness endpoint that returns 200 unconditionally is worse than none, because it converts an outage into a green dashboard.
- **The backup heartbeat from 1E.3 is checked here.** 1E.3a writes a heartbeat object on every successful run; 1E.2b alerts when it is older than 36 hours (a 24-hour schedule plus margin). That closes the loop the backup plan deliberately left open rather than faking.
- **The worker's crash loop gets a named check.** A container that restarts more than N times in an hour is a distinct alert from "the service is down", because a crash loop can keep a health check flapping green. This is exactly the shape of #124.
- **Alert routing is one channel to start**: email to Alex, with the message naming the environment, the check and the last known good time. Telegram is in `docs/PLAN.md` as an option and is added only if email proves too slow — an alerting setup nobody reads is worse than none, and two channels on day one is how that starts.
- **Alert on symptoms, not on every error.** Page-level alerts: API 5xx rate over a short window, `/ready` failing, the worker crash loop, and the backup heartbeat. Individual exceptions go to Sentry and are reviewed, not alerted on. The first version of this that pages on every 500 is the version that gets muted in a week.
- **No log shipping in this step.** `docs/PLAN.md` mentions it; container logs on a single preview host are reachable through Dokploy, and a log pipeline is a real piece of infrastructure that deserves its own step once there is more than one host. Recorded here so the omission is visible. (Noted: the Dokploy API exposes no container-log endpoint — verified by probing `docker.getContainerLogs`, `docker.getContainersLogs`, `docker.getLogs` and `docker.containerLogs`, all 404 — which is why diagnosing the worker crash needed a person on the host. That alone is an argument for shipping logs sooner rather than later.)

## 1E.2a tasks

1. `apps/api/src/instrument.ts` and the worker equivalent, imported as the first line of each `main.ts`; env schema gains `SENTRY_DSN`, `SENTRY_ENVIRONMENT`, `SENTRY_TRACES_SAMPLE_RATE` (default 0) and `SENTRY_REQUIRED`.
2. Shared redaction list extracted from `logger.options.ts` and used by both the logger and `beforeSend`.
3. Nest exception filter returning the event id; worker `failed` handler reporting on final attempt only.
4. Preview compose passes the new env to api and worker.
5. Tests: no DSN leaves the SDK uninitialised and the app boots; `SENTRY_REQUIRED=true` without a DSN fails the boot; `beforeSend` strips each header and key in the list; the 500 response carries an event id and no message; a job failure reports once on the final attempt, not per retry.

## 1E.2b tasks

1. Verify and, where needed, tighten `/ready` in both apps so it genuinely checks its dependencies.
2. Uptime checks and the alert rules above, as configuration in `infra/`, with a README section on what each alert means and what to do first.
3. The backup heartbeat check (depends on 1E.3a).
4. A deliberate failure drill: stop the worker, confirm the alert arrives, restart it, confirm recovery. Record the observed delay. An alert that has never fired is a hypothesis.

## Human follow-ups

- **A Sentry account and two project DSNs** (api, worker) — part of 0.6. Everything in 1E.2a ships and is tested without them; the SDK simply stays uninitialised until the DSN is set.
- **An external uptime provider** (any of the usual free tiers) so that a host-level outage is detectable at all. Until then the self-hosted check covers service-level failure only, and the README says so rather than implying coverage it does not have.
- **Confirm the alert email address** (and whether a second channel is wanted later).
