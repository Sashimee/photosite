| D6 | Languages at launch | English (default), French, German, Portuguese, Spanish; Luxembourgish and Italian as follow-up locales | English only | Luxembourg's largest communities; i18n from day one is far cheaper than retrofitting |
| D7 | Portfolio provenance | AI-generated detection + reverse image search + C2PA content credentials + EXIF signals, scored and sent to admin review | AI detection only | Catches both generated images and stolen work; never auto-bans, admin decides |

| D10 | Storage | S3-compatible object storage in the EU (Hetzner Object Storage first choice; Scaleway or Cloudflare R2 acceptable) | MinIO on the VPS; VPS disk | Keeps the VPS small, cheap egress, easy backups and CDN |
| D11 | Email | Brevo (EU) for transactional email | Resend; Postmark; self-hosted SMTP | EU hosting, GDPR posture, free tier, marketing email later. **Revised in 1A.7b:** the worker sends through Brevo's SMTP relay via nodemailer (`SMTP_HOST`/`SMTP_PORT`/`SMTP_SECURE`/`SMTP_USER`/`SMTP_PASSWORD`/`SMTP_FROM`) instead of Brevo's HTTP API, so local dev and the preview point the same code at Mailpit and the account dependency (0.6) never blocks sign-up working end to end. Production requires every SMTP variable and fails to start without them; nothing falls back silently. The API's `DevMailWorker` is removed — the worker owns delivery for both the `email` queue (auth mail) and the new `notify` queue (in-app/email/push notifications) |
| D12 | Scope | Phased: MVP launch, then increments | Everything before launch | Real users in Luxembourg sooner; job board and ads automation follow |
| D13 | Roles | One role chosen at sign-up (client, photographer, professional); more roles can be added later on the same account | Fixed single role | A client may become a photographer; avoids duplicate accounts |
| D14 | Photographer verification | Country-specific document upload + manual admin review; Stripe Connect KYC handles identity and payouts separately | Stripe Identity; self-declaration | Luxembourg needs an autorisation d'établissement and VAT number check that only a human can judge at this stage |
| D15 | Chat | Self-hosted Socket.IO gateway in the API, Redis adapter, messages in PostgreSQL, attachments in object storage | Stream Chat; Sendbird | Full data control, no per-user fee |
| D16 | Admin backend | Separate Next.js app `apps/admin` on admin.photoo.lu, mandatory 2FA, RBAC | Route group inside the public web app | Separate origin and bundle shrink the attack surface |
| D17 | Analytics | GA4 through Google Tag Manager with Consent Mode v2 behind a self-built consent banner; Firebase Analytics on mobile behind explicit consent and iOS ATT | Third-party CMP | Full control of consent records, no vendor fee |
| D18 | Country model | `Country` configuration table (currency, VAT rate, required verification documents, legal texts). Luxembourg only enabled at launch | Hard-coded Luxembourg | "Luxembourg now, world later" without a rewrite |
| D19 | API contract tooling | zod 4 schemas and a route registry in `packages/shared`, OpenAPI 3.1 generated with `@asteasolutions/zod-to-openapi`; typed client with `openapi-typescript` + `openapi-fetch`; mock server with Prism. The NestJS API (1A) serves the same registry | NestJS-first Swagger decorators; orval/hey-api generated SDKs | Contract exists before the API, clients build against a mock, one source of truth for validation and docs |
| D20 | Auth library | Better Auth 1.7 with the Prisma adapter, Argon2id via its custom `password.hash/verify`, plugins `bearer` (mobile), `two-factor` (TOTP). Better Auth stores session tokens in plain text, so a thin adapter wrapper hashes `session.token` (SHA-256) on write and on lookup to meet SECURITY.md; covered by tests in 1A.2 | Passport + hand-written sessions | Covers email, OAuth, 2FA and bearer out of the box; the one SECURITY.md gap is closable in a small, testable wrapper. Decided in 1A.1 because Account/Session shape depends on it. **Revised in 1E.6 (issue #15):** no Redis `secondaryStorage` — with it set, Better Auth mirrors every session under its raw token as the Redis key (30-day TTL) and serves reads from there first, bypassing the SHA-256 hash entirely and going stale against out-of-band role/status changes. Redis is used only through `rateLimit.customStorage` (our own INCR+EXPIRE Lua script); sessions live solely in Postgres, hashed. The `haveibeenpwned` plugin also runs the check inside `password.hash`, which sign-in calls on its user-not-found timing decoy and leaks account existence (issue #17); replaced with an explicit, timed, fail-open call in the sign-up and password-reset-confirm controllers only, never in `password.hash`/`verify`. |
| D21 | CSRF for cookie-authenticated auth routes | Origin allow-list check (`WEB_ORIGINS`) plus `Sec-Fetch-Site` rejection on cross-site, `SameSite=Lax` cookies, and JSON-only request bodies (form content types rejected with 415) | Double-submit CSRF token | Better Auth's contract routes are called via `auth.api.*` directly from Nest controllers (no `Request`, so Better Auth's own `originCheckMiddleware`/`formCsrfMiddleware` never run for them, see issue #16); a small Nest guard (`OriginGuard`) enforces the same property without adding a token the client has to read from a cookie and echo in a header. GET requests and bearer-only (no-cookie) requests are exempt, since neither carries an ambient credential a third-party site could ride |
| D22 | Direct-quote price at accept time | A direct quote's line item, `productTierId` and price are snapshotted at creation (1A.5). At accept, the client is still charged the snapshotted price as long as `productTierId` is still non-null and the profile/product are still published/active; the price is never recomputed from the current tier. If the tier was hard-replaced (`onDelete: SetNull`) or the profile/product is no longer published/active, the quote is marked `expired` at accept time and the client gets 409 instead of booking a stale or now-invalid offer | Recompute the price from the live tier at accept; always honour the snapshot regardless of profile/product state | The snapshot is what the client agreed to and what the licence terms (`licenceUsage`/`licenceTextVersion`) refer to, so silently repricing would break that agreement; but booking against a profile or product that has since been unpublished/deactivated would create a booking nobody can fulfil |
| D23 | Report shape for DSA notice-and-action | `Report.reporterId` is nullable so a signed-out visitor can file a notice, and there is **no** `category` field in Phase 1: the free-text `reason` plus admin triage carries it. A `ReportCategory` enum is added only once real reports show which buckets exist | Require an account to report; ship a guessed category enum now | DSA notice-and-action must accept notices from anyone, so a required reporter would be non-compliant. A category enum invented before any report exists would be guessed taxonomy in a migration - cheaper to add later from evidence than to migrate away from a wrong one. Settles the mismatch in #148, where the contract's `AdminReportSchema.reporterId` is required and the plan's `category` has no place in the contract |
| D24 | Job board `city` filter shape | `GET /v1/job-offers?city=` stays a case-insensitive exact match on `JobOffer.city` (`lower(jo.city) = lower($1)`), the same shape `ProfilesRepository.search`'s `city` filter already uses, instead of a `City`/PostGIS radius lookup as 1A.13's step doc called for | Route the filter through a canonical `City` table and `ST_DWithin`, matching the request feed's geo search | There is no canonical `City` table in this codebase — 1B.4a's `cities` endpoint groups existing profile rows by name at read time, it does not geocode or normalise one. Building real city-radius search needs that table plus `lat`/`lng`/`radiusKm` query params on `GET /v1/job-offers`, which is a contract change beyond a review fix-up (PR #266). `JobOffer.location` is still stored and returned (coarsened for anonymous callers), so the radius filter can be added later without a migration. Tracked in issue #274 |
| D25 | Report-free takedown (1D.6c) | `POST /v1/admin/reports/direct-takedown` synthesises a `Report` row (`reporterId: null`, `reason: MODERATOR_INITIATED_REPORT_REASON`, `status: 'resolved'` from creation) and takes down the target in the same transaction, rather than a parallel "takedown" action with no `Report` row. Scoped to the two entry points the plan names, `photographer_profile` and `job_offer`; the request schema's `targetType` enum only accepts those two | A first-class takedown action independent of `Report`, with its own audit shape and its own notice path; widening scope to all five report target types now | 1D.6a already built the entire pipeline this needs: `AdminAuditService`, `notifyDecision` (which already skips the reporter when `reporterId` is null and always notifies the owner — the DSA statement-of-reasons obligation does not depend on how the content was found), `restoreReportTarget`, and the moderation queue/detail views that key off `Report.id`/`targetId`. A parallel action would duplicate all four and give a moderator two places to look for the same kind of decision. The rejected alternative of a `source: 'user' \| 'moderator'` discriminator on `Report` would separate "a stranger complained" from "staff found it themselves" without overloading `reporterId: null`, which today only ever means "anonymous public report" — but that is a `schema.prisma` change outside this step's scope (api-developer does not edit the schema); `MODERATOR_INITIATED_REPORT_REASON`, a fixed, readable `reason` string, is the interim signal a future UI can match on. `portfolio_image` and `request` already have no admin-only viewing surface this step adds (a moderator reviewing an image or request already arrives via a report); `job_application` carries the applicant's own message and a report-free removal of another person's content without any complaint is more likely to need its own review than to reuse this shape as-is. Revisit if a moderator workflow for those three materialises |
| D26 | Where email templates live (1D.7c) | The pure email render code (templates, `format-message`, `html`, `MailMessage`) moves from `apps/worker` into a new `packages/email` (`@photoo/email`) used by the worker to send and by the API to render the admin preview; sending, queues and push stay in the worker | Make `@photoo/worker` a runtime dependency of the API; render previews inside the worker via a BullMQ request/response job; duplicate the templates in the API | The API must never pull in the worker's Nest modules, nodemailer or queue consumers just to render HTML, and a request/response round-trip through Redis for a synchronous admin page adds a failure mode for no gain. A package with no I/O is the one place both can import and the preview is guaranteed to render what is actually sent |
| D27 | Admin data-request list shows the email (1D.2b) | `GET /v1/admin/data-requests` returns the user's full email to `support`, and `apps/admin` masks it in the table, the same split as the admin users list. After deletion the row carries the anonymised `deleted-<id>@deleted.invalid` address. The route is read-only, never maps `exportKey`, and writes no `AuditLog`, like the other admin GET routes | Mask server-side; omit the email | Support must be able to match a request to the person who wrote in; one masking rule across admin views |
| D28 | Build priority after Phase 1 cleanup stalled visible progress (2026-09-26) | Phase 1 features come first. The follow-up cleanup backlog is labelled `phase-2` and waits for Phase 2 (#425 mobile in-app deletion stays required before App Store submission). Reviews fix blocker findings only; the rest is filed as `phase-2` issues. After each feature merges into `dev` with green CI, a `dev`→`main` release goes out so footoo.bas.lu shows it | Finish the 26-issue cleanup backlog first; release only on request | A day of cleanup produced nothing visible on the preview; testers need features to try |
